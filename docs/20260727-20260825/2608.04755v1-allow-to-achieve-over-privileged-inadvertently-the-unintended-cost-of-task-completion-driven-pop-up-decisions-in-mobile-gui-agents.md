## 摘要
移动GUI代理在执行任务过程中经常会遇到系统权限对话框，然而，它们仅授予所委托任务必要权限的能力在很大程度上仍未得到检验。我们对这种能力进行了系统性研究，并将其称为“权限素养”。我们基于任务相关性和隐私风险构建了一个四级权限框架，并由三位GUI代理安全领域的独立专家对评估场景进行了验证。我们将Android风格的权限弹出窗口注入到真实GUI任务中，并使用同步的带注释截图和UI树层次结构评估四个前沿多模态大语言模型，使请求者、权限、理由和可用操作对代理可见。除主要研究外，我们还进行了受控干预，分别改变任务上下文和代理可见的请求者身份。在相同的日历任务下，仅将请求者从Calendar更改为PiMusic，授权次数就从26/32降至0/32，揭示了一种强烈但受任务制约的应用信任偏差。在保持弹出窗口固定不变的同时改变任务上下文，也会显著改变授权决策，揭示了一种系统性的任务优先覆盖。提示干预可以减少不必要的授权，但其效果在不同模型间不一致，且可能以抑制正当授权为代价。这些结果表明，将任务执行与权限授权分离是未来工作的一个有前景的设计方向。

## Abstract
Mobile GUI agents routinely encounter system permission dialogs during task execution, yet their ability to grant only permissions that are necessary for the delegated task remains largely unexamined. We present a systematic study of this capability, which we term Permission Literacy. We construct a four-level permission framework based on task relevance and privacy risk and validate the evaluated scenarios with three independent experts in GUI-agent safety. We inject Android-style permission popups into real GUI tasks and evaluate four frontier multimodal large language models using synchronized annotated screenshots and UI-tree hierarchies, making the requester, permission, justification, and available actions accessible to the agent. Beyond the main study, we conduct controlled interventions that separately vary task context and agent-visible requester identity. Under the same Calendar task, changing only the requester from Calendar to PiMusic reduces grants from 26/32 to 0/32, revealing a strong but task-conditioned App-Trust Bias. Holding a popup fixed while changing task context also substantially changes authorization decisions, revealing a systematic Task-Prior Override. Prompt interventions can reduce unnecessary grants, but their effectiveness is inconsistent across models and may come at the cost of suppressing legitimate grants. These results suggest that separating task execution from permission authorization is a promising design direction for future work.

# 论文总结

## 1. 核心问题与整体含义（研究动机和背景）

- **核心问题**：移动 GUI 代理在自主执行任务时，经常遭遇系统权限弹窗（麦克风、通讯录、位置等），但它们是否具备“只授予当前委托任务所必需权限”的判断能力，此前未被系统研究。
- **提出概念**：作者将该能力定义为 **Permission Literacy（权限素养）**，即代理需要依据最小权限原则，识别哪些权限是任务必需的，哪些只是便利、无关或过度风险的，并在未经用户明确授权时拒绝或延迟授权。
- **动机**：
  - 现有 GUI 代理基准（如 WebArena、AndroidWorld、AndroidLab 等）几乎全部以任务成功率为核心指标，权限弹窗被视为需要快速“绕过”的障碍，而非安全决策点。
  - 安全研究多聚焦对抗性威胁、提示注入、恶意界面等，但未观察良性环境中代理面对标准系统权限弹窗时的行为。
  - 自主代理可能在单次长会话中持续积累不必要的权限，形成“静默的隐私侵蚀”，而人类用户往往对此无感知。
- **整体含义**：任务完成驱动的授权偏差可能导致系统性过度授权；论文主张将任务执行与权限授权分离，作为未来设计方向。

## 2. 方法论

- **整体思路**：在真实 Android 任务中注入合成权限弹窗，测量代理的允许（Allow）与拒绝（Deny）行为，而非仅看能否完成任务。
- **四级权限分类框架**：
  - **L1（合法）**：权限支持当前任务的必要功能，预期允许。例如 Clock 通知权限用于闹钟提醒。
  - **L2（弱相关）**：只提供次要便利，非当前任务必需，预期拒绝/延迟。例如 Contacts 访问日历以显示生日。
  - **L3（无关）**：与当前任务几乎没有功能关联，预期拒绝/延迟。例如 Clock 访问通讯录以“和朋友分享闹钟”。
  - **L4（过度风险）**：请求高敏感能力用于非必要功能，代理不应自行批准，预期拒绝/延迟。例如 Clock 访问麦克风以“用语音命令停止闹钟”。
- **实验平台与输入**：
  - 基于 **AndroidLab** 框架，代理每一步同时接收：
    - 带数字边界框标注的截图；
    - 同步的清理后 UI 层级树（XML）。
  - 这种双模态设置确保弹窗中的请求者、权限、理由、按钮对代理完全可见，因此错误授权属于**决策层失败**，而非视觉/OCR 失败。
- **弹窗注入**：在每个任务执行到第三步交互时，注入合成权限弹窗并替换当前 UI 状态。每个（应用，权限级别）组合独立测试。
- **模型**：四个前沿多模态大模型（MLLM）——Doubao（doubao-seed-2-0-lite）、Gemini（Gemini-3-flash-thinking）、GPT（GPT-5）、Qwen（qwen3-vl-235b-a22b-thinking）。统一系统提示、温度设为 0，输出确定性。
- **统计方法**：汇报明确分子/分母；使用 Wilson 95% 置信区间；预设对比采用双侧 Fisher 精确检验 + Holm 校正；以模型分层结果为主要依据。
- **受控干预设计**：
  - **平衡的任务 × 请求者实验**：固定权限内容、布局、按钮、时间，只改变活动任务（Calendar/PiMusic）和可见请求者（Calendar/PiMusic）。
  - **任务优先覆盖实验（B vs C）**：固定同一个异常 Calendar 弹窗（通讯录权限、分享播放列表理由），仅改变任务上下文（PiMusic vs Calendar）。
  - **自然验证**：使用 Calendar 位置访问的“自然”弹窗，测试是否仅由异常措辞导致。
  - **跨权限族复制**：固定 Contacts 文件访问弹窗，比较 PiMusic 任务与 Contacts 任务。
  - **提示缓解**：测试 lite、structured、few-shot、verifier-style、functional-chain-aware 五种提示策略。

## 6. 主要结论与发现

- **发现一：Task-Conditioned App-Trust Bias（任务条件化的应用信任偏差）**
  - 在 Calendar 任务下，仅将可见请求者从 Calendar 改为 PiMusic，授权从 26/32 降至 0/32，四个模型方向一致（Doubao/Gemini p≈6.22×10⁻⁴，GPT p=0.014，Qwen p=0.077）。
  - 但在 PiMusic 任务下，Calendar 请求者并未被更偏好（9/32 vs 12/32），说明该偏差不是对系统应用的普遍偏好，而是任务上下文与请求者身份交互作用的结果。
- **发现二：Task-Prior Override（任务优先覆盖）**
  - 固定同一个弹窗，仅将任务从 PiMusic 改为 Calendar，授权率在所有模型上均上升：例如 Doubao 0/10→9/14，Gemini 6/9→14/14，GPT 0/12→7/14，Qwen 0/10→13/14。
  - 自然化 Calendar 位置请求也获得较高授权率；第二个权限族（Contacts 文件访问）重复出该模式，但效应大小因模型和权限族而异。
  - 定性思考痕迹显示，模型常以“任务需要继续”而非弹窗中的真实理由来合理化授权。
- **发现三：Mitigation Instability（提示缓解的不稳定性）**
  - lite 提示能降低 L2–L4 授权，但可能同时压低 L1 正当授权。
  - structured 提示几乎消除 L2–L4 授权，但 L1 授权率大幅下降，存在安全-效用权衡。
  - 在定向子集上，某些组合校准良好（如 Doubao structured、Gemini few-shot），但 GPT、verifier-style 等会错误抑制正当授权。
  - functional-chain-aware 提示能大幅降低风险授权，但 L1 保留率仍不均匀。
- **总体结论**：
  - 当前 GUI 代理不存在稳定、上下文无关的最小权限策略；
  - 任务完成偏向会掩盖权限请求本身的合理性；
  - 提示工程只能部分缓解，不能统一校准；
  - 将任务执行与权限授权分离（例如独立授权层）是未来值得探索的设计方向。

## 7. 优点

- **研究空白填补**：首次系统评估 GUI 代理的权限决策能力，而非仅评估任务成功率。
- **方法论严谨**：
  - 设计四级权限分类，区分语义相关性与隐私风险；
  - 双模态输入（截图 + UI 树）排除感知失败干扰，将错误归因于决策层；

  - 固定弹窗、改变任务上下文的对比（B vs C）提供因果证据；

- **模型异质性明确**：所有结果按模型分层汇报，不掩盖个体差异。
- **统计谨慎**：使用 Fisher 精确检验、Holm 校正、Wilson 置信区间，并将非授权动作保留在分母中。
- **提示缓解探索全面**：涵盖 lite、structured、few-shot、verifier、functional-chain-aware 等多种策略，并做 held-out 测试。

## 8. 不足与局限

- **评估范围有限**：
  - 仅使用一个代理框架（AndroidLab）、五个 Android 应用、有限的任务集和权限类型。

  - 未扩展到 iOS、Web 等其他平台或更多代理架构。
- **样本量与统计功效**：

- **标签与用户偏好**：
  - 专家验证只能保证操作化标签的一致性，不能代表真实用户的多样偏好；
  - contacts_L1 等场景存在“便利依赖”歧义，需敏感性分析处理。
- **机制归因不足**：
  - 暴露的思维链痕迹不可靠，仅作为定性诊断，不能证明内部决策机制；

- **提示缓解的可推广性**：
  - 缓解实验是定向、非穷尽的；某些 held-out 情境下校准效果不持续；
  - 提示策略可能过度拒绝正当权限，带来任务效用损失。
- **长期影响未评估**：研究是单次会话内的决策，未跟踪长期累积授权或用户真实环境中的人机交互。
