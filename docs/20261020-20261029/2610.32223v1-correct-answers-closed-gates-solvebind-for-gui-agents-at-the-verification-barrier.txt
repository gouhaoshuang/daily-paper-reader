ABSTRACT
Real-world websites and applications often deploy CAPTCHAs and other anti-
automation mechanisms that use behavioral signals, such as interaction trajecto-
ries and timing, rather than outcomes alone, to distinguish human operators from
automated agents. We refer to such settings as protected GUI environments, where
correctly solving a local verification task is insufficient for end-to-end task com-
pletion. An agent must also convert solver outputs into interactions accepted by
the environment and adapt its execution based on runtime feedback under time
constraints. For these environments, we introduce SolveBind, a GUI-agent frame-
work that combines hierarchical solving with runtime supervision. A hierarchical
solving tree decomposes verification into interdependent Perceive, Ground, Solve,
Act, and Verify capabilities. A runtime supervisor grounds action commitments
in tool-derived evidence to allow them to be revised as new evidence arrives,
and mediates execution under explicit recovery budgets. For verification, across
nine CAPTCHA task families and nine backbone models, SolveBind achieves
the highest success rate on eight backbones, outperforming the strongest baseline
by 13.3–34.5 percentage points. For end-to-end task completion, it achieves the
highest success rate on all six backbones evaluated on AndroidWorld. In a paired
GPT-5.5 analysis, MobileAgent produces correct answers but fails dynamic ver-
ification on 13 of 90 tasks; SolveBind succeeds on seven of these tasks. With
automatic submission retained, removing binding reduces success from 82.22%
to 71.56% and increases latency and token usage. Recovery caps reduce execu-
tion cost with a small observed success trade-off: removing them raises success
from 82.22% to 83.56%, while increasing latency and token usage to 3.7× and
2.4× their full-supervision values, respectively. These results support evidence-
grounded execution control while identifying a success–cost trade-off in recovery
and failure boundaries of heuristic submission rules.

INTRODUCTION
GUI agents aim to translate users’ task intents into complete interaction workflows, transforming
requests such as retrieving information, filling out forms, or managing files into action sequences
that span multiple pages and applications (He et al., 2024; Agashe et al., 2025a; Rawles et al.,
2025). Real-world services, however, often deploy anti-automation mechanisms that rely on behav-
ioral signals, such as interaction trajectories and timing, rather than outcomes alone, to distinguish
human operators from automated agents (Acien et al., 2022; Wang et al., 2026). Even if an agent
has identified a viable solution, it must still advance the task through interactions accepted by the
environment within the available time budget, so verification checkpoints become an integral part of
task execution rather than an external obstacle to it.

Consider the invoice-download task in Figure 1. The agent locates the booking, requests the invoice,
and reaches a human-verification gate before saving the file. Although it correctly identifies the
target, the attempt can still be rejected because the verification mechanism also evaluates behavioral
signals such as the drag trajectory and timing (Acien et al., 2022; Song et al., 2026). The bottleneck
therefore lies not only in solving the local challenge, but also in executing the solution in a manner
accepted by the environment. Re-solving may not resolve the rejection, while repeated attempts
consume the limited verification budget and delay task completion. This illustrates why protected
GUI environments require agents to coordinate local solving with feedback-aware execution.
Interactive verification and behavioral discrimination make this a broader execution problem rather
than an issue confined to a single CAPTCHA type. HLL(Song et al., 2026) jointly evaluates task
responses and interaction evidence in dynamic CAPTCHA tasks, revealing a gap between correctly
solving a challenge and passing verification. Turing Test on Screen(Zhu et al., 2026) further shows
that touch behavior alone can distinguish agents from humans. We refer to GUI environments
equipped with anti-automation mechanisms that monitor interaction behavior and distinguish au-
tomated from human operation as protected GUI environments. Such evidence may derive from a
single action, a local interaction sequence, or a longer execution history, shaping the conditions un-
der which subsequent execution proceeds (Acien et al., 2022; Song et al., 2026; Wang et al., 2026).
We focus on two outcomes in these environments: task success rate and end-to-end latency.
Existing GUI-agent frameworks combine hierarchical planning with specialized tools to improve
long-horizon decision making and interface grounding (Agashe et al., 2025a;b). In protected set-
tings, however, these capabilities must be coordinated with the agent’s current execution state.
Redundant actions and costly planning or reflection calls increase end-to-end latency (Abhyankar
et al., 2026), while undetected action failures can lead to ineffective repetition and error accumula-
tion (Zhang et al., 2026). The central challenge is therefore determining which solver outputs should
constrain execution and which observations should cause the agent to revise its next action. Our key
idea is to treat solver outputs as runtime evidence that can be retained and revised. When the evi-
dence supports a concrete action, the runtime records it as an action commitment and prioritizes that
action until new observations update that evidence or trigger reconsideration. This coordination is
motivated by rational metareasoning: computation should be weighed against both its cost and its
expected value for the next decision (Russell & Wefald, 1991; Hay et al., 2012).
Building on this idea, we introduce SolveBind, a GUI-agent framework combining hierarchical
tool-based solving with runtime supervision. A hierarchical solving tree organizes capability depen-
dencies and alternative tool branches, allowing the model to select the capabilities needed for the
current execution state. The runtime supervisor binds tool-derived evidence to action commitments
and, under full supervision, prioritizes admissible pending commitments over conflicting action pro-
posals. Execution feedback then updates a shared protocol state that governs workflow progression,

• We formulate three design principles from rational metareasoning: evidence-grounded commit-

RELATED WORK
GUI agent harnesses and native policies. GUI-agent research follows two complementary direc-
tions. External harnesses organize multimodal models through planning, tool use, and memory:
WebVoyager (He et al., 2024) supports web interaction; MobileAgent (Wang et al., 2024) and Ap-
pAgent (Zhang et al., 2025) coordinate mobile perception and action; Agent S (Agashe et al., 2025a)
uses experience-augmented hierarchical planning; and Agent S2 (Agashe et al., 2025b) combines
a generalist planner with specialist grounding. Native policies, by contrast, directly learn interface
grounding (Cheng et al., 2024; Gou et al., 2025; Hong et al., 2024) or integrate perception, rea-
soning, and action generation (Qin et al., 2025). Evaluation spans action prediction from recorded
interaction traces (Deng et al., 2023; Rawles et al., 2023) and task completion in executable envi-
ronments (Zhou et al., 2024; Xie et al., 2024; Rawles et al., 2025). These settings primarily assess
grounding accuracy and goal achievement, rather than whether execution is accepted based on in-
teraction behavior. SolveBind builds on the external-harness paradigm but explicitly coordinates
task solving with environmental acceptance: an action may target the correct interface element yet
still be rejected, requiring execution to account for both the intended effect and the conditions under
which the environment permits progress.
Execution verification and recovery. Existing frameworks differ in where verification intervenes,
what execution decisions it constrains, and how recovery is bounded. VeriSafe (Lee et al., 2025)
translates user instructions into logical specifications and checks proposed actions before execution,
advising on predicate mismatches while blocking critical violations. VLAA-GUI (Han et al., 2026)
verifies action effects and completion claims, using repetition detection and strategy-switching di-
rectives to constrain subsequent decisions while leaving replacement actions to its manager. Struc-
tAgent (Wu et al., 2026) combines low-level effect checks with verifier-backed milestone updates
and can return execution to the planner. MAPLE (Guo et al., 2025) compares observed states with
predicted postconditions and constructs recovery plans, returning to high-level replanning after two
recovery failures. MobileUse (Li et al., 2025) uses hierarchical, on-demand reflection to support
recovery while limiting overhead. VeriGUI (Zhang et al., 2026) learns effect prediction and self-
correction within the policy, rather than relying on an independent dispatch controller. In SolveBind,
every action dispatch passes through the supervisor. Under full control, admissible pending com-
mitments take precedence over conflicting action proposals. Execution feedback updates their sup-
porting evidence, preserving valid commitments while triggering reconsideration when that support
no longer holds. Recovery is budgeted by category, with attempts and refreshes tracked separately.
Our focus is therefore not verification alone, but the coordination of evidence-supported dispatch
with rejection-aware, bounded recovery. More broadly, ReAct and Reflexion incorporate environ-

mental or evaluative feedback into reasoning (Yao et al., 2022; Shinn et al., 2023), whereas intrinsic
self-correction may fail without reliable external feedback (Huang et al., 2024). Our baseline cases,
detailed in Appendix D.8, reveal a complementary failure mode: an agent may correctly diagnose a
failure yet still repeat the rejected action.
Protected interaction and execution efficiency. CAPTCHA research has documented vulnerabil-
ities in semantic image challenges (Sivakorn et al., 2016) and the human burden of deployed verifi-
cation (Searles et al., 2023). Recent solvers exploit language and vision-language models: Halligan
formulates visual CAPTCHA solving as search (Teoh et al., 2025), while Oedipus decomposes rea-
soning CAPTCHAs into DSL-guided substeps (Deng et al., 2025). Salman and Bicakci (Salman
& Bicakci, 2026) study adaptation across CAPTCHA encounters by using VLM outputs to update
a detector; our focus is evidence reuse and revision within task execution. Open CaptchaWorld
evaluates multimodal agents on diverse interactive CAPTCHA puzzles (Luo et al., 2025). Next-
Gen CAPTCHAs develops scalable interactive challenges around persistent human–agent capabil-
ity gaps (Liu et al., 2026). Beyond puzzle solving, behavioral detection considers how interactions
are performed: BeCAPTCHA-Mouse (Acien et al., 2022) distinguishes human and synthetic input
using trajectory-level neuromotor features, while FP-Agent (Wang et al., 2026) finds behavioral fin-
gerprints more discriminative than shared browser fingerprints. HLL (Song et al., 2026) evaluates
answers and interaction evidence, while Turing Test on Screen (Zhu et al., 2026) measures the dis-
tinguishability of agent-generated touch behavior. Together, these studies motivate separating local
challenge solving from environmental acceptance. ReCAP (Chen et al., 2026) addresses CAPTCHA
solving through trajectory generation and self-corrective fine-tuning of native GUI policies. Its in-
teractive benchmark evaluates puzzle solving but does not simulate behavioral biometrics such as
cursor speed or acceleration. In contrast, SolveBind leaves the backbone unchanged and coordinates
execution at runtime under interaction-dependent validation. The distinction concerns the accep-
tance criterion and execution-control mechanism, rather than whether the task itself is interactive.
Finally, redundant actions and expensive planning or reflection increase end-to-end latency (Ab-
hyankar et al., 2026), motivating joint evaluation of task success and completion time rather than
treating rapid failure as efficient.
Runtime supervision and metareasoning. The separation of action proposals from external con-
trol is well established in supervisory control of discrete-event systems (Ramadge & Wonham, 1987)
and shielded reinforcement learning (Alshiekh et al., 2018). We adopt this architectural separation,
but not its formal guarantees: admissibility is determined by runtime predicates over accumulated
evidence, without guarantees of correctness or non-blocking behavior. Our design rationale instead
draws on metareasoning, which weighs computation against its cost and expected value for sub-
sequent decisions (Horvitz, 2013; Russell & Wefald, 1991; Zilberstein, 1996; Hay et al., 2012),
as well as resource-rational accounts of cognition (Lieder & Griffiths, 2020). These perspectives
motivate acting once sufficient evidence is available, revising commitments when their supporting
evidence changes, and bounding recovery once further computation is unlikely to improve subse-
quent decisions. These principles remain empirical design choices rather than consequences of an
optimal metareasoning policy. In our ablations (Section 5.4), relaxing mediation, fail-safe defaults,
or supervision reduces success rates while increasing latency and token usage. Removing only the
recovery cap yields slightly higher observed success at substantially greater latency and token usage,
supporting bounded recovery as a practical success-cost trade-off.

3.2
DESIGN PRINCIPLES FROM A RATIONAL METAREASONING PERSPECTIVE
Protected GUI execution requires deciding whether to continue solving, act on available evidence, or
reassess an attempt. Additional computation and evidence gathering may improve the next decision,
but both consume execution time. Rational metareasoning weighs the expected decision benefits of
computation against its costs (Russell & Wefald, 1991; Hay et al., 2012). We use this perspective to
guide three principles for coordinating computation and execution.
Evidence-grounded commitment. Maintain an evidence-supported operation as a revisable com-
mitment. While its supporting conditions hold and execution constraints are satisfied, let the com-
mitment constrain conflicting proposals and redundant solving. Reconsider it when new observa-
tions indicate that relevant conditions have changed.
Progress-checked transition. Advance only when available evidence satisfies the completion cri-
terion for the current capability or the overall task, not merely because an operation has been dis-
patched. When an outcome remains unresolved, seek evidence that helps determine whether to
advance, reassess, or continue observing.

SOLVEBIND: HIERARCHICAL SOLVING WITH RUNTIME SUPERVISION
SolveBind uses a hierarchical solving tree to organize task-solving capabilities and a runtime super-
visor to coordinate execution, progress verification, and recovery. Tool-derived evidence supports
concrete, revisable action commitments, while execution feedback updates a shared protocol state
that guides subsequent capability selection and dispatch.
4.1
FRAMEWORK OVERVIEW
As shown in Figure 2, the solving tree specifies required subgoals and alternative capabilities. The
model selects capabilities and proposes operations, while the supervisor determines which oper-
ations to dispatch based on retained evidence, pending commitments, and execution constraints.
Execution feedback then informs subsequent decisions.

RUNTIME SUPERVISION
Evidence binding and commitment-based dispatch.
When a tool output passes the binding
checks, the runtime establishes a commitment ck = (n, ac, Ec), linking a concrete operation ac
to the capability node n which it serves and its supporting evidence Ec ⊆Ek. In the full-control
configuration, an admissible pending commitment takes dispatch precedence:

Admissibility requires that the supporting evidence remains valid in the current context, the relevant
stage and budget checks pass, and no terminal condition has been triggered. If a proposal conflicts
with an admissible commitment, the supervisor replaces it with the committed operation ac.
Once dispatched, a commitment is no longer pending for repeated execution; its supporting evidence
and attempt record are retained for outcome assessment. Dispatch alone does not establish progress
or task completion.
For example, the supervisor can replace a repeated localization proposal with an admissible pend-
ing operation already supported by grounding evidence. The commitment remains subject to re-
assessment if the target or page conditions change. Appendix B.2 details the binding checks and
commitment lifecycle.
Progress verification and bounded recovery.
The supervisor assesses outcomes as progress,
failure, or unresolved using the active stage, execution feedback, and subsequent observations.
Progress evidence updates capability status, with advancement permitted once the corresponding
completion criterion is satisfied. Failure feedback guides revisions to hypotheses and commitments
or the selection of an alternative branch, while unresolved outcomes prompt further observation and
feedback acquisition.
Recovery combines runtime constraints with model guidance, using feedback and attempt history to
revise affected hypotheses while preserving applicable evidence. Recovery budgets are consumed
in configured units, such as attempts or refreshes. Once a budget is exhausted, the runtime stops the
recovery operations within its scope and terminates the run when no permitted continuation remains.
Appendix B.4 specifies the feedback categories, state updates, and budget rules.

EXPERIMENTS
We evaluate SolveBind for reliable and efficient task execution in protected GUI environments from
two complementary perspectives: interaction acceptance on the verification side and workflow effi-

5.2
RESULTS ON VERIFICATION-SIDE INTERACTION ACCEPTANCE
Coordinating solving and execution improves interaction acceptance. On the verification side,
success requires executing a solution in a form accepted by the environment. In Table 1, SolveBind
achieves the highest success rate on eight of nine backbones, exceeding the strongest baseline by
13.3–34.5 percentage points across those eight configurations. Appendix D.2 provides per-backbone
success gaps and unscaled token results.
Higher verification success with lower latency. Relative to MobileAgent, GPT-5.5 and Gemini
3.1 Pro Preview improve SR while reducing mean E2E. GPT-5.5 reduces E2E from 167.3 to 112.0
seconds, a 33.05% reduction. Gemini 3.1 Pro Preview reduces E2E from 577.7 to 88.6 seconds, an
84.66% reduction, while increasing success by 34.5 percentage points based on the displayed SR
values. Token usage increases for GPT-5.5 but decreases for Gemini 3.1 Pro Preview and Qwen3.7-
Plus. Lower latency is therefore not uniformly accompanied by lower token usage.
GUI specialization alone does not remove the verification bottleneck. UI-TARS-1.5-7B with
its native harness completes 325 of 900 tasks in the full evaluation, achieving 36.11% success and
leaving 575 tasks unsuccessful. Thus, a policy specialized for GUI operation still encounters a
substantial completion bottleneck under difficult, high-distraction verification conditions. Solving,
interaction evidence, and feedback coordination remain central to translating GUI capabilities into
successful protected execution. Appendix D.3 and Appendix D.6 report the native-policy evaluation
separately from the backbone–harness comparisons.

5.3
RESULTS ON TASK-SIDE EXECUTION EFFICIENCY
The shared runtime reduces task-side execution costs. Relative to MobileAgent, SolveBind re-

E2E is lower, although total-token usage is higher. The native UI-TARS-1.5-7B system averages
95.24 seconds and 14,018.81 tokens, but completes 23 of 116 tasks. These comparisons show why
short outputs and short runs must be considered together with task completion. SolveBind improves
completion rates and, in multiple system comparisons, reduces the time required for task execution.
5.4
ABLATING RUNTIME CONTROLS
The ablation uses GPT-5.5 on 25 instances from each of nine HLL families, yielding 225 episodes
per configuration. We compare full control against variants that bypass mediation, remove fail-safe
defaults, relax binding with or without automatic submission, or remove recovery caps.
Binding contributes under fixed automatic submission. Relaxing binding alone reduces success
from 185/225 (82.22%) to 161/225 (71.56%), while mean E2E rises from 112.13 to 128.71 seconds
and tokens from 41.82k to 49.32k. Because automatic submission is unchanged, this comparison
isolates the contribution of binding in this configuration.
Weaker runtime control reduces success while increasing cost. Bypassing mediation lowers suc-
cess by 9.33 percentage points, while jointly relaxing binding and submission lowers it by 13.78
points. Removing fail-safe defaults reduces success by 7.11 points and produces the largest cost
increase, adding 46.00 seconds and 18,818 tokens per run. These results support coordinating exe-
cution with available evidence rather than allowing unconstrained dispatch.
Recovery caps provide a success–cost trade-off. Removing only the recovery caps increases suc-
cess from 185/225 to 188/225, but raises E2E and token usage to 3.7× and 2.4× their full-control
values. Thus, additional recovery yields only a small completion gain at substantially higher cost,
supporting bounded recovery. Appendix D.7 provides full configurations and analyses.

CONCLUSION
We studied GUI task execution in protected environments, where goal achievement and environmen-
tal acceptance are distinct. SolveBind combines a hierarchical solving tree with a runtime supervisor
that treats tool outputs as revisable evidence, binds them to action commitments, mediates dispatch,
and budgets recovery by category. Across evaluated backbones, it improves success in most verifi-
cation settings and all AndroidWorld comparisons while reducing latency in several cases. A paired
GPT-5.5 diagnostic further suggests gains when agents find correct solutions but fail to execute them
acceptably, although improvements are not uniform. Our verification evaluation uses recorded inter-
action evidence rather than production detectors, while AndroidWorld measures general workflow
execution. Extending these results to deployed protections and identifying the backbone properties
underlying runtime supervision remain future work.

B.3
COMMITMENT LIFECYCLE AND DECISION RESOLUTION
The commitment lifecycle has four logically distinct situations:
1. Unbound. Evidence is insufficient to establish the next committed operation. The model
can propose relevant evidence acquisition or another permitted operation.
2. Pending. Actionable evidence establishes ck. In the full-control configuration, a still-
admissible commitment takes precedence over a conflicting proposal.
3. Dispatched, outcome unresolved. The operation has been issued and is no longer pending
for repetition. Its effect still requires assessment through feedback or observation.
4. Resolved or reconsidered. Progress supports advancement; failure or changed support
motivates revising the hypothesis, reacquiring evidence, or recovering within budget.
These are semantic distinctions rather than four required implementation flags. Consuming the
pending status and recording an attempt must preserve the information needed for outcome verifica-
tion.
For the controller in Eq. 24, replacing a proposal is justified by a currently admissible commitment,
not merely by an old pending record. Admissibility assessment must incorporate the latest accessi-
ble feedback. A commitment cannot override terminal conditions or violated enforced constraints.
When its support no longer holds, it loses its basis for execution precedence, and the runtime recon-
siders the continuation.
Rejecting a proposal, deferring an interaction, and initiating recovery need not each produce a new
GUI action. A rejected proposal can be withheld; a deferred GUI interaction can be replaced by
a grounding or verification request; recovery can revise the active capability before the next inter-
action is selected. A hold decision dispatches no request, so active evidence acquisition must be
selected as an operation in A. All dispatched replacements remain subject to applicable checks.
These dependencies do not require every implementation to use the same ordered list of conditional
branches.
The same proposal can lead to different decisions in different states. An admissible pending commit-
ment can replace repeated localization, whereas changed page conditions can make that localization
necessary again. Proposal identity alone is therefore insufficient to determine the runtime response.

introducing an additional search algorithm. Logical binding does not imply that every continuation
saves a model call; call scheduling and binding are distinct concerns.

C
RATIONAL METAREASONING AND DESIGN RATIONALE
This appendix expands the design principles in Section 3.2. Rational metareasoning provides a
perspective on allocating processing effort; the concrete execution mechanisms are specified in Sec-
tion 4 and Appendix B.
C.1
DECISION IMPROVEMENT AND PROCESSING COST
Rational metareasoning distinguishes the choice of external actions from the choice of computations
that inform those actions. A computation is valuable insofar as its expected contribution to subse-
quent decision quality justifies its cost (Russell & Wefald, 1991). This perspective addresses both
which computations to perform and when to stop deliberating and act. For example, Hay et al. (2012)
formulate computation selection as a metalevel decision problem in which computational outcomes
inform the eventual choice of an external action. Performing more computation is therefore not an
objective in itself.
We borrow this benefit–cost perspective for model reasoning, tool-based solving, evidence acquisi-
tion, and outcome verification. These activities contribute to end-to-end latency, and their usefulness
depends on how they support subsequent execution. They are not all purely internal computations:
obtaining an observation may require an environment interaction, and a tool may both return infor-
mation and execute GUI actions. We therefore retain the distinction between tool invocations and
realized interactions, rather than identify every tool call with a metalevel computational action. The
corresponding runtime interfaces and execution rules are described in Appendix B.
C.2
IMPLICATIONS FOR PROTECTED EXECUTION
Reliable and efficient execution depends not only on answer correctness, but also on when to acquire
information, act on an available solution, and revise an attempt after feedback. Additional reasoning
and checks can improve execution decisions, but also incur latency. Acting prematurely can lead
to rejection or rework, whereas repeatedly revisiting an already-supported solution can add cost
without improving the next decision. The design objective is thus to coordinate these activities,
rather than maximize reasoning effort or minimize interaction count in isolation.
Environmental acceptance further makes reassessment consequential. A correct answer can be fol-
lowed by a rejected interaction, and dispatch can leave the intended effect unresolved. Conversely,
when recovery is permitted, feedback from a failed attempt can support a useful continuation. These
conditions motivate the following design choices.
Reusing an applicable result.
An evidence-grounded commitment preserves a specific supported
continuation across successive proposals. It allows the runtime to act on an available result while
the supporting conditions and applicable execution constraints remain satisfied, rather than reopen
selection without a decision-relevant reason. Relevant changes in the target, page context, or feed-
back can instead justify renewed grounding or solving. This reuse rule neither certifies semantic
correctness nor implies that further computation has no value merely because a candidate operation
exists.
21


Preprint
Checking consequential uncertainty.
An incorrect progress judgment can cause subsequent op-
erations to rely on an unfinished prerequisite. Verification incurs a cost, but can prevent downstream
rework by informing whether to advance, reassess, or continue observing. This motivates checks
tied to capability and task criteria, not a separate verification call after every internal computation.
The objective is to obtain evidence relevant to continuation while satisfying the applicable verifi-
cation requirements, rather than add checks indiscriminately or omit required verification to reduce
measured time.
Using feedback within a budget.
Recovery revises assumptions undermined by feedback while
retaining evidence that remains applicable. A rejected solution need not invalidate every geomet-
ric observation; a changed page may require renewed grounding without changing the user goal.
Feedback and execution history should therefore guide subsequent attempts toward unresolved is-
sues rather than mechanical repetition. Budgets limit designated recovery operations, as specified
in Appendix B.4. These limits constrain repeated attempts but do not, by themselves, establish a
bound on all model calls or external waiting time.
C.3
SCOPE OF THE THEORETICAL CONNECTION
The three principles are design choices inspired by rational metareasoning, not theorems derived
from an optimal metalevel policy. The framework implements them through accessible evidence,
execution history, and budget constraints, without requiring an online estimator of expected compu-
tation value or a complete probabilistic model of computational outcomes. Neither the hierarchical
solving tree nor the runtime supervisor is claimed to maximize a computation-value objective. Their
effects on success and end-to-end latency are evaluated empirically under the timing and acceptance
definitions in Appendix A.

E2E is the elapsed wall-clock interval from the first model call to
success or failure termination, as formalized in Appendix A.4; it includes model inference, tool calls,
runtime control, GUI execution, environmental responses, and recovery rather than summing poten-
tially overlapping component durations. Tok accumulates input and completion tokens from every
model call in an episode, including planning, reflection, recovery, and failed attempts, while ex-
cluding deterministic perception computation. Separately reported reasoning tokens, model-backed
tools, and missing usage records must be identified rather than silently treated as ordinary tokens or
zeros. The main verification, AndroidWorld, and runtime-ablation tables express Tok in thousands;
dedicated appendix token tables retain unscaled counts. Relative differences are calculated from
unscaled supplied values rather than rounded display values.

D.7.3
CONNECTION TO RUNTIME DESIGN PRINCIPLES
Separate controls answer different questions.
The no-binding condition isolates dispatch prece-
dence while retaining automatic submission. The recovery-cap condition isolates the configured
recovery limit while retaining binding and submission. The former supports enforcing available
evidence in the tested configuration; the latter characterizes the success–cost trade-off of bounded
recovery. Neither establishes that the runtime computes the optimal value of further information.
Relation to metareasoning.
Full control outperforms the mediation, defaults, binding, and
relaxed-supervision variants in success and aggregate cost. Unbounded recovery instead slightly
improves success at higher cost. This pattern motivates evaluating additional processing by its con-
tribution to task completion relative to its expense. It supports the practical control design, without
demonstrating an optimal metalevel policy or a rule that reliably detects when further information
has no value.
Execution traces would localize where cost is incurred.
The aggregate measurements in Ta-
ble 3 establish net differences between configurations but do not identify which steps account for
the additional latency and tokens of the ablated configurations. Per-episode counts of model calls,
tool calls, dispatched GUI actions, commitment dispatches, proposal replacements, and recovery
attempts would connect these configuration-level results to the mechanisms illustrated in Appen-
dices D.8 and D.9. We do not infer such counts from the aggregate means, since several distinct step
profiles are consistent with the same episode average.

outcome. Repeated solving is assessed against whether relevant new evidence was obtained. Pre-
mature progression is assessed against the state required by the next operation. Reused grounding
is checked against target and page changes. Labels such as redundant solving, stale evidence reuse,
retries without hypothesis revision, or output-format failure are assigned only when supported by the
trace. The selected cases explain mechanisms rather than estimate population failure frequencies.

Two case studies examine the relationship between tool evidence, pending commitments, model
proposals, dispatch, and feedback updates. Each analysis identifies the operation supported by the
available evidence, the supervisor’s decision, and the execution outcome observed afterward. Both
are recorded runs with step-level decision records; they illustrate the protocol’s operation on indi-
vidual episodes and are not controlled comparisons against a matched baseline trajectory.
D.9.1
CASE STUDY S1: ICON-SEQUENCE VERIFICATION
The task requires clicking icons in a displayed order. The run proceeds through the three selections
in sequence, and the page reports readiness to verify. At step 6 the model proposes the operation
submit captcha. The recorded decision shows the supervisor dispatching this request as the
concrete tool operation SubmitCaptcha, realized as a tap at coordinates (543, 1557); the outcome
is recorded as success/captcha verified, with the observation, action overlay, and result-
ing screen retained as screen 005.png, screen 005 submitcaptcha action.png, and

This record shows the components the protocol makes explicit at dispatch time: the proposal as
generated, the supervisor’s decision, the concrete operation executed together with the tool that re-
alized it, the environment’s verification outcome, and the retained observation assets that allow the
transition to be reconstructed. The decision here is a dispatch rather than a replacement, so this
case does not demonstrate a corrected proposal. What it establishes is that a proposal, its realized
operation, and the resulting verification outcome are recorded as separate fields, which is the precon-

name to the executed tool operation is an interface mapping and is not by itself evidence of semantic
correction.

CASE STUDY S4: CATEGORY-GUIDED IMAGE SELECTION
The task requires selecting images in a grid that match the specified category. At step 7, the model

D.10
INFORMATION ISOLATION AUDIT
Operational boundary.
Tables 7 and 8 define the intended separation between agent-visible ob-
servations and evaluator-only information. CAPTCHA answers and hidden verification state remain
within the environment, while agents receive only permitted interface observations, enabled tool
results, and public feedback. AndroidWorld likewise retains private task parameters and the success
oracle within the official evaluator. An agent’s termination request is recorded independently of the
evaluator’s success decision.
Audit evidence and limitations.
The current evidence consists of observation and dependency-
isolation tests for UI-TARS configurations and a field-level audit of model observations, post-action
feedback, and tool results in the protected-interaction environment. The inspected records did not
expose answers or evaluator-only signals to the model. This evidence supports the stated interface
boundary but does not constitute a formal information-flow proof or exhaustive verification of every
execution path.
