## 摘要
移动使用多模态智能体通常以从干净初始状态开始的任务成功率进行评估，这无法单独衡量其从中间错误中恢复的能力。由于移动环境动态变化，通用移动使用智能体必须即使在意外状态和未见环境中也能稳健完成任务。这要求知道智能体何时、何处犯错，以及它能否从错误及后续状态中恢复。为评估该能力，我们提出 AndroidFlux，一个构建于 AndroidWorld 之上的故障恢复基准。AndroidFlux 将记录轨迹恢复到首个可恢复错误之前、之时和之后的受控检查点，使不同智能体从相同的设备状态和历史继续执行。在这些检查点上，一个互补的奖励建模基准利用下游 rollout 结果评估恢复动作偏好。我们进一步发布一个离线强化学习（RL）数据集，可同时提升错误恢复和整体任务成功率。我们的评估表明，恢复性能与干净启动成功率仅部分相关，并且显式推理仅对使用 GUI 领域特定 RL 训练的模型有帮助。

## Abstract
Mobile-use multimodal agents are typically evaluated by task success from a clean initial state, which does not isolate their ability to recover from intermediate errors. Because mobile environments change dynamically, a general mobile-use agent must complete tasks robustly even from unexpected states and in unseen environments. This requires knowing when and where an agent makes errors, and whether it can recover from errors and subsequent states. To evaluate this capability, we introduce AndroidFlux, a failure-recovery benchmark built on AndroidWorld. AndroidFlux restores recorded trajectories to controlled checkpoints before, at, and after the first recoverable error, so that different agents continue from the same device state and history. On these checkpoints, a complementary reward-modeling benchmark evaluates recovery-action preferences using downstream rollout outcomes. We further release an offline reinforcement learning (RL) dataset that improves both error recovery and overall task success. Our evaluations show that recovery performance only partially correlates with clean-start success, and that explicit reasoning helps only models trained with GUI-domain specific RL.

# AndroidFlux 论文结构化总结

## 1. 核心问题与研究动机

- **评估范式缺口**：现有移动/GUI 智能体基准（AndroidWorld、AndroidLab、MobileWorld、OSWorld 等）几乎都从干净初始状态（home screen）出发，只返回一个终端成功/失败信号，无法隔离"智能体从中间错误中恢复"这一能力。
- **真实部署需求**：移动环境动态变化，通用智能体必须在意外状态、未见环境中稳健完成任务；单次 pass/fail 掩盖了中间失败以及哪些动作有帮助/有害。
- **Agentic 系统的现实场景**：为降低推理成本，系统常把简单任务交给小模型，小模型卡住后再移交给强模型；强模型必须在"不是自己造成的错误、不是自己产生的上下文与设备状态"下恢复。
- **测量成本高**：干净起点 rollout 中失败状态只能偶然出现，每个失败状态需整条 episode 才能到达，且分数反映整条轨迹而非具体恢复步骤。
- **现有工作不足**：并发的 GUI-RobustEval 只做桌面端错误后恢复；UI-Genie 的负样本是对正确行为的扰动，而非策略在真实破坏状态下实际采取的动作，且错误来源未跨策略规模化。
- **论文主张**：首次针对移动智能体，构建覆盖首次错误**前、中、后**三个阶段的受控检查点基准，并配套恢复动作奖励建模基准与离线 RL 数据集。

## 2. 方法论

### 2.1 问题形式化
- 将移动交互建模为有限时域 POMDP：\(M=(S,O,A,P,\Omega,r,H,\mu_0)\)，智能体上下文 \(h^\pi_t=\Phi^\pi(c,o_{0:t},y_{0:t-1})\)，其中 \(\Phi^\pi\) 是目标智能体自身的上下文格式化函数。
- 截图不包含应用数据库、Activity 栈、文件系统状态，因此恢复本质上是**历史依赖**的。

### 2.2 重放与恢复（Replay & Resume）
- 对源轨迹 \(\tau_{src}\) 和检查点 \(k\)，在同一任务种子下重放记录的动作前缀；若无法复现则回退到模拟器快照：\(\hat{s}_k=\text{Replay}(\tau_{src},k)\)。
- 首次错误定义为最早未推进任务的步骤：\(t=\min\{i:e_i=1\}\)，仅考虑**可恢复的首次错误**；\(i>t\) 的任何动作都视为"从已破坏状态出发的恢复动作"。
- 目标策略从 \(\hat{s}_k\) 和重构上下文 \(h^\pi_k\) 继续，生成恢复轨迹 \(\tau_{rec}\)，由程序化验证器打分：\(SR(\pi,k)=\frac{1}{N}\sum_i \mathbb{1}[r(s^{(i)}_{T_i})=1]\)。
- \(\pi=\pi_{src}\) 测自恢复，\(\pi\neq\pi_{src}\) 测跨智能体接管；改变 \(k\) 相对 \(t\) 的位置可分离"已犯错误的代价"与"继承外来历史的代价"。

### 2.3 检查点设计
- **t−n**（n∈{1,3,5}）：正确前缀，测继承进度的影响；当 \(t_{err}<n\) 时映射为干净起点，并单独报告可行子集。
- **t**：错误已提交的检查点，核心恢复评测点。
- **t+1⁺ / t+1⁻**：在 t 状态注入一条最终成功/失败恢复 rollout 的**首个动作**，之后由被测策略自主执行，用于测量单个恢复动作的下游影响。

### 2.4 上下文中性化重渲染（关键技术细节）
- 将源模型响应反转为 **schema-neutral step record**（含 step idx、goal、前后截图、规范化动作、原始 thought、合成 summary、错误标注等），再按目标策略原生格式渲染，避免把某一模型的 prompt 格式直接复制给另一模型。
- **summary 合成两级规则**：优先复用源模型摘要（须为平实散文、过去时开头、经清洗），否则按动作类型模板合成；任何提及 error/mistake/replay/recovery 的候选一律丢弃——不能让历史"自曝失败"，因为"发现状态已坏"本身就是被测能力。
- 不存储 accessibility tree，恢复时提供实时树；坐标归一化到统一动作语法，适配器按目标模型重新发射其期望单位。
- 每个 (task, target) 运行 4 次，固定 Docker 镜像、快照、任务列表与种子。

### 2.5 首次错误标注与分类
- **人工集（HV）**：6 个源模型 × 112 任务 = 672 条轨迹逐步人工审查，保留非边界步骤出错的轨迹，每任务选 1 条并平衡源模型，得 80 例（65 例动作重放 + 15 例快照恢复）。
- **LLM 验证集（LV）**：Gemini Flash 3.0 实现"检测器 + 验证器"两阶段流水线，检测器读 10 步滑窗提出候选簇，验证器对照结果 UI 状态复核并取最早存活步；**精度优先**（误标会移动所有下游实验的起点），步骤级精度达 90.8%。
- **三类错误**（固定优先级 停滞→方向→执行）：
  - **Stagnation**：在基本不变的屏幕上重复已失败动作或来回振荡；
  - **Direction**：动作执行成功但偏离目标（错目标/屏幕/日期/应用、回退已完成进度、忽视可见矛盾）；
  - **Execution**：目标元素和动作类型正确，但局部效果错误或缺失（提交了错值、点到相邻控件）。

### 2.6 恢复动作奖励建模基准
- 固定恢复状态 \(x=(h_t,o_t)\)，奖励模型给候选动作打分 \(r_\phi(x,a)\)，配对正确当 \(r_\phi(x,a^+)>r_\phi(x,a^-)\)。
- **偏好由后果接地而非规则或 LLM 裁判**：每个候选动作被执行，12 个 agent 组成的固定面板从诱导出的 t+1 状态独立 rollout，候选得分 = 面板中达成目标的数量；取组内最高/最低分为正/负动作，仅保留 margin \(\Delta_g\ge 2\) 的配对，共 100 对（72 个错误路径 + 28 个干净路径，26 种任务类型）。
- 5 个候选生成器（Qwen3-VL-2B/8B、GUI-Owl-7B、GUI-Owl-1.5-8B、MAI-UI-8B），同分时优先使用此前担任该角色较少的生成器以提升来源覆盖。

### 2.7 离线 RL 数据集与训练
- **8,499 个策略诱导上下文**，四个切片：t−n（2,097）、t−1（2,080）、t（2,080）、成功上下文（2,242）；每个标注 `is_next_terminate`（目标是否已满足）。
- 训练：Qwen3-VL-4B-Instruct + LoRA（rank 64, α=32），离线 **GRPO + Group Preference Reward Shaping (GPRS)**，奖励来自冻结的 UI-Genie BT-128K；每组 K=8 个采样，优势 \(A_i=B_i-\frac{1}{K}\sum_m B_m\)，不除以组内标准差。
- **Terminate guard**：对 terminate 动作，除非 `is_next_terminate=True`（或 UI-Genie 参照动作为终止），否则置 \(B_i=0\)，防止奖励模型错误奖励提前终止。
