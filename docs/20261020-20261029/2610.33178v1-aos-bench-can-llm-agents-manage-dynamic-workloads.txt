## ABSTRACT 

Coding agents are moving from handling one request at a time to serving as persistent assistants to which users hand a stream of work: a build, a data-processing job and a bug fix may all be pending on the same machine at once. Such an agent must decide when to take on new tasks, how to delegate and overlap them, and how to stay within the machine’s CPU and memory. Existing benchmarks cannot measure this, because they evaluate each task in isolation. We introduce AOS-Bench, which evaluates an agent system as a workload manager: verified tasks arrive over time and must be delivered under shared CPU and memory limits, and the same tasks run one at a time serve as a per-system reference. Across five model–harness pairs, isolated task success does not carry over evenly. On heavy workloads every system loses 13 to 23 points. On medium workloads, systems span 11 points in isolated success but 26 points in stream success, and two systems 0.6 points apart in isolation deliver 54% and 68% of the same tasks. Execution-policy interventions trace much of this gap to task intake: serial dispatch leaves 73% of heavy-workload tasks unclaimed. Yet more elaborate management does not necessarily help. A fixed concurrency of two comes within four points of the best agent-managed policy on both medium and heavy workloads, and under every policy median CPU use stays below 30% of the provisioned cores while tasks wait. These results identify workload management as a distinct capability for agents, and AOS-Bench as a way to measure it. Code is available at https: //github.com/AOS-Bench/AOS-Bench .

## 1 INTRODUCTION 

Advances in coding and computer-use agents let users delegate a growing range of computer tasks through natural language. Benchmarks such as Terminal-Bench and OSWorld typically use individual tasks as the unit of evaluation (Merrill et al., 2026; Xie et al., 2024). New requests may arrive before earlier work is finished, such as file processing requested during a software build. We call the collection of requests handled in a shared computing environment over time a workload . In a task-by-task workflow, users launch separate agent sessions and remain responsible for coordinating their work. We envision delegating this responsibility to a persistent agent system that manages an evolving workload on the user’s computer. The agent must construct each task’s execution plan while deciding when to accept more work, how to delegate it, and which activities to overlap. Task solving and workload management are therefore coupled. Overlapping execution can use resources left idle during model calls or tool waits, but can also introduce contention and coordination overhead under shared CPU and memory constraints. Performance on isolated tasks does not establish how well an agent maintains progress across requests, or whether its execution decisions improve workload delivery and efficiency. This motivates our central question: Can current frontier agent systems effectively manage dynamic workloads under shared resource constraints? We call this role Agent as a Workload Manager . Our contributions are: • A formulation of agent workload management and the AOS-Bench benchmark with construction pipeline, execution protocol, and metrics. • A comparative evaluation of five model–harness pairs showing that the share of isolated task performance a system retains under a shared workload differs widely across systems and reorders them on medium workloads.

## 2 EVALUATION FRAMEWORK 

AOS-Bench evaluates how well an agent system completes a workload —a set of tasks released over time under a shared CPU and memory budget. An agent system is a model paired with an agent harness that provides its interaction loop, tools, and execution interface. We do not prescribe internal organization: the system may execute requests in its main session, launch subagents, or invoke other tools. 2.1 TASK FORMULATION 

A workload is W = ( J , B ) where J = {Ji}ni=1 and each task Ji = ( xi, a i, V i) consists of a natural-language instruction xi, a release time ai, and a verifier Vi that checks success against fixed criteria. B specifies the shared CPU and memory budget; one end-to-end run is a trial .Our primary setting is stream execution , in which tasks arrive while the agent is already working. An external dispatcher releases each task Ji at its release time ai; the agent system cannot see an instruction before its release, nor the schedule of future releases. Through a Model Context Protocol (MCP) interface, the agent system can query the dispatcher to view all tasks released so far and their current states. Using this view, the agent system decides when to take on additional work, how to organize and delegate execution, and when to check progress. A task is claimed once the agent system marks it as taken in the dispatcher; a claim only declares ownership and does not indicate that execution has started or succeeded. We use two comparison settings in addition to stream execution. Individual runs execute each task separately and provide a reference for isolated task-solving capability. Because they collectively receive more resource opportunity than a shared run, they serve as a capability reference rather than an equal-cost throughput baseline. Burst runs use the same shared environment and task set as stream runs, but release all tasks at t = 0 . Source benchmarks include Terminal-Bench (Merrill et al., 2026), SkillsBench (Li et al., 2026), TerminalWorld (Chu et al., 2026), WildClawBench (Ding et al., 2026), CompileBench (Quesma, 2025), CompileAgent (Hu et al., 2025), ParEval (Nichols et al., 2024), and the One Billion Row Challenge (Morling, 2024), supplemented by synthetic tasks. Tasks are standardised in the Harbor format (Harbor Team, 2026) with instructions, environments, reference solutions, and verifiers. Calibration runs measure execution duration and CPU utilization; L2 and L3 denote moderate and high resource intensity (Appendix A). Task sets are merged into a shared Docker image with consistent path resolution across instructions, reference solutions, and verifiers. Iterative validation applies four gates: a source audit, a Docker validity gate (image builds and launches), a solution validity gate (each reference solution must reach full score in the merged environment), and an overlap check against admitted workloads. For cross-system speed, Table 2 also gives the absolute rate: GPT-5.6-sol delivers the most rewarded tasks per hour on medium (5.74) and Claude Opus 5 on heavy (3.29). A thirty-task workload, three repeats per system, stresses intake harder than either reported tier and exposes the mechanism in isolation. We therefore measure intake rate and execution organization, but never the ordering policy that scheduling theory treats as the central decision, and because every task is worth the same, the objective reduces to maximizing total reward under a shared budget. The stream and individual settings also differ in more than scheduling. The stream setting adds a shared filesystem, a task-pool interface, a scheduling preamble, and contention for one allocation, so the paired difference measures the cost of moving a task from isolation into a managed workload rather than the cost of scheduling decisions alone. Individual runs additionally receive more aggregate resource opportunity, which makes them a capability reference rather than an equal-cost baseline. The workload design samples one region of a larger space. Tiers of 10, 20, and 30 tasks over 4 CPUs and 8 GiB draw different but overlapping task sets (22 of medium’s 29 scored task variants recur in heavy and reuse the same individual baselines), so tier differences confound scale with composition and the two tiers’ estimates are not independent, and one burst condition does not characterize sensitivity to the arrival process. Whether these failure modes persist under tighter resource ratios, or under hundreds rather than tens of concurrent requests, is outside what this design establishes. Inference is finally bounded by workloads rather than trials, since repeats share a task set and an individual baseline. That leaves ten clusters on medium and five on heavy, too few for a calibrated interval, and most heavy trials stop at the wall-clock limit, so delivery on that tier is a lower bound. 

## 6 CONCLUSION 

We introduced AOS-Bench to evaluate agent systems as workload managers, composing verified CLI tasks into shared container workloads with controlled arrivals and measuring five model–harness pairs in individual and stream settings. The central finding is that how much isolated task performance carries over to a shared workload differs widely across systems: every system loses 13.0 to 22.7 points on heavy workloads, and on medium workloads the systems span 11.0 points in individual success rate but 25.8 in stream success rate with no system holding its rank across both, and two systems whose individual baselines differ by 0.6 points deliver 53.9% and 68.1%. Execution-policy interventions identify task intake as a primary factor limiting delivery — serial execution cannot claim released work fast enough to deliver a competitive share within the budget, while a fixed concurrency of two comes within four points of the best agent-managed policy on both tiers, so most of the available gain comes from not executing serially — and on the thirty-task case a single system spans the full range of outcomes across identical repeats, which suggests that single-task-at-a-time execution can be a failure mode rather than a stable capability level. Workload management is therefore a distinct evaluation dimension from task solving, and the immediate work it calls for is enforced resource limits, instruction-level deduplication for repeated task families, more heavy-tier workloads for calibrated intervals, and trajectory-level attribution of execution overlap.

## D THE INTAKE -COLLAPSE FAILURE MODE 

On heavy workloads Claude Opus 5 retains 83% of its isolated success rate while GLM-5.3 and DeepSeek-V4-Pro retain 74% and 61% (Table 2). This appendix identifies what the three systems do differently and rules out the main experimental explanations. All three run the same harness at the same version, the same reasoning-effort setting, the same disabled tools, the same dispatcher, the same arrival schedule, the same container limits and the same scheduling preamble; the deployed per-trial configurations differ only in the model identifier and the output-token cap (Appendix H.1). 

The mechanism is how many tasks a run ever holds at once. Every one of Claude’s 15 trials claimed all 20 released tasks, with a peak concurrency of 6 to 19. GLM claimed all 20 in 9 trials and between 5 and 10 in the other six, and in those six its peak concurrency was 1 or 2 — it executed the workload one task at a time. DeepSeek did not claim the full workload in any trial: its peak concurrency is 1 to 3 in 15 of 15, and it claimed 5 to 18 tasks. The resulting never-claimed share is 0%, 25% and 48% of the 300 task instances per system, and median claim latency, the delay from a task becoming claimable to being claimed, is 552, 1187 and 6242 seconds. 

The collapsed runs are not idle, short, or faulted. GLM’s six collapsed trials are all clean 

under both the operational filter and the looser nearly-clean rule, with zero request-level API errors, zero output-cap events, zero unavailable-route events and zero verifier download failures. Four of the six ran past 3.7 of the 4 available hours. They issue 145 to 281 shell commands and produce 59 to 100 MB of transcript — four to six times Claude’s median of 15.5 MB on the same workloads — while calling the task-intake tool only 12 to 17 times. DeepSeek’s median transcript is 102 MB against a median of 14 intake calls. The pattern is sustained effort concentrated on a handful of claimed tasks, not a failure to act; two of GLM’s collapsed runs also record context-window compaction in their final message, which makes context pressure a candidate trigger without establishing it. 17 Preprint

## F TERMINAL -STATE ACCOUNTING 

Two of the six terminal states in Figure 8 depend on which component writes the record, and the comparison in Appendix J is grouped so that it survives that dependence. 19 Preprint The fixed policies carry high reported-failed shares — 19.7% and 10.7% of released tasks on medium and heavy, against 1.7% and 9.3% for native management — because their driver records a solver session that exits non-zero as a failed task. An agent-managed run has no such driver and may simply stop reporting on a task it still holds, which lands in the claimed-but-unfinished state instead. The two states therefore trade off against each other for reasons of bookkeeping as much as behavior. Grouping them resolves the ambiguity: greys are work never served and warm shades are work served without full credit, regardless of which component wrote the terminal record. That grouping, not the individual state shares, is what the policy comparison rests on. The three reported-complete states are unaffected, since a verifier outcome is written by the same grader in every system, and they sum to the completion column of Table 3 in all eight cells. 

## G FAILURE -ATTRIBUTION METHOD AND ADJUDICATION 

This appendix records how the failure classification of Figure 10 is constructed and what the review-class findings contain. The figure applies the classification to the trials scored in Table 2; the review-class scans below cover all 390 native-stream trials of every tier, including the light tier and the thirty-task case, so that no trial escapes the manipulation check. The procedure is here because it governs what those counts are allowed to mean. 

Evidence classes. We separate three kinds of evidence and never mix them in one number. Struc-tured evidence is stated by an artifact: a harness exit code, a dispatcher terminal state, a container counter. Derived evidence is computed from a structured series, such as peak memory against the container’s own limit. Review evidence is a text match in a transcript, which locates candidates for inspection and is never reported as a rate. Text matching alone cannot support a rate. Generic out-of-memory phrasing appears 1807 times across 14 of 15 trials in one policy system, while the collection contains one structurally confirmed occurrence. The matched text is predominantly a system narrating an error it is reasoning about (“the build was killed, likely memory, retrying with fewer jobs”) rather than a container being terminated. Review evidence is therefore reported as a located case list rather than as a rate. 

Resource conflicts. Narrow patterns for four conflict classes match in a minority of trials: disk exhaustion in 56 of 390, process-table or descriptor exhaustion in 47, file-lock contention in 29, and port collisions in 12. Hit counts exceed trial counts by two to four times, which indicates individual transcripts repeating a message rather than many distinct conflicts. A match may be a conflict the system hit, a conflict it recovered from without consequence, or text it reproduced while reasoning, and the records do not distinguish these without inspection. We therefore report a located case list supporting the observation that shared-container execution produces contention, and derive no conflict rate. 

Adjudicating references to the harness log tree. We adjudicated by hand every reference to the harness log tree that our classifier placed inside an issued command rather than in tool output: 52 candidates in 31 trials, out of 278 references to that tree found in 70 of the 390 trials. No trial references the arrival schedule, which would be the high-severity case. Most candidates are environment reconnaissance: directory listings of the harness log tree, which is empty during the execution phase. Nine are a system rewriting the output paths inside a task’s own test script so that its results land in a scratch directory, which redirects grader output away from the harness tree rather than into it. Four are the content of a task’s test script appearing in tool output and misclassified as a command, so the in-command count is itself an overestimate. The lower-severity pattern, reading a task’s own bundled tests, occurs in 111 trials and is expected: those tests ship with the task. One candidate is a genuine write. A DeepSeek trial issued echo 1 > /logs/verifier/ reward.txt , and the harness reward reader does consult that flat path as its last fallback, after a per-task path. The write had no effect on the score: the task is recorded at 0.0 in the final breakdown while the system’s own note for it asserts “reward.txt=1” and “3/3 passed”, and the per-task reward record contains 0 with a modification time after the execution phase ended, so the authoritative grader ran afresh and contradicted the claim. This is the outcome the fallback ordering predicts, since the authoritative grader always writes the per-task path that takes precedence. 20 Preprint The validity argument therefore rests on the contradicted write, which is empirical, rather than on an argument that the write was impossible: the agent’s log-tree writes do reach the host-side trial directory, and one flat grader output file carries a modification time inside the execution window. The reported numbers are unaffected, and the flat fallback path remains reachable by an agent command.

H.4 CONTAINER AND HOST ENVIRONMENT

The tool mix separates the systems along the intake axis. Requests for the next available task account for 11.2% of Opus’s tool calls and 16.6% of Kimi’s, against 3.1% for GLM and 2.5% for DeepSeek. ## J TERMINAL STATES AND RESOURCE UTILIZATION 

The serial deficit is carried by never-claimed work. Figure 8 counts the scored tasks of Table 2. Never-claimed shares fall from 48.3% to 18.8% on medium and from 70.0% to 13.9% on heavy as the policy moves from serial to guidance, while the verified share rises from 34.9% to 55.9% and from 18.6% to 36.7%. Serial has no unfinished claims, because with k = 1 a task is either served to completion or never started. On heavy, serial and fixed k = 2 run to the 4-hour limit in every trial (Figure 16), so their lower delivery is not explained by stopping early. The serial-minus-native contrast in verified share is −0.172 [ −0.269, −0.076] on medium and −0.219 [ −0.329, −0.139] on heavy (percentile bootstrap over workloads), both excluding zero. 

Native management’s extra held tasks do not raise CPU use. Figure 9(a) shows that native management on heavy holds nearly four tasks at a time and reaches the same CPU utilization as fixed 

k = 2 holding two (27.2% vs 26.7%); on medium it holds 1.40 tasks at the same 14.6% CPU that serial reaches holding one. Going from one held task to two does raise it: fixed k = 2 uses 1.8 and 1.6 times serial’s CPU on medium and heavy (Table 3). Every policy leaves at least 70% of the four provisioned cores idle while tasks wait. 

Self-assessment does not improve with management. Of the tasks each policy reported complete, the share the verifier confirmed is 90.6%/80.4% for serial, 88.4%/87.4% for fixed k = 2 , 85.5%/78.7% for native management, and 83.4%/76.8% for guidance (medium/heavy). The two agent-managed policies are the least accurate in both tiers, guidance most of all. Between 9.4% and 23.2% of reported-complete tasks did not verify, so a self-reported completion is not interchangeable with a verified one. 

Compute cost per delivered task. CPU-seconds of the agent-execution phase per fully verified task is lowest for GPT-5.6-sol (759–1020 CPU-s) and highest for GLM (1442–2794). Across the GLM execution policies, serial FIFO costs more per solved task than native management in both tiers (1929 vs 1442 CPU-s on medium, 2852 vs 2794 on heavy), because its solved count falls faster than its compute does. Serial execution is therefore not a compute-saving configuration. 

Confirmed memory terminations are rare. No native-stream trial carries structured evidence of an out-of-memory termination, and exactly three trials elsewhere in the collection do (two GLM-5.3 25 Preprint heavy stream runs under burst arrivals and guidance, and one individual run, each terminated by signal with harness exit code 137). The containers expose no usable out-of-memory counters, so a zero reading is not evidence of absence. 

Memory overruns on heavy workloads. Figure 15 traces CPU and memory for every heavy stream trial. Kimi-K3 exceeds the memory allocation in 6 of its 15 trials, against 3 for Claude Opus 5, 2 for GLM-5.3, 1 for DeepSeek-V4-Pro and none for GPT-5.6-sol. Three causes can be separated. 

Workload composition. Six of the twelve overruns occur on one workload ( 55dcdddf : Kimi-K3 in all three trials, Claude Opus 5 in two, GLM-5.3 in one). It contains tb3-pretrain-shard-corruption , whose solutions need about 5 GiB even when the task runs alone: every system’s individual runs of it peak at a median of 5.0–6.5 GiB, so almost any concurrent work pushes the container past 8 GiB. One memory-hungry solution. On that task Kimi-K3 is the outlier: its individual runs peak at a median of 6.5 GiB and exceed 8 GiB in 3 of 8, while the other four systems stay near 5 GiB and never exceed it. One of its stream overruns happens with that task as the only one in flight. 

Not general inefficiency or over-concurrency. Across all heavy individual runs Kimi-K3 exceeds 8 GiB in 1.9% of them, against 1.3% for Claude Opus 5 and GPT-5.6-sol and 4.1% for GLM-5.3. It also holds fewer tasks at once than Claude Opus 5 or GLM-5.3 (median realized concurrency 4.5 against 5.4 and 5.9), and four of its six overruns occur with six or fewer tasks in flight, whereas four of the five Claude Opus 5 and GLM-5.3 overruns occur with 13 or more. It does not leave work running in the background: it launches the fewest background processes of any system (0.5% of its shell commands, against 5.3% for Claude Opus 5), and with at most one task in flight its container holds a median of 0.7 GiB. What remains is exposure: Kimi-K3 runs 11 of its 15 heavy trials to the 4-hour limit, against 6 for Claude Opus 5, so it spends longer with memory-heavy tasks open. 

Contention occurs but is not quantifiable; no score was manipulated. Narrow patterns for four resource-conflict classes match in a minority of the 390 native-stream trials of every tier (disk exhaustion in 56 of 390, process or descriptor exhaustion in 47, file-lock contention in 29, port collisions in 12), but a match may equally be a conflict recovered from or text narrated while reasoning. We adjudicated by hand all 52 command-level references to the harness log tree, in 31 trials, and report zero confirmed instances of score manipulation. One DeepSeek trial wrote a reward file on an agent-writable fallback path; the authoritative grader reran and overrode it, recording 0.0 (Appendix G). 

## K RELATED WORK 

Computer-use agent evaluation. Computer-use benchmarks evaluate agents by the state changes they produce in executable environments. SWE-bench packages software repositories with executable test suites (Jimenez et al., 2024). Terminal-Bench and TUA-Bench package each task with a container specification and an in-environment verifier (Merrill et al., 2026; Chen et al., 2026). CORE-Bench evaluates the reproduction of computational research from code and data (Siegel et al., 2024), while TerminalWorld reconstructs Docker environments and tests from recorded terminal workflows (Chu et al., 2026). On graphical interfaces, WebArena, VisualWebArena, and OSWorld evaluate browser and desktop agents (Zhou et al., 2024; Koh et al., 2024; Xie et al., 2024). Their common limitation for our setting is the evaluation unit: they score one objective in one environment instance, whereas AOS-Bench composes multiple independently verifiable objectives in a shared container released over time. 

Agents for management and sustained operation. A growing line of work evaluates agents as operators of persistent social or economic processes. Vending-Bench, Business Arena, and E-Commerce Bench ask agents to manage inventories, capital, suppliers, and long-horizon economic outcomes (Backlund & Petersson, 2025; Pan et al., 2026; Fan et al., 2026). TheAgentCompany embeds agents in a simulated software company requiring communication, code, and professional tasks (Xu et al., 2025). These environments expose important management capabilities, but their managed object is a domain process; AOS-Bench instead studies the role in which the managed object is the user’s computational workload under shared resource constraints.
