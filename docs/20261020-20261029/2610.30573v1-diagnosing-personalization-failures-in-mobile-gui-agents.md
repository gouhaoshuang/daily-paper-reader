## 摘要
与传统的 GUI 智能体不同，个性化 GUI 智能体需要用户偏好来指导在动态变化的 GUI 状态上的顺序执行。这带来两个挑战：确定每种偏好应如何改变执行策略，以及它应在交互轨迹的何时生效。现有基准主要评估整体任务成功率，对这些问题提供的洞察有限。我们提出 PrefDiag-Bench，包含两个部分：（1）将偏好分为五种类型，刻画它们如何影响执行；（2）一个分阶段诊断框架，包含 1,664 个探针，追踪偏好应在何时生效以及失败发生在何处。我们在两种用户上下文形式（显式用户画像和行为记忆日志）下评估了十一个 GUI 智能体系统，包括端到端智能体和智能体工作流。尽管现有智能体在非个性化任务上取得相对较高的完成率，但在偏好个性化任务上的性能显著降低。即使表现最好的模型 Seed-2.0-Pro，在显式用户画像下的 Process 偏好上也仅达到 47.17%。智能体尤其在 Ranking 和 Process 偏好上表现吃力。进一步分析揭示两个关键能力瓶颈：从用户历史中选择相关证据，以及识别偏好应在执行过程中何时生效。显式提供相关证据的受控干预可将端到端任务成功率最高提升 7.06%。PrefDiag-Bench 提供了超越整体任务成功率的、对 GUI 智能体个性化能力更系统的评估。代码和数据见 https://github.com/Zhixin-L/PrefDiag-Bench。

## Abstract
Unlike conventional GUI agents, personalized GUI agents require user preferences to guide sequential execution over changing GUI states. This raises two challenges: determining HOW each preference should alter execution strategy and WHEN it should take effect along the interaction trajectory. Existing benchmarks primarily evaluate overall task success, offering limited insight into these questions. We introduce PrefDiag-Bench with two components: (1) a categorization of preferences into five types, characterizing HOW they affect execution; and (2) a stage-wise diagnostic framework with 1,664 probes, tracing WHEN preferences should take effect and where failures occur. We evaluate eleven GUI agent systems, including end-to-end agents and agentic workflows, under two forms of user context: explicit user profiles and behavioral memory logs. Although existing agents achieve relatively high completion rates on non-personalized tasks, performance is substantially lower on preference-personalized tasks. Even the best-performing model, Seed-2.0-Pro, achieves only 47.17% on Process preferences under explicit user profiles. Agents struggle particularly with Ranking and Process preferences. Further analysis reveals two key capability bottlenecks: selecting relevant evidence from user history and recognizing when preferences should take effect during execution. Controlled interventions that explicitly provide relevant evidence improve end-to-end task success by up to 7.06%. PrefDiag-Bench offers a more systematic evaluation of GUI agents' personalization capabilities beyond overall task success. Code and data are available at https://github.com/Zhixin-L/PrefDiag-Bench.

## 1. 核心问题与整体含义

- **研究背景**：基于 LLM 的移动 GUI 智能体已在 GUI 感知、任务规划与多步执行上取得显著进展，正逐步走向“个性化助手”。在个性化场景中，仅完成用户请求已不够，智能体还需结合用户历史行为、习惯与偏好做出个体化决策。
- **核心问题**：个性化 GUI 智能体面临两个互补挑战：
  - **HOW**：每种偏好应如何改变智能体的执行策略（改变最终结果、限制可行选项、调整候选优先级、约束执行流程或交互行为）；
  - **WHEN**：偏好应在交互轨迹的哪个 GUI 状态/时机生效。
- **现有评估的不足**：已有基准（如 PersonalAlign、PSPA-Bench、KnowU-Bench、Persona2Web 等）主要评估整体任务成功率或偏好敏感的进度，无法刻画偏好如何改变执行要求、何时生效，也难以定位从用户上下文到 GUI 动作链路上的失败环节。
- **整体含义**：论文提出 **PrefDiag-Bench**，一个细粒度、面向执行、分阶段诊断的个性化 GUI 智能体基准，旨在超越“总体成功率”，系统评估偏好应用能力并定位能力瓶颈。

## 2. 方法论

### 2.1 核心思想

- 以**偏好对执行的主要影响**作为主评估轴，将用户偏好分为五类，并构建对应的端到端任务；同时为每个任务配套**分阶段诊断探针**，把端到端表现与具体能力阶段关联起来。
- 采用**任务—探针配对设计**：每个端到端任务与其诊断探针基于同一底层偏好实例构建，从而既能评估交互式 GUI 环境中的个性化任务成败，又能定位失败发生在哪个能力阶段。

### 2.2 偏好五分类（HOW）

- **Outcome（结果）**：指定期望的最终结果或选择（如“无糖、少冰”）。
- **Constraint（约束）**：设定有效结果或允许动作必须满足的条件（如价格 ≤ 20 元）。
- **Ranking（排序）**：规定有效候选之间的优先级（如优先配送更快的店铺，同速时选更便宜者）。
- **Process（流程）**：规定任务应如何执行（如下单前跨平台比价），仅看最终 GUI 状态不足以验证，需检查执行轨迹。
- **Interaction（交互）**：规定是否、何时、如何与用户交互（如下单前请求确认）。
- 区别：Process 约束任务流程，Interaction 约束与用户的沟通；两者都可能出现“最终状态正确但过程违规”。

### 2.3 形式化定义与评估流程

- 个性化实例定义为 **Tᵢ = (Iᵢ, Cᵢ, E⁰ᵢ, Sᵢ)**：Iᵢ 为指令，Cᵢ 为承载偏好 pᵢ 的用户上下文，E⁰ᵢ 为初始环境状态，Sᵢ 为确定性成功检查器。
- 执行产生轨迹 **τᵢ = (o₁, a₁, …, o_T, a_T)**；检查器返回 **Sᵢ(E_Tᵢ, τᵢ) ∈ {0,1}**，为 1 需同时满足任务目标与所有偏好要求（含规定流程或确认动作）。
- 个性化 AVG 为五类偏好 TSR 的宏平均；诊断准确率按任务级聚合——同一任务关联的所有问题全部答对才算正确（如 3 个 P4 题答对 2 个记为 0）。

### 2.4 分阶段诊断框架（WHEN 与失败定位）

覆盖三大阶段、五个诊断探针（共 1,664 个探针，源自 260 个偏好原子、256 个失败任务）：

- **信息处理**：
  - **P1 日志到记忆归纳**：从行为日志中归纳稳定偏好；
  - **P2 证据选择**：给定偏好，选出直接支持该偏好的日志条目（多选，需精确匹配）。
- **上下文推理**：
  - **P3 任务相关性**：判断哪条已知偏好应影响当前任务；
  - **P4 触发识别**：基于当前截图与历史动作，判断偏好处于“尚未激活 / 当前激活 / 已过期”三态之一。
- **动作制定**：
  - **P5 操作映射**：在偏好已激活的前提下，选择语义上正确的下一步策略（非屏幕坐标或动作 token）。
- 探针独立作答，不传递预测结果；需要时提供 ground-truth 前置条件。

### 2.5 数据构建

- 从 KnowU-Bench 选取任务，检查目标、应用设置与成功标准，人工审查后构建 53 个任务族，每族 1 个 Basic + 5 个偏好变体，共 **318 个实例（53 Basic + 265 个性化）**。
- 偏好通过用户上下文而非指令重述传达；构建**成对上下文**：
  - **显式用户画像（EUP）**：LLM 起草，GPT-5.6 Sol 修订，逐条人工审查；
  - **行为记忆日志（BML）**：由画像合成，每次收集 4–5 条相关记录，含支持证据与干扰项，同样经模型修订与人工审查。
- 两种上下文下指令、初始状态、成功检查器保持一致。
- 诊断探针从行为日志下的执行失败中导出，保留检查器结果有效者并按任务去重；P4/P5 仅使用触发边界清晰、有可用参考轨迹的原子；P5 参考动作取自成功 rollout 并表示为语义操作；所有选择题由人工作答确认。

## 6. 主要结论与发现

- **个性化任务显著更难**：11 个系统在偏好条件任务上的平均 TSR 均低于 Basic。Seed-2.0-Pro 最强（EUP 62.64%、BML 65.66%），但 Basic 达 81.13%；Claude Sonnet 4.6 Basic 最高（86.79%）却在个性化设置下被 Seed 反超——强通用 GUI 能力是必要但不充分条件。
- **偏好类型差异巨大**：Outcome 在 10/11（EUP）和 11/11（BML）系统中表现最好；**Ranking 与 Process 持续最难**。BML 下 Qwen3.7-Plus 从 Outcome 62.26% 跌至 Process 16.98%（差 45.28 点）；Seed-2.0-Pro 从 Outcome 83.02% 降至 Ranking 45.28%（差 37.74 点）。仅报告总体个性化分数会掩盖这些能力差异。
- **显式上下文不一定更有效**：EUP 与 BML 无一致方向。Seed-2.0-Pro（62.64%→65.66%）和 T3A（24.91%→29.44%）在日志下更好，M3A 则从 37.73% 跌至 18.49%；M3A 与 T3A 同用 GPT-5.4，说明上下文形式的效果还取决于工作流如何处理用户信息。
- **两大能力瓶颈**：P2 证据选择（平均 40.06%）与 P4 触发识别（平均 39.69%）是得分最低阶段，远低于 P3（88.80%）及 P1/P5（>98.9%）；即使 Seed-2.0-Pro 也仅 71.48%（P2）和 58.14%（P4）。
- **联合分析佐证**：P2/P4 的“任务与探针双失败（FF）”比例显著更高（如 Step-GUI-4B 分别为 82.1% 和 66.0%），把探针弱点与真实任务失败直接关联。
- **Thinking 变体表现突出**：Qwen3-VL-8B-Thinking 在开源系统中 P2（69.53% vs Instruct 21.88%）与 P4（45.79% vs 25.58%）最高，接近闭源领先水平。
- **证据干预有效但受 GUI 能力制约**：C0→C1，Seed-2.0-Pro 提升 7.06 点（76.47%→83.53%），Qwen3.7-Plus 提升 5.88 点；但 C2（仅保留支持日志）反而回落（81.18%、51.76%），说明“标注噪声”比“删除噪声”更有效，噪声可提供对比线索。Qwen3-VL-Thinking 虽 P2 较强，但受基础 GUI 能力限制，干预收益有限。
- **记忆构建方法不改变结论**：Mem0、LangMem、Hindsight 下 Outcome 仍最高、Ranking/Process 仍最低，偏好类型难度差异具有稳健性。

## 7. 优点

- **评估视角创新**：以“偏好如何改变执行”为分类轴，五类偏好直接对应不同的执行要求，比语义分类更贴近智能体设计需求。
- **任务—探针配对设计**：将端到端成败与 P1–P5 能力阶段打通，可定位失败环节，而非只给一个总分。
- **同时刻画 HOW 与 WHEN**：P4 触发识别三态（未激活/激活/过期）直接检验“偏好何时生效”，弥补现有基准空白。
- **双上下文对照**：EUP 与 BML 在指令、状态、检查器固定下对比，揭示“更显式不一定更好”的反直觉发现。
- **失败驱动 + 人工审查的数据构建**：探针源自真实失败轨迹，偏好原子可独立诊断；LLM 起草后经 GPT-5.6 Sol 修订与逐条人工复核，并有自动化一致性校验。
- **控制干预具有可操作性**：C0/C1/C2 设计区分“
