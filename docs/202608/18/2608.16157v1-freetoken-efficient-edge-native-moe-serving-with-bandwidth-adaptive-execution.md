## 摘要
前沿开放权重模型日益普及，但其服务仍主要假设数据中心基础设施。我们提出FreeToken，一个边缘原生的MoE服务系统，它将个人机器不仅仅视为小型GPU，而是一个统一的、弹性的推理平台。FreeToken围绕本地AI的两个现实，协同设计完整的服务栈，包括模型布局与加载、专家驻留、CPU-GPU执行、智能体状态复用以及运行时内存管理：智能体工作负载会持续改变其执行模式，而边缘硬件暴露的异构资源在不同机器间存在平衡差异。FreeToken不采用固定的卸载策略，而是持续将计算和模型状态映射到实际可用的资源上。FreeToken支持20多种MoE模型，以及从8GB笔记本GPU到单个工作站GPU的硬件上的真实编码和工具使用智能体。更重要的是，它改变了这些机器实际能服务的范围：从笔记本上的35B模型，到游戏台式机上的284B模型，再到单个工作站GPU上的753B GLM-5.2。FreeToken将开放权重转化为可部署的本地软件，使用户已有的机器成为前沿规模智能的实用平台。我们在flashml.ai发布该系统。

## Abstract
Frontier open-weight models are increasingly available, but serving them still largely assumes datacenter infrastructure. We present FreeToken, an edge-native MoE serving system that treats a personal machine not as a small GPU, but as a unified, elastic inference platform. FreeToken co-designs the full serving stack, including model layout and loading, expert residency, CPU--GPU execution, agentic state reuse, and runtime memory management, around two realities of local AI: agent workloads continuously change their execution pattern, and edge hardware exposes heterogeneous resources whose balance differs from machine to machine. Rather than committing to a fixed offloading strategy, FreeToken continuously maps computation and model state onto the resources actually available. FreeToken supports more than 20 MoE models and real coding and tool-using agents across hardware ranging from an 8GB laptop GPU to a single workstation GPU. More importantly, it changes what these machines can practically serve, from a 35B model on a laptop to a 284B model on a gaming desktop and the 753B GLM-5.2 on a single workstation GPU. FreeToken turns open weights into deployable local software, making the machines users already own a practical platform for frontier-scale intelligence. We release the system at flashml.ai.

# FreeToken论文中文总结

## 1. 核心问题与整体含义

- **背景**：前沿开放权重MoE模型（如DeepSeek-V4-Flash、GLM-5.2）在能力上不断接近专有模型，但其服务仍严重依赖数据中心级GPU集群，成本高昂，个人用户和小团队难以承受。同时，全球已有超过一亿台带独立GPU的消费级设备，但缺乏能充分利用这些异构资源的服务系统。
- **核心问题**：MoE模型虽然激活参数稀疏，但完整专家池需要大量内存，远超单个消费级GPU的VRAM。现有边缘服务系统（llama.cpp、KTransformers、Ollama等）存在三大缺陷：
  1. **Prefill阶段**：长提示词会激活几乎所有专家，导致大量专家权重反复从主机内存传输到GPU，且Agent工具调用频繁触发上下文编辑，造成大量重复计算（re-prefill）。
  2. **Decode阶段**：专家缓存未命中处理策略不当——静态放置跟不上动态路由，预测式预取无法解决不可避免的miss，且未能在PCIe传输与CPU执行之间做合理分工。
  3. **资源动态性**：边缘GPU同时被浏览器、游戏等应用占用，可用VRAM和带宽动态变化，固定策略无法适应。
- **整体含义**：论文主张将个人机器视为统一、弹性的推理平台，而非“小型GPU”。通过全栈协同设计，让用户已有的消费级硬件能够交互式运行前沿规模模型，从而把“开放权重”真正转化为“开放访问”。

## 2. 方法论

### 核心思想
- 采用两级专家内存层次：主机（CPU/DRAM）保存完整专家池作为“唯一事实来源”，GPU上维护一个全局的、可弹性调整的LRU专家缓存。
- 围绕两个执行原则：**带宽自适应执行（Bandwidth-Adaptive Execution）** 和**语义感知缓存（Semantic-Aware Caching）**，以及一个弹性资源管理策略。

### 关键技术细节

#### (a) Prefill：全层双缓冲 + 语义锚点状态缓存
- **全层双缓冲**：为prefill分配两个full-layer缓冲区。GPU计算第l层路由专家时，专用传输流同时将第l+1层完整专家集加载到另一缓冲区，从而隐藏PCIe传输时间。由于加载的是完整层，无需等待路由结果，传输可提前开始。
- **语义锚点状态缓存**：针对混合注意力（如gated DeltaNet、稀疏注意力）的循环状态，在语义边界（thinking段、工具调用、工具输出、对话轮次）保存检查点。当Agent框架编辑上下文时，可从最近的、未失效的锚点恢复，只重新计算新后缀，避免数千token的重复prefill。

#### (b) Decode：语义感知专家缓存 + q*策略
- **LRU专家缓存**：利用相邻token路由的强局部性，以（layer, expert）为粒度的全局LRU缓存跟踪当前工作集，大多数路由访问可在VRAM命中。
- **带宽自适应执行**：对于每层m个未命中的唯一专家，将其分为两类：
  - **F集合**：通过PCIe传输到GPU缓存并执行，同时为未来复用做缓存填充。
  - **C集合**：直接在CPU上从主机内存计算，不改变GPU缓存状态。
- **q*公式推导**：
  - 设BP为PCIe专家传输带宽，BH为主机端专家处理带宽。
  - PCIe饱和后剩余主机带宽为 BR = max(BH - BP, 0)。
  - 平衡两条并发路径的耗时得到：q⋆ ≈ m · BP / BH。
  - 当BH接近BP时，系统退化为纯按需缓存填充；该公式适配从笔记本到工作站的任意硬件平衡。
- CPU和GPU分别计算部分和，精确合并输出，不产生近似误差。

#### (c) 弹性边缘资源管理
- **运行时缓存重配置**：在调度安全点，无需重启或重新加载主机专家池，即可根据变化的VRAM预算动态重建GPU专家缓存。
- **快速启动**：从磁盘读取专家权重直接写入最终主机布局，随后再锁定内存；冷启动时第一个请求由普通的decode路径处理，无需预热。

### 实现层面
- **CUDA-Graph兼容的LRU缓存**：所有路由相关控制（去重、分类、选择victim、计算q值）在单GPU内核内完成，避免每层设备同步；victim选择采用单次遍历识别K个LRU候选槽位。
- **FTW格式**：将模型checkpoint标准化为“expert bank”，以层-专家ID作为统一逻辑标识，加载时跳过tensor发现和重打包。
- **平台适配**：CPU执行器根据SIMD和核心布局调度；若无法锁定内存则退化为纯CPU MoE后端。

## 6. 主要结论与发现

- **吞吐优势**：FreeToken在RTX 5090上，Qwen3.6达到77–83 tok/s，DSV4-Flash达到22–25 tok/s，是最强基线的1.5–2.3倍。
- **agent场景稳定性**：在三种agent工作负载下，decode速率保持在单轮场景（W1）的12%以内；而KTransformers在DSV4上从W1到W2已退化31%，说明单流基准会高估基线在agent场景的表现。
- **尾延迟**：FreeToken在所有工作负载下最差TTFT低于44秒；每个基线都至少在一个场景中超过150秒，达到真实Agent客户端的超时阈值。
- **跨硬件普适性**：在5个消费级系统上提升1.3–2.1倍；8GB笔记本上35B模型达到39.3 tok/s（超过Codex生产轨迹中位数33 tok/s）；32GB游戏台式机可交互式运行284B模型；工作站上753B GLM-5.2吞吐为llama.cpp的2.0倍。

## 7. 优点

1. **系统化全栈设计**：将模型布局、加载、缓存、执行、内存管理统一在一个框架下，而非碎片化修补。
2. **带宽自适应模型**：用两个实测带宽推导出闭式最优解，简单高效且可嵌入CUDA Graph，适配所有硬件平衡。
3. **针对Agent工作负载的原创优化**：语义锚点状态缓存与上下文编辑模式（工具调用、思考块裁剪）深度耦合，解决真实场景痛点。
4. **弹性内存管理**：适应边缘设备资源波动，无需重启即可调整缓存配置，且冷启动无需预热。
5. **工程实现扎实**：CUDA Graph内完成动态路由控制，FTW格式减少加载开销，CPU/GPU精确合并输出。
6. **实验设计完整**：覆盖从8GB笔记本到96GB工作站的硬件谱系，使用真实编码/邮件Agent，并报告尾延迟，结论可信度较高。

## 9. 综合评估与适用边界

### 整体判断
这是一篇**系统性、工程完成度极高**的推理服务系统论文。其核心贡献不在于单一算法突破，而在于将"带宽自适应"这一思想贯穿prefill、decode、缓存、内存管理全链路，并用真实的Agent负载和6种硬件谱系验证了普适性。对于"消费级硬件能否交互式运行前沿MoE模型"这一问题，给出了目前最完整、最有说服力的肯定回答。

### 最适用的场景
- **个人开发者/研究者**：拥有24–32GB VRAM的消费级GPU，希望本地运行200B+开放权重MoE模型，用于编程Agent、长文档分析等交互式任务。
- **小团队私有化部署**：需要数据不出内网、但无力承担数据中心GPU成本的团队，FreeToken可将现有工作站/游戏机转化为推理资源。
- **8GB级轻薄本/笔记本用户**：在带宽受限（PCIe 4.0×8）的平台上首次实现30B+模型超40 tok/s的交互体验。

### 不太适用的场景
- **严格实时/硬延迟保证**的系统（如工业控制、实时翻译），因为PCIe传输的不确定性使得尾延迟虽可接受但不具备硬上界。
- **多租户共享设备**：缓存和内存管理未做租户隔离设计。
- **超长单上下文（>100k）持续生成**：prefill双缓冲和锚点缓存的收益在单轮超长生成中会被decode端的CPU/GPU带宽竞争所稀释。

## 10. 关键术语速查

| 术语 | 含义 |
|------|------|
| MoE | 混合专家（Mixture-of-Experts），稀疏激活模型架构 |
| Prefill / Decode | 提示词批量解析阶段 / 逐token自回归生成阶段 |
| TTFT | Time To First Token，从请求到首个输出token的延迟 |
| MXFP4 / NVFP4 | 4比特浮点量化格式（微软 / NVIDIA标准），模型权重的压缩存储格式 |
| q* | 最优CPU执行配额，由PCIe带宽与主机处理带宽之比推导的闭式解 |
| FTW格式 | FreeToken Weight，按"层-专家ID"预布局的标准化checkpoint格式 |
| 语义锚点 | 在Agent语义边界保存的循环状态检查点，用于跳过高代价的re-prefill |
| 全层双缓冲 | 用两个full-layer缓冲区隐藏prefill阶段专家权重传输时间的技术 |

## 11. 对读者的启示与复现建议

1. **思想可迁移**：q*公式（q⋆ ≈ m · BP / BH）本质是一个通用的异构执行平衡公式，不仅适用于MoE推理，也可推广到任何"GPU+CPU混合计算+传输"的场景（如视觉模型、多模态RAG）。
2. **复现注意**：论文涉及2026年时间戳的模型（DeepSeek-V4-Flash、GLM-5.2），实际复现时可先用同架构的现行模型（如DeepSeek-V3.x、Qwen2.5-MoE）验证核心机制；FTW格式的离线转换脚本和CUDA Graph内的LRU内核应优先实现。
3. **阅读重点**：建议重点关注第5章（q*推导与带宽自适应执行）和第6章（弹性缓存管理）——前者是理论核心，后者是工程难点，理解这两部分即可把握论文精髓。

**总体结论**：FreeToken以严谨的公式推导、扎实的CUDA工程和覆盖广泛的实验，证明了一条"不依赖数据中心"的推理路线是现实可行的；尽管存在基线对比不完全、安全模型缺失等瑕疵，它仍然是边缘大模型推理领域近年来最具实用价值的系统工作之一。
