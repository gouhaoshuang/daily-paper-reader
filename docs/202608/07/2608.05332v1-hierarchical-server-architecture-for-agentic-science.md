## 摘要
代理科学正在改变计算工作的格局，延伸到科学工作流和工作负载管理器。这些工作负载需要机构内部及跨机构的专用硬件。如果调度需要评估工作负载需求与环境，那么资源的自动发现就是一个必不可少的步骤。在本文中，我们提出了一种层次化、动态的架构和软件，用于在多样化的云、边缘和HPC系统中发现资源。该设计使得使用秘书代理进行并发、异步的协商、选择和调度工作请求成为可能。这些代理探测并发现了7个类别中的51个真实和模拟提供者。我们进行了19,973次协商和6,952次选择模拟来评估决策的可靠性，展示了高(87.71%)的协商准确性和与传统策略相当的选择成本。该架构专为可扩展性而设计，目前支持Genesis任务，体现了代理、发现工具和基础设施之间精心协调对于代理科学的重要性。

## Abstract
Agentic science is transforming the landscape of computational work, extending to scientific pipelines and workload managers. The workloads require specialized hardware within and across institutions. If assessing workload needs against environments is required for scheduling, automated discovery of resources is an essential step. In this paper, we present a hierarchical, dynamic architecture and software to discover resources across diverse cloud, edge, and HPC systems. The design enables concurrent, asynchronous negotiation, selection, and dispatch of requests for work using secretary agents. The agents probe and discover 51 real and simulated providers across 7 categories. We perform 19,973 negotiation and 6,952 selection simulations to assess reliability of decisions, demonstrating high (87.71\%) negotiation accuracy and selection costs comparable to more traditional strategies. Designed for extensibility and currently supporting the Genesis Mission, this architecture exemplifies the importance of careful coordination between agents, discovery tools, and infrastructure for agentic science.

## 2. 方法论：核心思想、关键技术细节

### 2.1 整体架构
- 基于 **Model Context Protocol (MCP)** 标准构建服务器，MCP 是 Anthropic 开发、后捐赠给 Agentic AI 基金会的行业标准协议，定义了客户端与服务器之间的 JSON-RPC 调用规范。
- 服务器可以在多个层次部署：**Job**（作业生命周期内、用户拥有）、**Cluster**（集群级持久服务）、**Center**（中心级最高安全要求）。
- 层次结构中的角色包括：**hub**（分发请求的父节点）、**worker**（工人节点）、**fleet**（工人组）。hub 可兼作 worker，但生产环境建议独立部署。

### 2.2 作业协商流程（Job Negotiation）
用户通过 `negotiate_job` 接口提交文本请求，流程如下：
1. 用户提交文本请求（应用、资源、约束）；
2. hub 解析请求并用 `gather` 函数**并发异步**发送给所有子 worker；
3. worker 通过 `ask_secretary` 实例化一个 **SecretaryAgent**，该代理**针对单个请求限定作用域**（保证安全性）；
4. 代理调用**可发现的 provider 接口**探测本地资源状态；
5. 代理返回**proposal**（提案），包含：
   - **READY**（可立即执行）
   - **BUSY**（可稍后执行）
   - **INCOMPATIBLE**（无法满足）
   - 推理理由 + 指标 + 约束（JSON 格式）；
6. **选择算法在客户端运行**，减轻中心和集群负担；
7. 客户端通过 `dispatch_job` 将选中的提案发送到目标集群。

### 2.3 秘书代理与提供者接口
- **Resource Secretary** 库定义了 51 个真实/模拟资源提供者，涵盖 7 个类别（工作负载管理器、容器、存储、网络、硬件、并行库、软件包管理器）。
- Provider 通过 `secretary_tool` 和 `dispatch_tool` 装饰器暴露功能，代理通过解析函数签名和文档字符串来理解工具用法。
- 代理被要求必须**至少执行一次系统观测**，不得编造结果或提供泛泛的聊天回复。

### 2.4 分派代理（Dispatch Agent）
- 收到分派请求后，代理将文本请求转换为**作业规范**（针对特定工作负载管理器）；
- 通过 provider 工具进一步查询精确路径、库、参数；
- 执行提交、监控状态更新，并可通过事件流（event stream）回传状态。

### 2.5 选择算法
提供 7 种选择算法（表 1）：

| 策略 | 类型 | 逻辑 | 状态 |
|------|------|------|------|
| `agentic` | LLM推理 | 灵活处理复杂请求 | 视情况 |
| `first-ready` | 贪心 | 第一个可用兼容 | READY |
| `random` | 随机 | 随机选择 | READY |
| `soonest` | 量化 | 最早开始时间 | READY/BUSY |
| `run-anytime` | 随机 | 所有兼容集群 | 全部 |
| `min-cost` | 经济 | 预算优化 | READY/BUSY |
| `queue-depth` | 量化 | 舰队负载均衡 | READY/BUSY |

## 3. 实验设计：数据集、场景、基准与对比方法

### 3.1 模拟工人生成
- 生成 **200 个模拟 worker**，按 40/40/20 比例分为 **HPC、Cloud、Standalone** 三种原型。
- 使用**过程化生成**方法：worker 身份哈希为整数种子，保证**确定性和可复现性**。
- 每种原型定义 `scale (T_s)` 和 `density (T_d)` 两个潜变量，从高斯分布 N(μ,σ) 采样并裁剪至 [0.01, 1.0]。
- 每个原型定义资源槽位的数量和类型（如 HPC 有 1 个工作负载管理器（Flux/Slurm）、1-3 个软件管理器（Spack/Modules/Conda/Pip）、存储（Lustre/NFS）、网络（InfiniBand/Omni-Path）、并行（OpenMPI/MPICH）、硬件（CPU/GPU/内存）等）。
- 规模范围示例：HPC 100–10K 节点、32–128 CPU/节点、128–1024GB RAM/节点，0–8 GPU；Cloud 1–500 节点；Standalone 单节点。

### 3.2 提示词（Prompt）生成
- 沿 **10 个资源维度**、**3 种风格**、**7 个特异性指数（SI）** 进行维度采样。
- SI 代表逻辑 AND/OR 门，取值为 1–7，权重分布为 5/20/30/20/10/10/5。
- 生成了 **100 个确定性提示词**，应用于 200 个 worker，总共约 20,000 次潜在测试。
- 属性包括应用名、版本（带有 ≤、≥、== 运算符）、资源数量、环境特征、时间需求等。

### 3.3 审计与分析
- **Auditor** 模块将 worker 的 ground truth 与代理判断进行比较；
- 计算**最小必需工具调用集**，对比代理的实际调用轨迹，以区分“严谨探索”和“幻觉成功”；
- 工具调用得分为 `(satisfied)/(required)`。

### 3.4 选择模拟
- 对 6 种传统启发式 + 1 种 agentic 策略进行对比；
- 使用真实节点成本数据（如密歇根大学 Great Lakes 集群费率、GPU 云定价）进行成本计算；
- 对 HPC、Cloud、Standalone 分别做归一化成本效率指数（CEI）分析。

## 6. 主要结论与发现

### 6.1 协商准确性
- 整体准确率：**87.71%**；
- 最常见的错误是**将不兼容的集群判为兼容（N=1,611）**，其中：
  - 1,089 例为软件版本匹配错误（代理将依赖版本混为应用版本）；
  - 其余分布在网络（156）、存储（180）、计算（186）；
- 417 例 UNKNOWN，原因为代理超过 10 次探索循环上限；
- 高特异性（SI=7，涉及容器技术）时错误率最高，代理经常混淆容器技术（如 Podman 与 Singularity）；
- SI=1（仅应用名）时，代理因信息不足而无法判断。

### 6.2 逻辑回归显著性发现
- **HPC 原型**：计算需求显著提高成功几率（β=0.5, p<0.001）；容器需求显著降低成功率（β=-0.96, p<0.001）；
- **Standalone 原型**：计算为正驱动（β=1.08, p<0.001），容器负向（β=-0.96, p<0.001）；
- **Cloud 原型**：计算、网络、并行均为正向驱动。

### 6.3 选择模拟
- Agentic 延迟（约 2.2 秒）显著高于传统算法（毫秒级），但**主观上并不算慢**，只是在高吞吐决策场景中可能成为瓶颈；
- **成本效率**：HPC 原型中无显著差异；agentic-cost 策略在 standalone 环境中优于传统 min-cost；
- 传统 `first-ready` 和 `random` 策略表现出**贪心偏差**，总是选择 standalone 或 cloud 实例；
- Agent 在考虑 GPU 时仅关注单价，未将更快的运行时间纳入综合成本模型（模拟中未建模运行时长）。

## 7. 优点

1. **架构设计新颖且实用**：将 MCP 标准引入科学计算资源管理，实现跨云/边缘/HPC 的统一发现与协商；
2. **层次化设计合理**：hub 最小化计算负载，算法在客户端运行，避免集群过载；
3. **模块化提供者接口**：51 个提供者覆盖 7 个大类，易于扩展，附有模拟类便于实验；
4. **安全设计周到**：SecretaryAgent 针对单个请求实例化，信息不跨作业共享；提供认证/授权中间件；
5. **实验可复现性强**：使用确定性种子、过程化生成、开源数据集（20K+），并提供完整软件与数据（Zenodo）；
6. **审计机制严谨**：区分“实际探索”与“幻觉成功”，通过工具调用覆盖率评估推理质量，而非仅看最终结果；
7. **开源生态意识**：软件和数据集全部开源，支持社区扩展。

## 8. 不足与局限

1. **模拟环境局限**：模拟原型基于人为概率分布，不能完全代表真实多样化的计算环境；未建模多租户、用户数量、安全/调度策略等维度；
2. **模型单一**：仅使用 Gemini 2.0 Flash，不同 LLM 的性能差异未探索；
3. **分派未验证**：论文明确说明 dispatch 实验已实现但未包含在本报告中，等待后续论文；
4. **选择实验简化**：选择模型未考虑作业形状（job shape）、应用运行时长、任务依赖等关键调度因素；GPU 成本未考虑运行时间收益；

9. **选择实验缺乏真实集群对照**：没有在真实生产集群上验证调度决策的实际效果。
