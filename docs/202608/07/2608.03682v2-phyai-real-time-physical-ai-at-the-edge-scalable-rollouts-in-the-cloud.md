## 摘要
物理AI策略在其整个生命周期中都需要推理，包括模型评估、云端强化学习推演、边缘GPU服务和机载部署。尽管这些场景共享相同的检查点和动作语义，但它们通常依赖独立的推理程序。为了统一这些场景，我们构建了PhyAI，这是一个物理AI推理引擎，采用单一运行时，将特定于架构的条件处理、求解器、缓存和输出逻辑保留在模型适配器中，同时共享图执行、内核、内存管理和并行服务。同一代码库可以在机载、边缘和云端部署中，于单个或多个GPU上运行视觉-语言-动作（VLA）模型和世界-动作模型（WAM）。我们利用适配器接口在其发布当天就加入了MiniCPM-Robot。与pi0、pi0.5、GR00T N1.7和MiniCPM-Robot的官方实现相比，PhyAI实现了1.40倍至4.65倍的加速。在Cosmos3-Nano-Policy-DROID上，它在八块H20 GPU上（CFG=2，TP=4）将延迟从2.46秒降低到1.18秒，加速了2.08倍。在多种配置下，专用运行时仍然更快，因此我们的目标是提供一个具有竞争力延迟的单一运行时，而不是在每种情况下都取得最快结果。详细的性能剖析揭示了不同模型为何需要不同的执行策略：在Hopper系列GPU上，批大小为1时，pi0.5动作专家仅占8.8%的FLOPs，却贡献了57.2%的延迟；当批大小增至32时，其占比降至13.5%，吞吐量达到约100个样本/秒。Cosmos3仍以生成为主导，当批大小从1增至16时，吞吐量仅提升14.3%。我们进一步引入了控制时间Roofline，用以区分受推理限制与受环境限制的控制；在四个LIBERO基准套件上测得的pi0.5点受环境限制，而Cosmos3则保持受推理限制。代码和基准测试：https://github.com/mingti-org/phyai。

## Abstract
Physical AI policies require inference throughout their lifecycle, including model evaluation, cloud reinforcement learning rollout, edge GPU serving, and onboard deployment. Although these settings share the same checkpoint and action semantics, they often rely on separate inference programs. To unify them, we build PhyAI, a Physical AI inference engine with a single runtime that keeps architecture-specific conditioning, solver, cache, and output logic in model adapters while sharing graph execution, kernels, memory management, and parallel services. The same codebase runs vision-language-action (VLA) models and world-action models (WAMs) on single or multiple GPUs across onboard, edge, and cloud deployments. We used the adapter interface to add MiniCPM-Robot on the day of its release. PhyAI achieves 1.40x-4.65x speedups over the official implementations of pi0, pi0.5, GR00T N1.7, and MiniCPM-Robot. On Cosmos3-Nano-Policy-DROID it reduces latency from 2.46 to 1.18 s on eight H20 GPUs (CFG=2, TP=4), a 2.08x speedup. Specialized runtimes remain faster in several configurations, so our goal is one runtime with competitive latency rather than the fastest result in every case. Detailed profiles reveal why different models need different execution policies: on a Hopper-series GPU at batch size one, the pi0.5 action expert accounts for 8.8% of FLOPs but 57.2% of latency; at batch size 32 its share drops to 13.5% and throughput reaches about 100 samples/s. Cosmos3 remains generation-dominated and gains only 14.3% throughput as batch size increases from 1 to 16. We further introduce the control-time Roofline, which distinguishes inference-bound from environment-bound control; the measured pi0.5 points on four LIBERO suites are environment-bound while Cosmos3 stays inference-bound. Code and benchmarks: https://github.com/mingti-org/phyai.

## 一、核心问题与整体含义（研究动机和背景）

- **问题背景**：物理AI（Physical AI）策略在其完整生命周期中都需要推理，包括模型评估、云端强化学习（RL）推演、边缘GPU服务和机载部署。尽管这些场景共享相同的检查点和动作语义，但它们通常依赖**独立的推理程序**，导致每条路径都需要单独优化和验证，工程复杂度高且行为一致性难以保证。
- **核心挑战**：具身模型在**执行结构**（如π家族VLA的视觉语言骨干+迭代动作专家，Cosmos3世界动作模型的视频和动作状态协同演化）和**部署需求**（机载强调单请求低延迟、边缘服务需平衡延迟与吞吐、云端推演需大批量分布式执行）上均存在巨大差异，难以用单一LLM式预填充-解码模式覆盖。
- **现有工作不足**：FlashRT、vla.cpp、realtime-vla等只优化特定模型或设备；LeRobot提供生命周期接口但缺乏内核级多架构执行引擎；vLLM和SGLang等LLM服务系统无法直接表达多模态条件、迭代动作求解器、演化世界潜变量或分类器无关引导（CFG）分支。
- **核心观点**：需要一个保留模型语义的同时允许每种架构和部署场景选择合适执行策略的统一推理运行时。

## 二、方法论：核心思想、关键技术细节

### 1. 整体架构：模型语义与执行策略分离

- **模型适配器（Model Adapters）**：保留条件处理、求解器状态、可复用张量、调度和动作转换等架构特定逻辑。
- **共享运行时（Runtime）**：提供图重放、优化内核、内存与缓存管理、量化路径、通信和并行执行等共享服务。
- **分层结构**：调度器（Scheduler）→ 模型运行器（Model Runner，持有状态）→ 无状态建模模块（Modeling Modules）→ 层接口（Layers，含算子选择器）。

### 2. 优化方法

- **内核融合**：实现AdaRMSNorm、融合残差加RMSNorm、单GEMM完成QKV投影、融合GeGLU/SwiGLU激活等；为MiniCPM-Robot实现深度可分离因果Conv1d+SiLU+QKV分割的Triton内核。
- **图重放（Graph Replay）**：声明可复用状态的无效范围，利用CUDA Graph捕获完整循环；如π0.5的视觉语言前缀在十个Euler步中固定，只需计算一次。
- **算子选择（Profiled Operator Selection）**：基于张量形状、数据类型、加速器型号和执行配置，为特定形状选择最优内核（如FlashInfer FA2 vs FA3），且不同加速器可选用不同实现。
- **量化**：通过phyai-model-optimizer离线执行RTN量化，支持W4A16、W8A16、W8A8、W4A8；基准测量使用BF16，加速比不依赖量化路径。

### 3. 并行执行策略

- **数据并行（DP）**：独立请求分配到独立模型运行器，各运行器持有自己的缓冲区和求解器状态（π0.5使用此方式，无需独立分布式路径）。
- **张量并行（TP）+ CFG并行**：Cosmos3-Nano-Policy-DROID使用2×N的TP网格，条件分支和无条件分支分别在不同TP组中执行，每步去噪后通过CFG all-gather获取两分支速度，再执行引导公式：

  \[
  v_{guided} = v_{uncond} + \gamma (v_{cond} - v_{uncond})
  \]
  
  其中γ为引导尺度。
- **空间分块VAE解码**：视频解码时8个秩以2×4网格逐块解码后再拼接。

### 4. 控制时间Roofline（Control-Time Roofline）

- 全路径延迟分解：\[
  L_{critical} = L_{observe} + L_{transfer} + L_{queue} + L_{inference} + L_{actuate}
  \]
- 顺序执行与理想重叠的周期分别为：
  \[
  L_{seq} = L_{inference} + L_{env}, \quad L_{overlap} = \max(L_{inference}, L_{env})
  \]
- 归一化坐标：\(X = L_{env}/L_{inference}\)（相对推理速率），\(Y = L_{env}/L_{control}\)（相对控制速率）。
- 两条曲线：\(Y_{seq} = X/(1+X)\)（顺序循环）、\(Y_{roof} = \min(X, 1)\)（理想重叠屋顶）。
- 关键区分：当推理快于环境执行（X>1）时系统受环境约束，进一步加速只创造时序余量而非提高控制率，该余量可用于更大模型、更便宜设备或吸收尾延迟抖动。

## 六、主要结论与发现

1. **统一推理引擎可行**：PhyAI在所有11个官方对比对中均快于官方实现，加速1.40×-4.65×；同一代码库可运行π0、π0.5、GR00T、Cosmos3、MiniCPM-Robot等多种模型，且能当天适配新发布的模型。
2. **不同模型需不同执行策略**：π0.5动作专家在bs=1占57.2%延迟但仅8.8% FLOPs，批量增大后其瓶颈地位被视觉语言路径取代；GR00T瓶颈从Action Head转为Backbone；Cosmos3始终以生成为主导，批量提升收益有限。
3. **控制时间Roofline有效区分瓶颈**：LIBERO上π0.5的实测点为环境受限（推断已完成，提高控制率需减少环境时间），Cosmos3为推理受限（降低推理延迟直接改善控制率）。
4. **批量规模对吞吐和延迟影响不同**：π0.5在bs=32达到约100样本/秒但同步批延迟需320ms；GR00T在bs=8已达bs=32吞吐的92.2%。
5. **推理时间在RL推演中占比可观**：在实测配置中predict占RL步骤时间的15.9%；在更多去噪步数或更少actor更新轮数下，可达40%-50%，届时加速推理的端到端收益更显著。

## 七、优点与亮点

- **架构设计优雅**：模型适配器与共享运行时的边界清晰，允许特定模型的优化路径与通用服务共存，避免重复实现。
- **适配效率高**：得以及时支持MiniCPM-Robot发布当天，验证了接口的可扩展性。
- **分析工具新颖**：控制时间Roofline为部署决策提供了量化依据；利用Roofline模型和逻辑算术强度解释不同模型的批量行为，分析深入。
- **评估维度全面**：覆盖延迟、吞吐、相位分解、MFU、内存占用、多GPU并行、真实任务成功率等多个维度。
- **坦诚客观**：明确声明目标不是每种配置都最快，承认专用运行时的优势场景，未宣称端到端机器人成功率的提升。
- **代码开源**：提供基准测试工具链，利于复现和扩展。

## 八、不足与局限

1. **精度匹配不完全**：部分对比存在精度差异（BF16 vs FP8），降低可比性。
2. **端到端加速为模拟**：云端RL推演的墙钟加速基于Amdahl模型估算，未实测完整集成的RL训练流程。
