## 摘要
物理AI策略在其整个生命周期中都需要推理，包括模型评估、云端强化学习展开、边缘GPU服务以及机载部署。尽管这些场景共享相同的检查点和动作语义，但它们通常依赖独立的推理程序。为统一这些场景，我们构建了PhyAI，一个物理AI推理引擎，其单一运行时在模型适配器中保留特定于架构的条件化、求解器、缓存和输出逻辑，同时共享图执行、内核、内存管理和并行服务。同一代码库可在机载、边缘和云端部署中，于单个或多个GPU上运行视觉-语言-动作（VLA）模型和世界-动作模型（WAM）。我们利用适配器接口，在MiniCPM-Robot发布当天便为其添加了支持。PhyAI相对于pi0、pi0.5、GR00T N1.7和MiniCPM-Robot的官方实现实现了1.40倍至4.65倍的加速。在Cosmos3-Nano-Policy-DROID上，它将该模型在八块H20 GPU（CFG=2，TP=4）上的延迟从2.46秒降至1.18秒，加速比达2.08倍。专用运行时在多种配置下仍然更快，因此我们的目标是实现一个具有竞争性延迟的单一运行时，而非在每个案例中都达到最快结果。详细的剖析揭示了不同模型为何需要不同的执行策略：在Hopper系列GPU上，批大小为1时，pi0.5的动作专家占FLOPs的8.8%，却占延迟的57.2%；当批大小增至32时，其占比降至13.5%，吞吐量达到约100样本/秒。Cosmos3仍然以生成为主导，随着批大小从1增至16，吞吐量仅提升14.3%。我们进一步引入了控制时间Roofline模型，用于区分推理受限与环境受限的控制；在四个LIBERO套件上测得的pi0.5点属于环境受限，而Cosmos3仍属于推理受限。代码和基准测试：https://github.com/mingti-org/phyai。

## Abstract
Physical AI policies require inference throughout their lifecycle, including model evaluation, cloud reinforcement learning rollout, edge GPU serving, and onboard deployment. Although these settings share the same checkpoint and action semantics, they often rely on separate inference programs. To unify them, we build PhyAI, a Physical AI inference engine with a single runtime that keeps architecture-specific conditioning, solver, cache, and output logic in model adapters while sharing graph execution, kernels, memory management, and parallel services. The same codebase runs vision-language-action (VLA) models and world-action models (WAMs) on single or multiple GPUs across onboard, edge, and cloud deployments. We used the adapter interface to add MiniCPM-Robot on the day of its release. PhyAI achieves 1.40x-4.65x speedups over the official implementations of pi0, pi0.5, GR00T N1.7, and MiniCPM-Robot. On Cosmos3-Nano-Policy-DROID it reduces latency from 2.46 to 1.18 s on eight H20 GPUs (CFG=2, TP=4), a 2.08x speedup. Specialized runtimes remain faster in several configurations, so our goal is one runtime with competitive latency rather than the fastest result in every case. Detailed profiles reveal why different models need different execution policies: on a Hopper-series GPU at batch size one, the pi0.5 action expert accounts for 8.8% of FLOPs but 57.2% of latency; at batch size 32 its share drops to 13.5% and throughput reaches about 100 samples/s. Cosmos3 remains generation-dominated and gains only 14.3% throughput as batch size increases from 1 to 16. We further introduce the control-time Roofline, which distinguishes inference-bound from environment-bound control; the measured pi0.5 points on four LIBERO suites are environment-bound while Cosmos3 stays inference-bound. Code and benchmarks: https://github.com/mingti-org/phyai.

## 1. 核心问题与整体含义（研究动机与背景）

物理AI策略在生命周期中面临多个推理场景，包括：

- **模型离线评估**
- **云端强化学习（RL）rollout**
- **边缘 GPU 共享服务**
- **机载（onboard）部署**

尽管这些场景使用**相同的模型检查点（checkpoint）和动作语义**，现有方案通常针对每个场景编写**独立的推理程序**。这导致以下问题：

- 每个路径都需要单独优化和验证，成本高昂。
- 一个场景中验证过的行为无法自动迁移到另一场景。
- 缺少一个统一的推理基础设施来覆盖物理AI策略的全生命周期。

此外，不同类型的具身模型（embodied models）在执行结构与部署需求上差异显著：

- **π 系列 VLA 模型**：视觉-语言骨干 + 迭代式动作专家。
- **Cosmos3 等世界-动作模型（WAM）**：视频与动作状态联合演化。
- 机载执行重延迟，边缘共享服务需权衡延迟与吞吐，云端 rollout 需大批量与分布式执行。

**核心目标**：构建一个统一推理引擎 PhyAI，使同一模型路径能够无缝运行于机载、边缘和云端，同时保持与专用实现竞争性的延迟性能。

## 2. 方法论（核心思想、关键技术细节）

### 2.1 总体架构：模型语义与执行策略分离

PhyAI 的核心设计原则是 **模型适配器（Model Adapter）** 与 **共享运行时（Runtime）** 分离：

- **模型适配器**：保留架构特定的条件化（conditioning）、求解器状态、缓存有效性、调度、动作转换等语义逻辑。
- **共享运行时**：提供图执行（graph replay）、优化内核（optimized kernels）、内存与缓存管理、量化路径、通信与并行执行等通用服务。

这一边界使得同一适配器可运行在不同设备、批量大小和并行配置上，无需修改模型路径。

### 2.2 优化方法

### 内核融合

- 实现了自定义 AdaRMSNorm、融合残差加 RMSNorm 内核。
- π 0.5 中：Q/K/V 投影合并为单个 GEMM，MLP gate/up 投影合并，GeGLU/SwiGLU 激活与乘法融合。
- MiniCPM-Robot 的 Qwen3.5 混合骨干：单一 Triton 内核实现 RMSNorm + SiLU gate，另一内核实现深度可分离因果 Conv1d、SiLU、Q/K/V 拆分。

### 图重放（Graph Replay）

- 迭代式策略常重复相同形状与控制流，仅少量状态变化。
- π 0.5：视觉-语言前缀在十个 Euler 步骤间固定，KV 张量、注意力元数据、索引数组等只计算一次。
- 在 CUDA Graph 桶中捕获完整去噪循环，新观察到来时才失效前缀状态并重新预测。

### 基于性能剖析的算子选择

- 不对 Layer 绑定单一内核实现，而是根据矩阵形状、数据类型、加速器型号和执行配置动态选择。
- 例：π 0.5 动作专家（50-token query，head dim 256）使用 FlashInfer FA2 prefill 优于自动选择的 FA3 路径。

### 量化

- 离线 RTN（round-to-nearest）量化，支持 W4A16、W8A16、W8A8、W4A8。
- 报告中的主要结果使用 BF16，不依赖量化路径。

### 2.3 并行执行

支持三种并行策略：

- **数据并行（DP）**：独立请求分配到多个模型 runner，无状态交换，适用于 π 0.5。
- **张量并行（TP）**：QKV 与 MLP gate/up 投影列并行，注意力头跨 rank 划分，输出投影行并行 + all-reduce。
- **CFG 并行**：条件与无条件分支独立运行，去噪步骤后通过 all-gather 交换速度场。
- Cosmos3 在八 GPU 上使用 2（CFG）× 4（TP）网格，CFG all-gather 配对后进行 guidance：
  \[
  v_{guided} = v_{uncond} + \gamma (v_{cond} - v_{uncond})
  \]

### 2.4 控制时间 Roofline

引入新分析框架，将推理延迟与环境执行时间关联：

\[
L_{overlap} = \max(L_{inference}, L_{env})
\]

- \( X = L_{env} / L_{inference} \)：推理速率相对环境执行速率。
- \( Y = L_{env} / L_{control} \)：控制速率相对环境执行上限。
- 顺序循环：\( Y_{seq} = X / (1 + X) \)
- 理想重叠：\( Y_{roof} = \min(X, 1) \)

该 Roofline 帮助区分**推理受限**（X < 1，降低推理延迟直接提升控制率）与**环境受限**（X > 1，加速推理仅产生时序余量，可换取更大的模型或更低成本的设备）。

## 6. 主要结论与发现

1. **统一推理引擎可行且高效**：相对于官方实现，PhyAI 在 11 对测量中全部更快，加速比 1.40×–4.65×。
2. **不同模型需要不同执行策略**：
   - π 0.5 在 batch=1 时动作专家占 8.8% FLOPs 却占 57.2% 延迟，是低批量瓶颈；batch=32 时占比降至 13.5%。
   - GR00T 在 batch=8 就达到 batch=32 吞吐量的 92.2%，瓶颈从 Action Head 切换至 Backbone。
   - Cosmos3 生成阶段主导，batch 1→16 吞吐量仅提升 14.3%，适合请求内并行（TP/CFG）而非增加批大小。
3. **控制时间 Roofline 有效区分约束类型**：
   - π 0.5 在四个 LIBERO 套件上属于环境受限（X > 1），加速推理不直接提升控制率。
   - Cosmos3 属于推理受限，降低推理延迟可提升控制率。
4. **RL 训练可从推理加速受益**：预测阶段占 RL step 的 15.9%（实际），模拟显示在预测占比 40–50% 时端到端可加速 1.32×–1.44×。
5. **适配器接口扩展性极强**：一天之内成功添加 MiniCPM-Robot 支持。

## 7. 优点

- **统一运行时设计**：模型语义与执行策略分离是优雅的架构创新，兼顾了模型差异性与部署灵活性。
- **覆盖生命周期**：从评估、训练 rollout、共享服务到机载部署，同一代码库贯穿始终。
- **控制时间 Roofline**：首次将推理加速与控制率增长之间的关系形式化，提供明确的优化停止点。
- **多维性能剖析**：阶段/批量/FLOPs/延迟分解清晰，为系统优化提供了数据支撑。
- **研究透明性**：承认专用运行时的优势，不宣称全面的统治地位，表述客观。
- **可复现性**：代码与基准测试开源，并附带完整的实验配置与复现协议。
- **社区友好**：作者列表中有数十位研究者，论文表述为“共享基础设施”追求。

## 8. 不足与局限

**实验覆盖局限**：

- 与 FlashRT 等专用运行时对比不完全，部分设备配置缺失。
- 没有在真实机器人上验证闭环控制，全部在模拟器（LIBERO、RoboTwin）中评估。
- 缺少量化（INT4/INT8/FP8）路径下的延迟对比，主要结论基于 BF16。

**方法局限**：

- 控制时间 Roofline 的简化假设：忽略传输、排队、控制器开销，低估真实系统的复杂度。
- RL rollout 的加速结论基于模拟而非实测端到端，实际收益可能低于预测。

**部署风险**：

- 统一运行时设计的收益依赖适配器生态的扩展，目前支持的模型数量有限。
- 物理 AI 的广泛部署仍需解决车间级 MaaS（模型即服务）的网络延迟、队列延迟与服务可靠性问题，文中仅提出方向未实证。

**公平性考量**：

- 官方实现的优化程度参差不齐，部分加速比可能包含了对朴素实现的提升空间，而非同一优化水平下的比较，需要辩证看待。
- 批量分析部分未充分报告批次间的方差与尾部延迟。
