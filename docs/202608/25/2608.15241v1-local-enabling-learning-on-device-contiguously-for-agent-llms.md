## 摘要
设备端大语言模型智能体在本地硬件上与用户反复交互，产生的私有轨迹虽对自适应有价值，但不应发送给远程训练器。理想情况下，此类智能体应能连续学习——从每次交互中适应，而不中断或挂起面向用户的推理——然而现有推理运行时假定权重稳定，现有强化学习系统假定资源分离，两者均无法支持这种连续性。我们提出LOCAL，首个支持智能体大语言模型在单GPU上实现设备端连续学习的运行时。关键洞察在于：GPU调度、适配器版本管理和KV缓存有效性无法由独立子系统处理：适配器更新会使旧版本的缓存KV张量失效，而缓存保留又会影响训练可用内存。LOCAL将适配器版本、任务优先级和缓存状态暴露给三个协作组件——协作调度器、版本感知的KV缓存管理器和多智能体模型运行时——它们共享这些状态，以保持调度、执行和缓存维护的相互一致性。在单块24 GB GPU上使用7B级模型时，相较于FIFO，LOCAL将前台队列等待p95降低3.1倍；相较于不可抢占训练，p95首Token时延（TTFT）降低1.55倍；发布后首次命中预填充p99降低25.6%，跨智能体TTFT p99降低21.9%；并在紧凑KV预算下保持后台学习持续推进。

## Abstract
On-device LLM agents interact repeatedly with users on local hardware, producing private traces that are valuable for adaptation but should not be sent to a remote trainer. Ideally, such agents would learn contiguously---adapting from every interaction without pausing or suspending user-facing inference---yet existing inference runtimes assume stable weights and existing RL systems assume separated resources, so neither can support this continuity. We present LOCAL, the first single-GPU runtime that enables contiguous on-device learning for LLM agents. The key insight is that GPU scheduling, adapter version management, and KV-cache validity cannot be handled by independent subsystems: adapter updates invalidate cached KV tensors from older versions, and cache retention affects the memory available for training. LOCAL makes adapter version, task priority, and cache state visible to three cooperating components---a cooperative scheduler, a version-aware KV-cache manager, and a multi-agent model runtime---that share this state to keep scheduling, execution, and cache maintenance mutually consistent. On a single 24 GB GPU with 7B-class models, LOCAL lowers foreground queue-wait p95 by 3.1x over FIFO, lowers p95 time-to-first-token (TTFT) by 1.55x versus non-preemptible training, cuts post-publish first-hit prefill p99 by 25.6% and cross-agent TTFT p99 by 21.9%, and keeps background learning progressing under tight KV budgets.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：本地部署 LLM 已成为现实，隐私是主要驱动力。设备端 LLM 智能体（如 ReAct 式智能体）会与用户进行多轮交互，产生包含用户修正、偏好、工具调用结果等私有轨迹。这些轨迹对个性化自适应非常有价值，但发送到远程训练器会破坏本地部署的隐私初衷。因此理想方案是在设备端利用这些轨迹进行本地持续学习。
- **核心矛盾**：
  - **现有推理运行时**（vLLM、SGLang、MLC-LLM、ExecuTorch 等）都建立在“权重稳定”假设上：服务期间模型参数不变，KV 缓存有效性只取决于 token 前缀是否匹配。一旦在线训练循环更新适配器权重，旧版本适配器产生的 KV 张量就不再有效，若继续复用会静默混合不同适配器状态的隐状态。
  - **现有 RL 训练系统**（HybridFlow、OpenRLHF、ReaL 等）假设“资源分离”：rollout、reward、reference、training 可放在不同加速器上优化吞吐。但单个消费级 GPU 需要同时响应用户、运行 judge 推理、训练适配器、维护 KV 状态，不存在独立集群来吸收负载。
- **关键挑战**（单 GPU 上的三大耦合问题）：
  1. **前台-后台争用**：前台推理、judge 推理、训练步骤、缓存刷新争抢同一 GPU。训练无法在任意点廉价抢占，安全中断点只在 mini-step 或 optimizer commit 之间。
  2. **适配器演化下的 KV 缓存复用**：适配器版本更新后，旧版本产生的 KV 缓存即使 token 前缀相同也不能复用。全部失效会破坏长前缀复用，选择性失效需要细粒度策略。
  3. **受限 VRAM 下的内存管理**：24 GB GPU 上 7B 模型权重约占 13.5 GB，剩余内存需容纳 KV 缓存、适配器参数、judge/replay 批次、训练激活、梯度、优化器状态和检查点暂存，且对象生命周期各不相同。
- **论文含义**：首次提出单 GPU 上支持 LLM 智能体连续学习的运行时系统，使设备端智能体能在不中断用户推理的情况下边交互边学习，为隐私保护的自适应智能体部署奠定基础。

## 2. 方法论：核心思想、关键技术细节

### 2.1 核心思想
> **关键洞察**：前台延迟、适配器发布和 KV 缓存有效性不能由独立子系统管理。适配器更新会失效旧版本 KV，缓存保留影响训练内存。因此 LOCAL 将**适配器版本、任务优先级、缓存有效性**作为一等运行时状态，暴露给三个互相协作的组件，使调度、执行和缓存维护保持相互一致。

### 2.2 三大核心组件

#### (1) 协作调度器（Cooperative Scheduler）
- **统一任务模型**：所有 GPU 绑定操作抽象为任务，元数据包括：任务类别 `c_x`、硬优先级 `p_x`、所需适配器状态 `a_x`、预计执行时长 `t̂(x)`、预计峰值内存 `m̂(x)`、最长不让步区间 `ŷ(x)`、效用 `u(x)`。时长估计通过在线 EMA 校准。
- **严格前台优先级**：当前台推理队列非空时，不启动新后台任务（judge、训练、stale-coverage prefill）。
- **协作式中断训练**：训练任务只在安全边界（如 mini-step 之间、optimizer commit 前）响应中断信号。前台请求等待时间被限制到“距下一个安全边界的剩余时间”，而非整个训练流程时长。被中断的训练不会暴露部分适配器状态，前台仍绑定最后已提交的 serving 适配器。
- **时隙感知的后台准入**：后台任务 `x` 只有在 `m̂(x) + M_reserve ≤ M_free` 且 `ŷ(x) + δ ≤ W_bg`（工具截止时间 `D_tool` 场景下还需 `t̂(x)+δ ≤ R`）时被允许执行。在可准入任务中选择效用最高的。
- **内存背压集中处理**：调度器统一决定是否允许 cross-agent pre-prefill、是否启动训练块、是否优先 judge 而非训练等，避免策略分散。

#### (2) 版本感知 KV 缓存管理器（Version-Aware KV Cache Manager）
- **Agent 作用域 KV 身份**：KV 条目可复用仅当**有效性键**匹配请求：
  `κ = (token span, context namespace, adapter, adapter version)`
  不再仅依赖 token 前缀相等。agent 身份作为溯源元数据而非硬键，若 agent 间共享相同序列化前缀、命名空间、适配器和版本，则可共享 KV。
- **热前缀统计**：将 KV 热度解耦为前缀热度 `H_P(p)` 和适配器热度 `H_A(v)`，两者均为衰减统计量。综合 KV 热度为：
  `H_KV(e) = (ε + H_P(p)) * (ε + H_A(v)) * (1 + α_L * min(L_e, L_max)/L_max)`
  保留优先级 `Π_keep(e) = H_KV(e) * C_recompute(e)/max(1, B_e)`，用于驱逐排序。
- **调度器可见的过期覆盖预填充（Stale-Coverage Prefill）**：训练产生新适配器版本后，先将适配器置为 staged 状态（旧版本继续服务），KV 管理器根据热前缀统计生成预填充块，作为普通后台任务提交给调度器。预填充只在前台空闲窗口执行，发布后首次请求的热路径 KV 已被预先算好，降低后发布 TTFT。
- **优先级保留与卸载**：根据 `Π_keep` 升序排序，低热度相对高内存成本的条目先卸载；活跃适配器权重和当前请求的 KV 状态不可卸载。

#### (3) 多智能体模型运行时（Multi-Agent Model Runtime）
- **跨智能体预填充（Cross-Agent Pre-Prefill，推测性）**：基于多智能体通信状态（如下游 agent 即将消费的共享上下文），向 KV 管理器提出预填充任务提议。提议包含目标 agent、命名空间、适配器、版本、前缀跨度、预计 token 数和置信度。预期需求信号：
  `D_ma(c) = ρ_c * (1 + β_s * log(1+s_c)) * min(Δc, M_max)/M_max`
  最终优先级 `Π_xpre(c) = D_ma(c) * H_KV(e_c) * C_prefill(e_c)`。该机制不会绕过调度器，也不会削弱版本化 KV 正确性。
- **内存压力卸载请求**：训练等后台任务提交前，运行时对比预计内存需求与调度器可用余量。若会消耗前台储备，则先向 KV 管理器发出卸载请求，由缓存管理器按策略选择卸载对象。
- **集成方式**：所有 GPU 工作仍经协作调度器，所有适配器更新经适配器管理器，所有可复用 KV 覆盖经版本感知 KV 管理器。单 agent 部署时 cross-agent pre-prefill 路径自然消失。

## 6. 主要结论与发现

- **协作调度显著**保护前台交互：
  - Foreground-first 相比 FIFO，队列等待 p95 降低 **3.1×**、p99 降低 **3.4×**，同时完成 34 次训练提交和 34 次适配器发布；相比 round-robin，p99 降低 2.1×，训练提交多 1.6 倍。
- **协作中断训练**有效降低前台尾延迟：
  - 可抢占训练使 p95 队列等待从 4.140s 降至 2.676s，p95 TTFT 从 4.247s 降至 2.749s（即 **1.55×** 改善），累计训练阻塞时间降低 **2.6×**；代价是训练吞吐降低 21.6%（346.8→271.8 steps/h）。
- **vLLM full-LoRA sleep/train/wake 路径不适合交互式本地学习**：
  - 其中位窗口约 12.1s（sleep ~1.0s, train ~9.7s, wake ~1.5s）。LOCAL 的 p95 队列等待比该路径低 **5.9×（foreground-first）、12.8×（round-robin）、6.3×（FIFO）**。
- **stale-coverage prefill** 有效降低适配器发布后的首次命中延迟：
  - 首命中 prefill p99 降低 **25.6%**，p50 缓存覆盖率从 0 升至 0.210，说明收益来自物化的热前缀 KV。
- **cross-agent pre-prefill** 在 judge 和训练同时运行时降低前台 TTFT：
  - 平均降低 38.0%、p95 降低 12.8%、p99 降低 **21.9%**，仅增加 43 个 prefill 任务和 5.184s GPU 时间，对前台阻塞贡献仅 0.018s。
- **内存压力下可继续运行**：
  - 在 512~1280 KV page 配置下均无 OOM，峰值内存 21.6~23.5 GB，仍完成 31~35 次训练提交和 146~283 次 stale-coverage prefill 事件。KV page 预算从 512 提升至 1024 可使队列 p95 降低 1.5×，显示内存配置直接影响调度准入和前台延迟。

## 7. 优点

- **问题定位精准**：清晰识别出现有系统“稳定权重”和“资源分离”两大假设与设备端连续学习的不兼容性，并给出形式化失效场景（KV 缓存跨适配器版本复用导致隐状态混合）。
- **系统设计精巧且一体化**：将调度、KV 缓存、多智能体运行时三者通过共享状态解耦又协同，避免了独立子系统互相冲突。版本感知 KV 缓存键设计（token span + namespace + adapter + version）简洁且正确性明确。
- **协作式中断而非强制抢占**：不依赖于内核级抢占，尊重 GPU 执行安全边界，设计务实。
- **前瞻性性能优化**：stale-coverage prefill 和 cross-agent pre-prefill 都是将原本前台昂贵的预填充移到后台空闲窗口，且不绕过调度器，避免优先级倒挂。
- **实验设计细致**：在不同调度策略、预填充开关、内存配置上均有对比；直接与 vLLM 的 full-LoRA 路径对比，彰显系统级差异；对队列等待来源进行归因分析，提升了结果可解释性。

## 8. 不足与局限

- **评估范围有限**：仅单一 GPU（RTX 3090 级）、单一模型（xLAM-7b-r）、单一 benchmark（tau-bench retail），未验证其他模型规模、其他消费级 GPU（如 8/16 GB）、其他 agent 任务或更长会话。
- **统计可信度不足**：未报告多次运行方差、置信区间或显著性检验；单次 24-task 运行的数值可能受随机性影响。
- **学习质量未验证**：未展示训练适配器后 tau-bench 成功率或奖励是否提升，系统只证明了“能训练”，未证明“学得好”。
- **基线公平性问题**：与 vLLM full-LoRA 对比时使用了不同的推理引擎（FlashInfer vs vLLM），可能混入引擎本身的性能差异而非 sleep/train/wake 机制差异。
- **训练成本未深入分析**：由于 LoRA rank=4 且仅单个 GPU，未评估更大 rank、更长上下文、多适配器并发训练等更实际场景下的内存与调度复杂度。
- **测试流程简化**：judge 输出预算固定 512 token，未测试更长 judge 输出对延迟的影响；也未考虑多用户并发或设备热降频等现实因素。
- **工程复杂度**：24k+ 行 Python 实现，实际产品化需考虑与主流推理框架的集成成本。
