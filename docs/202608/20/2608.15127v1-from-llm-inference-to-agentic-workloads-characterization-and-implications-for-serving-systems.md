## 摘要
智能体应用正在将AI服务从孤立的模型推理转变为长时间运行的工作负载，其中LLM协调工具、环境和持久状态。然而，这些工作负载的系统行为——包括延迟、成本和瓶颈的出现位置——仍然缺乏充分刻画，导致服务系统不得不依赖为传统推理构建的假设。我们提出AgentSysBench，这是一个基准测试套件与测量工具包，包含十个具有代表性的智能体应用和统一的系统级探针。通过受控部署和生产环境追踪，我们识别出六个将智能体工作负载与传统LLM服务区分开来的特性：(1) 执行是重量级且有状态的，在10个应用中，非LLM组件在5个应用中主导延迟，沙箱工作集内存每个会话峰值达到28 GB；(2) 应用由具有异构资源亲和性的组件构成——GPU受限的推理、内存受限的检索、CPU受限的沙箱——其任务延迟差异可达32倍；(3) 瓶颈随请求、模型和部署而变化；(4) 生产会话在活跃步骤之间会保持状态空闲数分钟到数小时；(5) 控制平面开销——辅助LLM调用以及工具模式和观察带来的上下文开销——挤占了有效的计算和上下文；(6) 来自三个应用的生产追踪显示，搜索查询和网页获取中存在大量的跨请求冗余，这暴露了巨大的缓存机会。四项设计探索表明这些发现是可操作的：任务感知服务减少29%-40%的延迟，通信感知放置减少高达4.5倍延迟，状态卸载减少4.6倍内存使用，工具结果缓存消除了35.2%的冗余搜索调用并节省了19.3%的总搜索延迟。

## Abstract
Agentic applications are shifting AI serving from isolated model inference to long-running workloads in which LLMs coordinate tools, environments, and persistent state. However, the system behavior of these workloads---where latency, cost, and bottlenecks arise---remains poorly characterized, leaving serving systems to rely on assumptions built for conventional inference. We present AgentSysBench, a benchmark suite and measurement toolkit with ten representative agentic applications and unified systems-level instrumentation. Across controlled deployments and production traces, we identify six properties that distinguish agentic workloads from conventional LLM serving: (1) execution is heavyweight and stateful, with non-LLM components dominating latency in 5 of 10 applications and sandbox working-set memory peaking at 28 GB per session; (2) applications compose components with heterogeneous resource affinity---GPU-bound inference, memory-bound retrieval, CPU-bound sandboxes---whose task latencies diverge by up to 32x; (3) bottlenecks shift across requests, models, and deployments; (4) production sessions hold state idle for minutes to hours between active steps; (5) a control-plane tax---auxiliary LLM calls and context overhead from tool schemas and observations---crowds out productive compute and context; and (6) production traces from three applications reveal heavy cross-request redundancy in search queries and web fetches, exposing a large caching opportunity. Four design explorations demonstrate that these findings are actionable: task-aware serving reduces latency by 29--40%, communication-aware placement by up to 4.5x, state offloading reduces memory usage by 4.6x, and tool-result caching removes 35.2% of redundant search calls and saves 19.3% of aggregate search latency.

## 1. 核心问题与整体含义

- **背景**：AI serving 正从“单次、无状态的 LLM 推理”转向“长时、有状态、工具调用的智能体（agentic）工作负载”。一个用户请求可能触发检索、代码执行、浏览器交互、API 调用和数十次模型调用。
- **核心问题**：现有服务系统仍然基于传统 LLM 推理的假设（如模型推理为中心、无状态请求、短时执行）来设计，但对智能体工作负载的延迟来源、成本构成、瓶颈位置、状态增长等系统行为缺乏系统性刻画。
- **整体含义**：论文指出，模型推理不再是唯一成本中心；工具、环境、长时会话状态、通信和跨请求冗余同样重要。服务系统需要从“纯模型优化”转向“模型-工具-状态-通信协同管理”的新范式，否则会留下大量未被利用的效率空间。

## 2. 方法论

- **统一形式化框架**：
  - 将智能体工作负载定义为四个因素：$W = \langle R, T, M, O \rangle$，分别对应请求分布、工具集/环境、模型选择、编排结构。
  - 将服务系统定义为三个因素：$S = \langle H, C, A \rangle$，分别对应硬件资源、组件服务机制、部署架构。
  - 观测到的系统行为为 $Y = \Phi(W, S)$，即同一工作负载在不同服务配置下会呈现完全不同的瓶颈特征。
- **提出 AgentSysBench**：一个包含基准应用集合、模块化服务栈和统一测量工具的开源套件，满足四个设计需求：
  - R1（工作负载代表性）：选择十个跨域应用，覆盖不同请求类型、工具环境、模型与编排结构。
  - R2（服务系统可控性）：以 Docker 容器化方式隔离硬件分配、组件机制和部署拓扑，支持本地调用与远程服务的切换。
  - R3（统一组件级插桩）：对 LLM 调用、工具调用、状态操作记录统一格式的 trace（延迟、资源、token、成本等），结合 cAdvisor、DCGM Exporter、Prometheus 采集资源时间序列。
  - R4（生产轨迹互补）：额外收集三个生产系统的 24 小时 trace，揭示受控实验无法出现的请求到达、空闲期和跨请求冗余。
- **四个设计探索**（验证发现可操作性的概念验证）：
  - 任务感知服务（task-disaggregated serving）：将不同逻辑任务拆分为独立服务，减少 HOL 阻塞和相互干扰。
  - 通信感知放置（communication-aware placement）：将高通信组件（如 embedding 与向量库）共置，减少网络传输。
  - 状态卸载（state offloading）：在会话空闲（如等待 LLM 规划）时卸载沙箱状态。
  - 工具结果缓存（tool-result caching）：跨会话缓存搜索查询结果和 URL 抓取内容。

## 3. 实验设计

- **受控实验**：
  - 覆盖 10 个应用：RAG、HuggingGPT、DeepResearch、Mini-SWE、Codex、WebAgent、GUIAgent、Claude Code、Openclaw、Pi-AutoR。

  - 测量规模：4,641 个 benchmark 请求、64,924 次 LLM 调用、118,274 次工具调用。
  - 针对瓶颈转移的实验：分别改变请求类型/负载大小（R）、工具集（T）、模型组合（M）、编排结构（O），以及硬件资源（H）、组件服务机制（C）、部署架构（A）。
  - 针对性能干扰的实验：HOL blocking（embedding 服务）、co-batching interference（长上下文请求干扰短请求 TPOT）、共享资源竞争（并发沙箱）。
- **生产 trace 分析**：
  - 三个应用：编码智能体（35,037 会话）、基于搜索的 QA 智能体（141,376 会话）、Openclaw-like 智能体（2,386 会话）。

- **对比基线**：
  - 任务感知：component-sharing baseline vs task-disaggregated。
  - 通信放置：co-none（各组件独享服务器）、co-vdb-embed（向量库+embedding 共置）、co-all（全部共置）。
  - 状态卸载：有/无 offload。
  - 工具缓存：不同 TTL（30s 到 24h），记录缓存命中率与节省延迟。

## 4. 资源与算力

- 默认部署：除 RAG 外，每个工作流使用一台高端 NVIDIA GPU 服务器，各组件以 Docker 容器运行并通过共享内存虚拟网络通信。
- RAG 使用一台 x86_64 服务器，配备 8× NVIDIA 4090D GPU。

## 6. 主要结论与发现

- **受控实验发现（前三条）**：
  1. **重量级、有状态、非 LLM 主导**：10 个应用中有一半的非 LLM 组件（沙箱、搜索、向量库、实验环境）主导端到端延迟；沙箱工作集峰值达 28 GB/会话；单会话 token 消耗可达数十万至百万级；数据 I/O 可达数十 MB。
  2. **跨栈异构性**：同一应用内不同任务延迟相差最高 32×（如 Embed-Doc 比 Embed-Query 慢 32×）；LLM 调用在同一执行内可波动 30×；异构任务共服务会造成 HOL、共批干扰和共享资源竞争。
  3. **瓶颈动态转移**：请求类型、输入大小、工具集、模型选择、编排结构、硬件分配、服务机制和部署拓扑的变化都会移动瓶颈位置，静态画像和固定资源分配无法适配。
- **生产 trace 发现（后三条）**：
  4. **长时空闲但存活**：编码智能体会话中位执行时间仅占生命周期的 20%，空闲间隔从数秒到数小时，此时仍持有沙箱、KV cache、会话状态。
  5. **控制平面税**：系统提示、工具 schema、历史观察和辅助调用占用大部分上下文；上下文压缩事件平均耗时 156 秒；固定 TTL 的 prefix cache 导致 59.4% 的会话发生缓存驱逐，贡献 31.5% 的货币成本。
  6. **跨请求冗余**：27% 的重复搜索查询贡献了 67.3% 的搜索调用；24% 的重复 URL 贡献了 64% 的抓取调用，存在巨大的缓存机会。
- **优化验证**：
  - 任务感知服务：延迟降低 29–40%。
  - 通信感知放置：相比全分布式，最高 4.5× 加速。
  - 状态卸载：平均内存降低 4.6×，峰值降低 2.1×，延迟仅增加 0.5% 以内。
  - 工具结果缓存：10 分钟 TTL 下消除 35.2% 冗余搜索调用，节省 19.3% 聚合搜索延迟；URL 缓存节省 16.5% 抓取延迟。

## 7. 优点

- **统一的形式化框架**：用 $W$ 和 $S$ 明确区分工作负载与服务系统，为归因和泛化提供坚实基础。
- **模块化、可扩展的基准套件**：支持新增应用，复用统一的 trace 格式和部署框架，降低了后续研究的进入门槛。
- **受控实验与生产 trace 互补**：既能隔离变量，又能捕捉生产环境独有的空闲、冗余、控制面开销等行为，结论更全面。
- **发现到优化闭环**：不是停留在测量，而是将每条关键发现转化为可量化的优化设计，证明其实际收益。
- **测量工具标准化**：统一 instrumentation、资源监控、分析库和可视化，让不同应用、不同部署之间的结果可比较。
- **开源承诺**：促进社区后续建设。

## 8. 不足与局限

- **应用覆盖有限**：十个应用虽具代表性，但无法覆盖所有智能体类型（如多智能体协作、语音/视频等模态），结论可能存在域偏差。
- **黑盒应用依赖代理插桩**：Codex、GUIAgent、Claude Code、Openclaw、Pi-AutoR 等使用 LLM/tool 代理或沙箱 hook，可能引入额外开销或 trace 精度损失。
- **生产 trace 代表性有限**：仅三个应用、单日数据、单一运营环境；压缩率、缓存失效等数值可能随平台不同而变化。
