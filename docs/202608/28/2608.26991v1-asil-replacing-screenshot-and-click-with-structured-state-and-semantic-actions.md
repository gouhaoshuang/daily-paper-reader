## 摘要
强大的代码智能体可以执行脚本、调用工具和管理文件，然而许多重要应用仍然主要通过图形用户界面进行访问。我们认为，对于操作软件的智能体而言，截图-点击是一种低效的接口：截图的状态不完整，GUI动作脆弱、语义弱，并且与长程规划匹配不佳。我们提出ASIL（智能体-软件交互层，Agent-Software Interaction Layer），这是一种智能体原生接口，通过结构化JSON观察和可执行代码的语义动作来暴露软件功能，并通过每个应用可行的最深访问路径实现。我们在15个应用和一个包含300个单应用任务和80个多应用任务的基准测试上实例化ASIL。使用闭源模型时，ASIL的成功率超过80%，同时每个任务执行的动作少于五个。在修复后的运行时和50步截图预算下，相同的任务在截图-点击控制下的严格成功率分别仅为6.6和26.6，而在一个更简单的、与OSWorld可比较的范围内则上升到15.0和53.3。在与匹配任务的应用原生接口对比中，ASIL在严格成功率上超过LibreOffice的UNO API 28-38个百分点，但仅与draw.io的MCP内容契约持平。这种结构化模态也适合训练：小规模SFT（监督微调）将Qwen3.5-2B从58.0提升到72.1，将Qwen3.5-9B从66.6提升到80.4，而资源受限的在策略强化学习（on-policy RL）进一步将它们提升到74.4和82.2。

## Abstract
Powerful code agents can execute scripts, call tools, and manage files, yet many important applications remain accessible primarily through graphical user interfaces. We argue that screenshot-and-click is an inefficient interface for software-operating agents: screenshots are state-incomplete, and GUI actions are brittle, semantically weak, and poorly matched to long-horizon planning. We introduce ASIL (Agent-Software Interaction Layer), an agent-native interface that exposes software through structured JSON observations and code-executable semantic actions, realized through the deepest feasible access path for each application. We instantiate ASIL across 15 applications and a benchmark of 300 single-application and 80 multi-application tasks. ASIL reaches above 80 with closed models while executing fewer than five actions per task. Under a repaired runtime and a 50-step screenshot budget, the same tasks yield 6.6 and 26.6 strict success under screenshot-and-click control, rising to 15.0 and 53.3 on an easier OSWorld-comparable band. Against application-native interfaces on matched tasks, ASIL exceeds LibreOffice's UNO API by 28-38 strict points but only matches draw.io's MCP content contract. The structured modality also suits training: small-scale SFT raises Qwen3.5-2B from 58.0 to 72.1 and Qwen3.5-9B from 66.6 to 80.4, and resource-limited on-policy RL further raises them to 74.4 and 82.2.

## 1. 核心问题与整体含义（研究动机和背景）

- **研究背景**：代码智能体已能在终端、IDE、CI/CD 中执行脚本、调用工具和操作代码仓库，但许多重要应用（创意工具、办公套件、桌面工具等）仍主要通过 GUI 暴露功能，形成“最后一公里”的障碍。
- **核心问题**：现有计算机使用智能体（computer-use agent）采用**截图-点击（screenshot-and-click）**模式模拟人类操作。然而这种接口存在双重错配：
  - **观察侧**：截图只是软件状态的可见投影，缺少隐藏面板、后台进程、文档结构和内部元数据，迫使模型反复在呈现层上进行多模态推理。
  - **动作侧**：GUI 事件是坐标敏感的底层动作，一个语义意图需要展开为冗长脆弱的动作序列，易受布局/主题变化影响，错误累积严重。
- **论文主张**：智能体操作软件应采用智能体原生的交互接口，而非人机界面。核心问题不是“如何让模型更会看屏幕”，而是“软件智能体应使用什么样的观察和动作接口”。

## 2. 论文提出的方法论

### 2.1 核心思想：ASIL（Agent-Software Interaction Layer）

- 用**结构化 JSON 观察**替代截图，用**可执行代码的语义动作**替代 GUI 事件。
- 形式化定义：将截图-点击接口 $(Pix, M_k)$ 替换为 $(\Phi, A)$，即：
  - $o_t = \Phi(s_t)$（结构化观察）
  - $a_t \sim \pi_\theta(\cdot | o_t)$（语义动作策略）
  - $s_{t+1} = T(s_t, a_t)$（状态转移）

### 2.2 四个设计原则

1. **完整性（Completeness）**：暴露可见界面之外的软件状态。
2. **语义性（Semanticity）**：动作与软件的有意义操作对齐，而非 GUI 机制。
3. **稳定性（Stability）**：标识符和目标在呈现变化下保持有效。
4. **可组合性（Composability）**：通过少量高层动作表达复杂任务。

### 2.3 实现途径：ASILization 流水线

- 为每个应用找出“最深可行访问路径”（deepest feasible access path），即最接近软件真实状态转移系统且实际可运行、可评估的接口。
- 三种实现模式（同一协议的不同实现路径，而非不同的智能体类型）：
  - **文件驱动**（如 SVG、ODF、notebook）：解析并修改结构化文件。
  - **原生脚本驱动**（如 Blender Python）：在应用内部生成/执行脚本。
  - **服务/API 驱动**（如 REST、WebSocket）：调用服务端点。
- 15 个实现中：6 个文件驱动、4 个原生脚本、5 个服务/API。
- 新应用接入流程为半自动化：自动化部分（接口发现、配置生成、验证门）由模型辅助，人工负责任务/评估器设计、应用桥接和 GUI 同步。

### 2.4 协议对象与闭环

- **Observation 对象**：包含元数据、应用状态、交互元素、环境上下文、导航结构、文本摘要六类字段。
- **Action 对象**：包含动作类型（如 `set_value`、`invoke_function`、`modify_file`、`api_call`、`navigate`、`batch`）、目标（target）和参数（params）。
- **闭环**：观察→规划→执行→验证→记忆→重试，均在同一个 JSON 契约下进行。

### 2.5 训练协议

- ASIL 轨迹可序列化、验证和复用，同时服务于 SFT 和 RL：
  - **SFT**：使用已知正确动作的轨迹（SFT-v0）和 GPT-5.4 验证轨迹（agentic-guided-v2）构造训练集。
  - **RL**：使用评估器提供奖励的在线策略 GRPO 式更新，通过外部 ASIL AgentService 进行 rollout。
  - 奖励信号与推理时评估使用同一个评估器，训练信号与评估信号一致。

## 6. 主要结论与发现

1. **接口层是主要瓶颈**：在相同任务和验证器下，ASIL 与 GUI 的差距巨大——GPT-5.4 在 380 任务上 ASIL 81.6 vs GUI 6.6（严格成功率），sonnet4.6 为 81.2 vs 26.6；即使 GUI 预算从 15 提高到 50 步，差距仍然显著。
2. **ASIL 动作更短、更稳定**：ASIL 平均每个任务执行不超过 5 个语义动作，远低于 GUI 的步数需求。
3. **ASIL 不一定超越成熟原生接口**：ASIL 超过 LibreOffice UNO（28-38 个严格点），但仅与 draw.io MCP 持平或落后（sonnet4.6 落后 30 个严格点），说明组合式贡献而非普适性优势。
4. **ASIL 是高效的训练模态**：小规模 SFT + RL 为 2B 模型带来 +14.1/+16.4 提升，为 9B 模型带来 +13.8/+15.5 提升；硬套件上 9B 的增益进一步扩大至 +17.1/+19.8。
5. **实现模式影响训练效果**：RL 在文件驱动和服务/API 模式增益明显，但原生脚本模式几乎无变化（-0.9），说明训练收益模式相关。
6. **剩余失败来自建模与覆盖而非界面**：主要是感知型任务（GIMP 真实照片编辑）、数据覆盖缺口和训练回归。

## 7. 优点

- **问题定义精准**：将 GUI 智能体失败归因于接口不匹配而非模型能力不足，提出了可操作的新接口范式。
- **方法设计完整**：从协议定义（观察/动作对象）、四个设计原则到三种实现路径，形成完整的方法体系；半自动化的 ASILization 流水线降低了扩展成本。
- **实验设计严谨且有自知之明**：同时报告 ASIL 与 GUI、与原生接口（UNO/MCP）、训练前后、不同实现模式的对比，不回避提示不对称和比较局限。
- **训练实践验证真正落地**：不只是推理接口，还证明同一模态下小模型也能通过小规模训练获得显著提升，具有实际应用价值。
- **可复现性意识强**：公开适配器库、任务定义、验证器、训练数据、checkpoints 和基线脚本，并提供 Docker 一键构建。
- **界面效果的直观展示**：如图 5 的 LibreOffice 案例——GUI 控制陷入重复粘贴字面转义字符的循环而失败，ASIL 用一条 `modify_file` 动作直接满足全部 6 个评估检查点，非常具有说服力。

## 8. 不足与局限

### 8.1 论文自述的局限

- **提示不对称**：主表对比中 ASIL 提示包含评估器派生的成功提示，GUI 提示没有，因此主表不能单独隔离接口变量。虽然修订版用无提示对比修正，但未覆盖全部 380 任务。
- **2B 模型 RL 稳定性**：Qwen3.5-2B 的 RL 在硬套件上增益仅为 +3.6，且落后于 SFT（+6.0）；所选 checkpoint 在长程任务上并未保持一致改进。
- **覆盖缺口**：完全封闭且无文件/脚本/API 访问门的应用无法使用 ASIL；15 个应用均有一个开放访问门，可推广性有限。
- **感知型任务**：GIMP 真实照片编辑等目标依赖像素级视觉语义，当前语义动作词汇无法完全覆盖（GPT-5.4 硬套件 Creative 区域平均仅 14.7，24 个任务全零完整通过）；单纯的视觉补充不能解决（44.1 vs 43.7）。

### 8.2 其他可讨论的局限

- **GUI 对比的天然困难**：GUI 侧的公平对比受限于模型本身的视觉-动作能力差异（sonnet4.6 50 步 26.6 vs GPT-5.4 6.6），两份数据的方差较大，削弱“GUI 普遍低效”结论的确定性。
- **基准难度校准不精确**：easy60 只是“结构代理”校准，论文承认不是精确难度匹配。
- **draw.io MCP 对比揭示了边界**：对 sonnet4.6，ASIL 严格成功率（25.0）比 MCP（55.0）落后 30 个点，说明在已经存在成熟原生契约的应用中，ASIL 反而可能增加额外抽象层成本。
- **LibreOffice 路径限制研究中两种 ASIL 路径结果完全一致（98.6）**，这可能是天花板效应而非路径无关性的充分证明。

## 总结

ASIL 的核心贡献在于将软件操作从“像素+动作”范式迁移到“状态+语义动作”范式，并用 380 任务基准的实证结果展示了这一转换的巨大收益。虽然存在提示不对称、感知任务覆盖不足和 2B 模型稳定性问题等局限，但其设计框架、评估方法和训练实践为后续研究提供了坚实的基准和可行路径。
