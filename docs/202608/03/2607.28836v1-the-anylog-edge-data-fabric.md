## 摘要
工业与自治系统日益依赖AI、自动化及实时协调，以便在运行数据生成时对其采取行动。然而，传统架构通常要求数据在做出决策之前先经过集中式平台。云系统在训练、报告和长期分析方面仍然有价值，但它们在关键决策路径上增加了延迟和外部依赖性，并且随着每个新站点添加更多边缘设备和数据，扩展变得越来越困难。随着智能遍布机器、站点、设施和车辆，对集中化的持续依赖将限制响应时间、弹性、可扩展性和自主操作。本文介绍了AnyLog边缘数据织网，这是一个基于代理和边缘的平台，在数据源头管理运行数据，同时将分布式数据、资产、计算资源和服务呈现为一个逻辑系统。通过其分布式元数据层、虚拟数据湖、统一命名空间、单系统映像和模型上下文协议，授权用户、应用程序、自动化服务和AI代理可以发现、查询、处理分布式资源并对其采取行动，而无需知道它们托管在何处。查询和计算在持有相关数据的代理处执行，因此只有请求和结果通过网络传输。这保留了本地所有权，减少了数据移动，支持在连接中断期间继续运行，并能从经过验证的数字孪生配置中实现可重复部署。AnyLog为分布式SQL、实时自动化、边缘AI、联邦学习和弹性决策提供了一种类似云的操作模型，没有单点故障，也不依赖集中式基础设施。

## Abstract
Industrial and autonomous systems increasingly depend on AI, automation, and real-time coordination to act on operational data as it is generated. Yet conventional architectures often require that data to pass through centralized platforms before decisions can be made. Cloud systems remain valuable for training, reporting, and long-term analytics, but they add latency and external dependencies to the critical decision path and become harder to scale as each new site adds additional edge devices and data. As intelligence spreads across machines, sites, facilities, and vehicles, continued dependence on centralization will constrain response time, resilience, scalability, and autonomous operation.   This paper presents the AnyLog Edge Data Fabric, an agent- and edge-based platform that manages operational data at its source while presenting distributed data, assets, compute resources, and services as one logical system. Through its Distributed Metadata Layer, Virtual Data Lake, Unified Namespace, Single System Image, and Model Context Protocol, authorized users, applications, automation services, and AI agents can discover, query, process, and act on distributed resources without knowing where they are hosted. Queries and computation execute at the agents holding the relevant data, so only requests and results traverse the network. This preserves local ownership, reduces data movement, supports continued operation during connectivity disruptions, and enables repeatable deployment from validated digital-twin configurations. AnyLog provides a cloud-like operating model for distributed SQL, real-time automation, Edge AI, federated learning, and resilient decision-making without a single point of failure or any dependence on centralized infrastructure.

## 一、核心问题与研究动机

- **背景问题**：工业与自主系统（自动驾驶、智能制造、智能电网等）日益依赖 AI 和实时自动化对运行数据做出即时决策。但传统架构要求数据先经过集中式云平台（传输→接入→规范化→存储）后才可供应用使用，导致：

  - 应用与 AI 操作的是物理环境的"延迟副本"而非当前状态。
- **核心矛盾**：时间敏感的处理必须靠近数据源；同时，授权应用与 AI 又必须能跨边缘站点对分布式数据做统一推理，而非局限于孤立的本地位图。
- **论文主张**：集中式系统对训练、报告、合规和长期分析仍有价值，但不应成为实时决策路径的默认通道。需要通过一种"数据不动、计算上门"的架构，将分布式边缘资源呈现为单一逻辑系统。

## 二、方法论：核心思想与技术细节

### 1. 三大设计原则
1. **将运行数据保留在产生地**；
2. **将处理移动到数据所在处**；
3. **共享元数据而非原始数据**。

### 2. 核心组件：AnyLog 代理（Agent）
- 所有代理使用同一套核心软件，可配置一种或多种角色：
  - **Operator（操作者）**：本地数据库存储数据、执行查询/过滤/聚合、执行本地访问策略；
  - **Publisher（发布者）**：资源受限设备仅采集并转发数据；
  - **Query Coordinator（查询协调器）**：接收请求，利用元数据定位相关 Operator，协调分布式执行并返回统一结果；
  - **MCP Provider**：通过模型上下文协议（MCP）向 AI 代理提供受治理的数据/工具/模式访问；
  - **Metadata Manager（元数据管理器）**：同步模式、数据位置、策略、统一命名空间关系等元数据（也可用区块链账本替代）。
- 代理可运行于工业网关、嵌入式计算机、树莓派、云实例或企业服务器。

### 3. 分布式元数据与策略层
- 元数据描述"什么数据/资产/服务存在、在哪里、如何关联、如何访问"，同步开销远小于原始数据。
- 八类策略：**节点策略**（一键部署配置）、**访问策略**（身份授权，白名单）、**表策略**（逻辑表定义与物理映射）、**统一命名空间策略**（资产层级关系）、**规则引擎策略**（本地事件响应）、**聚合策略**（压缩/时间窗聚合）、**保留与转发策略**（本地保留周期与上云策略）、**复制策略**（高可用副本）。
- 策略由持有资源的代理**本地强制执行**，无中心控制依赖。

### 4. 系统模型（形式化定义）
- 用数学符号定义了代理集合 N、角色映射 τ: N → 2^T（T = {pub, op, meta, qry}）、虚拟表 v=(c,d,t)、物理放置映射 μ、本地分片 Fn(v)。
- 逻辑表内容定义为所有参与代理分片之并：v ≡ ∪ Fn(v)。
- 分布式查询语义：Ans(q,v) = Combine({Eval(q, Fn(v)) | n ∈ S(q,v)})——各代理在本地分片上并行求值，协调器融合部分结果。

### 5. 三层虚拟化视图
- **虚拟数据湖（VDL）**：应用用标准 SQL 查询分布式数据，无需知道物理位置；
- **统一命名空间（UNS）**：以 工厂/区域/产线/单元/工位/资产/测量 等层级路径组织资产，独立于底层存储；多个命名空间可共存；
- **单系统映像（SSI）**：管理员将地理分布的代理当作一个集中式云平台管理。
- 通过 `get virtual tables` 暴露逻辑数据面，通过 `get data nodes` 暴露物理拓扑（集群 ID + 主/备端点）。

### 6. 分布式查询处理流程（五步）
1. 应用提交标准 SQL（命令行 / REST / MCP）；
2. 接收代理临时充当 Query Coordinator；
3. 协调器查分布式元数据层定位相关 Operator（或使用显式指定目标）；
4. 分发 SQL 到各代理，各代理本地并行执行过滤、聚合、检索；
5. 各代理仅返回记录或部分聚合（count/sum/min/max），协调器融合后返回统一结果。

### 7. 分布式实时视频 AI 分析
- RTSP 采集 → 本地 AI 推理 → 结构化检测结果存本地 SQL，视频段存本地对象存储（MinIO/MongoDB/S3）；
- 通过逻辑表 `video_inference_events` 和 `blob reference` 实现跨设备视频检索，无需将视频流回传云端。

### 8. 自动模式（Schema）创建与管理
- 新数据到达时，代理先对比元数据层已有表策略：匹配则复用现成模式，不匹配则自动生成新模式并发布，实现"即插即用"，无需单独集成项目。

### 9. 安全模型（白名单授权）
- 请求形式化为 x = (i, s, d, T, Δ)，策略 p = (Sp, Gp, Δp)；
- 授权条件：Allow(x) ⇔ ∃p ∈ PM，满足身份、服务、数据库、表集合、时间范围全部匹配；否则拒绝。
- 查询协调器只能协调与转发，不能覆盖资源持有者的本地授权决定；每个代理用加密身份（支持 TPM）。

## 六、主要结论与发现

- 将计算移至数据所在处，配合元数据协调，可显著减少网络数据移动（估算降低约 98.9% 的日常传输），并消除对集中式平台的实时决策依赖。
- 每个新增代理同时贡献数据、存储、计算与服务，平台容量随站点数横向扩展（Cplatform = ΣCi），而非堆积在中心网关。
- 本地自治 + 共享元数据可实现无中心依赖的持续运行：断网时织网收缩到可达子集，查询可部分满足并标注完整性；恢复后自动同步元数据。
- 自动模式生成可使新数据源"即插即用"，无需逐点集成；UNS 知识图谱可为变更管理提供跨上下文依赖可见性。
- 结合数字孪生元数据（`blockchain seed from` 命令）可快速复制部署逻辑、实现可重复部署。
- 分布式安全白名单模型将受损凭据的影响限制在已授权资源范围内。
- 联邦学习（EdgeFL）与 Byzantine 容错决策可在 AnyLog 之上作为原生应用运行，无需独立基础设施。

## 七、优点与亮点

- **架构设计清晰**：给出形式化系统模型（代理角色、虚拟表、集群分区语义），概念定义严谨。
- **"元数据共享而非数据共享"的思路**有说服力，带宽节省估算直观。
- **三层虚拟化（VDL/UNS/SSI）** 将数据、资产、基础设施的抽象分层设计，用户视角统一、复用性强。
- **务实集成**：南向支持 OPC UA、MQTT、Modbus、REST、gRPC、RTSP 等工业标准；北向支持 SQL、REST、MCP，并遵循 MOSA 模块化开放系统原则，可增量部署、保护既有投资。
- **AI 原生考量**：涵盖边缘 AI、MCP 接口、联邦学习、Byzantine 容错决策，面向下一代自主系统。
- **安全模型可扩展**：白名单授权有形式化表达，且强调"资源所有者本地执法"，符合零信任思路。
- **运维友好**：配置驱动一键部署、`query status` 诊断、超时部分结果返回、数字孪生装置复制等设计贴近实际运维需求。
