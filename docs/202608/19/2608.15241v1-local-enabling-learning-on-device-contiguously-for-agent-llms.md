## 摘要
设备上的LLM智能体与本地硬件上的用户反复交互，产生私有轨迹，这些轨迹对于适应很有价值，但不应发送到远程训练器。理想情况下，这样的智能体会连续学习——从每次交互中适应，而无需暂停或挂起面向用户的推理——然而现有的推理运行时假定权重稳定，现有的强化学习系统假定资源分离，因此两者都无法支持这种连续性。我们提出了LOCAL，这是首个支持LLM智能体在设备上连续学习的单GPU运行时。关键洞察在于，GPU调度、适配器版本管理和KV缓存有效性无法由独立的子系统处理：适配器更新会使旧版本的缓存KV张量失效，而缓存保留会影响可用于训练的内存。LOCAL使适配器版本、任务优先级和缓存状态对三个协作组件可见——协作调度器、版本感知的KV缓存管理器和多智能体模型运行时——它们共享此状态以保持调度、执行和缓存维护相互一致。在配备7B级模型的单个24 GB GPU上，LOCAL将前台队列等待p95比FIFO降低了3.1倍，将p95首令牌时间（TTFT）相比于不可抢占训练降低了1.55倍，将发布后首次命中预填充p99降低了25.6%，跨智能体TTFT p99降低了21.9%，并在紧张的KV预算下保持后台学习进展。

## Abstract
On-device LLM agents interact repeatedly with users on local hardware, producing private traces that are valuable for adaptation but should not be sent to a remote trainer. Ideally, such agents would learn contiguously---adapting from every interaction without pausing or suspending user-facing inference---yet existing inference runtimes assume stable weights and existing RL systems assume separated resources, so neither can support this continuity. We present LOCAL, the first single-GPU runtime that enables contiguous on-device learning for LLM agents. The key insight is that GPU scheduling, adapter version management, and KV-cache validity cannot be handled by independent subsystems: adapter updates invalidate cached KV tensors from older versions, and cache retention affects the memory available for training. LOCAL makes adapter version, task priority, and cache state visible to three cooperating components---a cooperative scheduler, a version-aware KV-cache manager, and a multi-agent model runtime---that share this state to keep scheduling, execution, and cache maintenance mutually consistent. On a single 24 GB GPU with 7B-class models, LOCAL lowers foreground queue-wait p95 by 3.1x over FIFO, lowers p95 time-to-first-token (TTFT) by 1.55x versus non-preemptible training, cuts post-publish first-hit prefill p99 by 25.6% and cross-agent TTFT p99 by 21.9%, and keeps background learning progressing under tight KV budgets.

## 一、核心问题与整体含义（研究动机与背景）

- **研究背景**：随着隐私意识的增强，本地部署LLM成为现实趋势（如MLC-LLM、ExecuTorch、PowerInfer等）。本地部署使私有数据（对话历史、个人偏好、工具交互）保留在用户设备上。同时，本地LLM部署正从一次性推理向交互式智能体发展，智能体需要从用户反馈中持续改进。
- **核心矛盾**：设备端LLM智能体产生大量私有交互轨迹（用户纠正、重复偏好、失败的工具调用等），这些轨迹非常适合用于个性化适应，但不应发送到远程训练器。理想情况是**连续学习**——从每次交互中适应，而不暂停或挂起用户可见的推理服务。
- **现有系统的根本假设缺陷**：
  - 推理引擎（vLLM、SGLang）假设**权重稳定**——模型参数在服务期间不变，KV缓存只要token前缀匹配就有效。适配器更新会使旧缓存失效，破坏这一假设。
  - 分布式RL系统（HybridFlow、OpenRLHF、ReaL）假设**资源分离**——部署、奖励、训练可以在不同加速器上运行。单一消费级GPU无法满足这一条件。
- **本文贡献**：提出LOCAL——首个支持设备端LLM智能体连续学习（contiguous learning）的单GPU运行时，使推理和适应共享同一模型实例而不互相中断。

## 二、方法论：核心思想、关键技术细节

### 2.1 核心洞察

- **关键洞察**：GPU调度、适配器版本管理和KV缓存有效性相互耦合，不能由独立子系统处理。
  - 适配器更新会使旧版本的缓存KV张量失效（即使token前缀相同也不能复用）；
  - 缓存保留策略直接影响可用于训练的内存空间；
  - 前台延迟、适配器发布、KV缓存有效性三者互相制约。
- **解决方案**：使适配器版本、任务优先级和缓存状态对三个协作组件共享可见，保持调度、执行和缓存维护互相一致。

### 2.2 系统架构（三个协作组件）

**（1）协作调度器（Cooperative Scheduler，§4）**
- 是唯一的GPU准入点，区分前台推理队列与后台任务队列；
- 前台推理请求保持严格优先级；后台任务（法官推理、训练、缓存刷新）仅在安全让步边界被调度；
- 用统一任务接口表示异构模型操作，元数据包括：任务类别、硬优先级、所需适配器状态、预计运行时长、预计峰值内存、最长非让步间隔和任务效用值；
- 时长估计在线校准，使用指数移动平均（EMA）；
- **协作式训练中断协议**：训练任务仅在安全边界（小步之间、优化器提交前）响应中断信号，前台等待时间被限制在一次让步边界内，而非整个训练过程；
- 后台任务准入条件：`估计内存 + 保留内存 ≤ 可用内存` 且 `最长非让步间隔 + 延迟余量 ≤ 后台窗口大小`。

**（2）版本感知的KV缓存管理器（Version-Aware KV-Cache Manager，§5）**
- 将适配器版本作为缓存键的一部分，过期覆盖在查找时被拒绝；
- **KV有效性键（validity key）**：`(token span, context namespace, adapter, adapter version)`——一个KV条目仅当其所有维度与请求匹配时才可复用；
- 维护前缀热度 `H_P(p)` 和适配器热度 `H_A(ν)` 两种衰减统计量；
- **联合KV热度分数**：`H_KV(e) = (ε + H_P(p))(ε + H_A(ν)) × (1 + 长度奖励)`——乘性组合确保热前缀不会因冷适配器被保留，反之亦然；
- **保留优先级**：`Π_keep(e) = H_KV(e) × 重建成本 / 内存占用`，低者先被驱逐；
- **过期覆盖预填充（Stale-Coverage Prefill）**：适配器训练完成后、新版本发布前，为热前缀预计算新版本下的KV，减少发布后的首次TTFT；
- 使用基数索引前缀表（radix-indexed prefix table）分离逻辑有效性与物理驻留状态。

**（3）多智能体模型运行时（Multi-Agent Model Runtime，§6）**
- 在多智能体共享一个模型实例时，保持每个智能体的身份、适配器绑定和KV来源；
- **适配器作用域失效**：一个适配器发布新版本只使其自己的KV条目过时，不影响其他适配器的KV条目；
- **跨智能体预预填充（Cross-Agent Pre-Prefill）**：利用待处理的多智能体通信结构，推测性地为共享上下文前缀预计算KV缓存；`Π_xpre(c) = D_ma(c) × H_KV(e_c) × 预填充成本`，其中 `D_ma(c)` 是来自多智能体运行时预测需求信号；
- 所有GPU工作仍必须通过协作调度器，不能绕过前台优先级。

## 六、主要结论与发现

1. **协作调度是可行的**：LOCAL在混合前台推理、法官推理、训练和缓存维护的工作负载下，将前台队列p95等待比FIFO降低3.1×、p99降低3.4×，同时完成34次适配器训练提交和发布。
2. **可中断训练是必要的取舍**：通过安全让步边界中断训练，p95 TTFT比不可中断训练降低1.55×，同时训练吞吐仅降21.6%——这对交互式本地区智能体是合理权衡。
3. **传统sleep/train/wake路径不适合交互式学习**：vLLM full-LoRA路径的秒级整块训练窗口导致前台队列p95等待比LOCAL高5.9×–12.8×。
4. **版本感知缓存显著降低更新后首次使用延迟**：过期覆盖预填充使发布后首次命中预填充p99降25.6%，缓存命中率p50从0提高到0.210。
5. **跨智能体预预填充有效**：利用多智能体通信结构推测性预填充共享上下文，使跨智能体TTFT p99降21.9%。
6. **内存压力必须对调度器可见**：KV页预算、图捕获预算、热前缀数量、预填充块大小都通过调度准入影响前台延迟，而不仅仅影响是否OOM。

## 七、方法或实验设计的亮点

1. **核心洞察深刻且实用**：准确识别出适配器版本、任务优先级、KV缓存有效性三者的耦合关系，挑战了现有推理和RL系统各自的关键假设（稳定权重、资源分离）。
2. **协作式设计取代独立子系统**：三个组件共享适配器版本、任务优先级和缓存状态，而非各管一段，实现了全局协调的调度、执行和缓存维护一致性。
3. **版本感知KV缓存契约**：将适配器身份和版本纳入KV缓存键，精确定义了“什么情况下缓存条目可复用”，从根本上避免了旧版本KV张量导致的状态混合错误。
4. **Scheduler-visible cache maintenance**：将缓存预热（stale-coverage prefill）和跨智能体预填充转化为调度器可见的后台任务，不会绕过前台优先级，保持了正确性。
5. **实用的协作中断协议**：不依赖不安全的GPU内核级抢占——而是利用小步/优化器提交等安全边界，既有理论正确性又有工程可实现性。
6. **内存压力作为调度信号**：将KV页预算、图捕获预算、热前缀数量等参数通过调度器准入影响前台延迟，提供了可调的系统设计维度。
7. **实验设计较全面**：包含调度策略对比、中断消融、与成熟系统（vLLM）对比、缓存机制消融、内存压力扫描等多个维度，且有队列归属日志分析辅助解释结果。

## 八、不足与局限

1. **硬件覆盖有限**：仅在单个24GB RTX 3090级GPU上验证，未覆盖更小显存的设备（如8GB、16GB）或非NVIDIA平台，也未测试不同GPU架构对结果的影响。
2. **模型与基准单一**：只使用xLAM-7b-r一个模型和tau-bench零售数据集，未验证其他模型规模（更小或更大）、其他benchmark（如WebArena、SWE-bench等）下的表现。
3. **未评估学习质量**：实验仅验证了机制层面的性能指标（延迟、队列等待、缓存命中率等），未评估连续学习后智能体的策略质量是否真正提升。
4. **多智能体验证不够充分**：虽然提出了跨智能体预预填充，但实验未明确展示具体多少个智能体并发、不同智能体拓扑下的效果。
5. **超参数敏感性**：热度统计半衰期、缓存管理参数（页数、热前缀数、预填充块大小）等需要调参，实验未充分探索这些参数的敏感性边界。
6. **长时间运行可靠性未知**：论文只做了24任务运行，未验证长时间、多会话运行下的数值稳定性、内存碎片化和性能退化问题。
7. **与真实用户交互的差距**：实验使用tau-bench离线重放，未涉及真实用户的交互模式和到达时间分布，一些队列属性的可能性可能被低估。
8. **公平性局限**：与vLLM的sleep/train/wake对比中，LOCAL使用自定义FlashInfer推理引擎，两组在推理引擎层面的差异可能部分解释了性能差距，而非完全归因于调度策略。
