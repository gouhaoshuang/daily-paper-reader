## 摘要
尽管前沿视觉语言模型在用户界面（UI）导航中展现出强大能力，但其高昂的推理成本阻碍了日常使用。相反，通过监督微调（SFT）或离线强化学习训练的小模型往往记忆静态轨迹，导致执行脆弱且无法从错误中恢复。为解决这些局限，我们提出一种新颖的在线强化学习框架，可直接在真实 iOS 应用上训练 UI 导航智能体。该框架将智能体解耦为两个专用组件：规划智能体和 UI 定位模型。我们依赖 LLM-as-a-Judge 提供全面的奖励信号，将用于评估中间进度的稠密步级反馈与用于整体任务完成的终端奖励相结合。为有效利用这种双重奖励结构，我们使用带有步级优势估计的近端策略优化（PPO）来优化智能体。此外，我们引入 GiGPPO，一种新颖的邻居条件价值估计方法，通过利用并发轨迹中视觉相似状态的奖励信号来提高评论家稳定性。为大规模支持这种在线训练范式，我们引入高效基础设施，可编排数百个并发虚拟 iOS 设备。在包括 UINavBench、iOSWorld 和 AndroidWorld 在内的严格基准上的评估表明，我们在线强化学习训练的智能体显著优于 SFT 和仅终端奖励 RL 基线，同时加速训练收敛。值得注意的是，我们的 8B RL 智能体在向 Android 环境的分布外泛化上相比 SFT 基线取得近七倍提升，同时在真实 iOS 应用上优于 Gemini-3.5-Flash 并与 Gemini-3.1-Pro 持平。

## Abstract
While frontier vision-language models demonstrate strong capabilities in user interface (UI) navigation, their high inference costs prohibit everyday use. Conversely, smaller models trained via supervised fine-tuning (SFT) or offline reinforcement learning often memorize static trajectories, leading to brittle execution and an inability to recover from errors. To address these limitations, we propose a novel online reinforcement learning framework that trains UI navigation agents directly on live iOS applications. Our framework decouples the agent into two specialized components: a Planning agent and a UI Grounding model. We rely on an LLM-as-a-Judge to provide comprehensive reward signals, combining dense, step-level feedback to evaluate intermediate progress with a terminal reward for overall task completion. To effectively leverage this dual reward structure, we optimize the agent using Proximal Policy Optimization (PPO) with step-level advantage estimation. Furthermore, we introduce GiGPPO, a novel neighbor-conditioned value estimation method that improves critic stability by leveraging reward signals from visually similar states across concurrent trajectories. To support this online training paradigm at scale, we introduce an efficient infrastructure that orchestrates hundreds of concurrent virtual iOS devices. Evaluations on rigorous benchmarks, including UINavBench, iOSWorld, and AndroidWorld, demonstrate that our online RL trained agents substantially outperform both SFT and terminal-only RL baselines while accelerating training convergence. Notably, our 8B RL agents achieve nearly a sevenfold improvement over the SFT baseline in out-of-distribution generalization to Android environments, while outperforming Gemini-3.5-Flash and tying with Gemini-3.1-Pro on real iOS applications.

# 论文结构化总结：面向真实 iOS 应用的规划-定位智能体在线稠密强化学习

## 1. 核心问题与研究背景

- **痛点一：前沿 VLM 成本过高**。Gemini 级视觉语言模型在 UI 导航上能力很强，但单任务推理成本可达数美元，无法支撑日常高频使用。
- **痛点二：小模型训练方式存在结构性缺陷**。
  - SFT 只在“已经走对”的成功轨迹上模仿下一步动作，几乎见不到错误状态，因此学到的是轨迹记忆而非可泛化策略，出错后难以恢复，跨 App/跨平台泛化差。
  - 现有 RL 方法多为“单步 RL”（奖励与黄金轨迹的相似度）或“仅终局奖励 RL”（信号稀疏，中间有效进展得不到信用分配）。
  - GRPO 及其变体是当前 GUI 智能体的默认选择，但其轨迹级聚合会把稠密信号压成一个标量，丢失时间结构；没有系统真正学习价值函数来做步级信用分配。
- **论文含义**：提出一个**直接在真实 iOS 应用上大规模在线 RL 训练**的框架，用“规划-定位解耦 + LLM-as-a-Judge 稠密/终局双通道奖励 + PPO 步级优势 + 邻域条件价值估计”来同时解决成本、脆弱性和信用分配三个问题。作者称这是**首次完全在真实 iOS 设备与真实 iOS 应用上做规模化 RL 训练**的 UI 导航智能体工作。

## 2. 方法论

### 2.1 核心思想：规划与定位解耦
- **Planning Agent**（8B，Qwen3-VL-8B-Instruct 初始化）：输入任务指令、当前截图、历史步级计划及其 CoT、上一步的“剩余计划”，输出带 CoT 的当前步计划 + 剩余高层计划。
- **Grounding Model**（3B 稠密模型，SFT 训练，>90% 留出集准确率，**冻结**）：把步级计划映射为动作原语与精确 x,y 坐标。
- **动作空间**：TAP、SWIPE、TEXT ENTRY、NAVIGATE HOME、LONG PRESS、ASK USER、TASK COMPLETE；ASK USER 用于任务欠指定时向用户澄清偏好。
- **解耦理由**：定位是相对确定的映射问题，SFT 即可做好；规划是开放式推理与动态适应问题，才值得投入昂贵的 RL。因此 RL 只用于规划器。

### 2.2 基础设施
- 云端托管 iOS 虚拟机 + VNC 驱动，动作接口与真机一致；预装应用并登录 Apple ID 后打**快照**，每回合结束回滚快照而非销毁会话，重启延迟约 **10 秒**。
- 训练时支持 **512 条并发轨迹**，每条独占一台设备与一个 agent-environment 循环。

### 2.3 奖励设计（LLM-as-a-Judge，无需黄金动作序列）
- **稠密判官**（每步调用，Gemini-3.5-Flash）：输入任务、动作历史（含历史判官结果）、当前计划、推理、前后截图，输出 `success / fail / overcomplete`；要求视觉上有进展且推理与画面一致，幻觉进展记为 fail，重复无效动作受罚，任务已完成仍继续动作记 overcomplete。另有独立判官只用当前截图判断 ASK USER 是否确有必要。
- **终局判官**（Gemini-3.1-Pro）：看最后三张截图 + 完整动作历史 + 历史稠密判决，输出 `success / fail / blocked complete`；blocked complete 用于奖励“被付费墙/CAPTCHA 等外部障碍阻断”的正确执行。
- **双通道奖励数值**：
  - 稠密通道（γ_dense=0.5）：+1.0 成功；0.0 失败或计划不可定位；−1.0 空计划/长度截断；−2.0 任务完成后继续动作。
  - 终局通道（不折扣，加到每一步）：+2.0 成功并声明完成；+0.5 blocked complete；−0.75 耗尽步数预算；−1.0 虚假完成声明；−2.0 输出不可解析/为空。
  - 稠密回报上界 1/(1−0.5)=2.0，恰等于一次终局成功，两通道量级平衡、互不主导。
  - 普通失败不惩罚以保持探索廉价；不可用输出按终局量级惩罚。
  - **基础设施性失败**（应用不渲染、安装失败、连接断开、生成超时）被 **mask**：不进策略梯度、不进 critic 回归、不能当邻居、不参与优势白化统计。

### 2.4 优化算法
- **价值函数与非对称折扣**：
  - \(V^\pi(s_t)=\mathbb{E}_\pi\big[R_T+\sum_{k=t}^{T}\gamma^{k-t}r^{\text{dense}}_k \mid s_t\big]\)，其中 \(\gamma=1/2\) 仅作用于稠密项，终局奖励 \(R_T\) **不折扣**。
  - 动机：γ=1 会让智能体靠“多走看似正确的步”刷稠密分而故意拖长轨迹（附录 A.2 的 GRPO 运行实证了这种 reward hacking）；而若终局奖励也被折扣，长轨迹上的任务级信号会衰减到可忽略，无法奖励“绕远但最终成功”的策略。
- **优势估计**：GAE 取 λ=1，退化为蒙特卡洛——优势 = 轨迹实际实现的回报 − critic 估计的 \(V^\pi(s_t)\)，对 critic 无偏、以方差换偏差。
- **critic 结构细节**：价值头接在 **动作 \(a_{t+1}\) 第一个 token 之前最后一个 token 的隐藏表示**上（而非动作 token 的平均嵌入），以免价值函数被未来动作信息污染。
- **GiGPPO（邻居条件价值估计）**：
  - 背景：GiGPO 依赖“完全相同的状态重复出现”做步级基线，但真实 UI 中同一屏幕几乎不重复，G=4/8 时子组退化为单例；放宽为“相似即同组”又会把偏差直接灌进价值估计。
  - 做法：在同一任务的兄弟轨迹中，用 **64-bit 感知哈希的 Hamming 距离**找最近状态作为“邻居”；小型 MLP 以“状态嵌入 + 邻居嵌入 + 邻居回报（折扣稠密和 + 不折扣终局）+ Hamming 距离”预测 \(V^\pi(s_t)\)。距离让 critic 自行校准邻居回报的可信度（距离 0 ≈ 直接观测，距离大则打折）。
  - **自身奖励从不作为输入**，防止回归目标泄漏。
- **训练稳定性技巧**：critic 先用 15 步单独预热（策略冻结，直接回归观测回报），避免早期价值误差主导优势、造成破坏性更新；critic 学习率 1e-4，比策略 1e-6 大两个数量级（critic 要快速跟踪移动目标且最终丢弃，策略是最终产物需缓慢更新）。
- **SFT 预热数据**：内部一方 iOS 应用数据 + 内部三方 iOS 应用数据 + 公开 GUIOdyssey（仅取其多 App 轨迹能力）。三者均无推理标注，用 Gemini 生成 CoT、剩余计划及其推理。
- **在线 RL 任务构造**：从 SFT 数据采样单 App 任务；多 App iOS 任务用两阶段合成（Gemini 先挑逻辑配对的 App，再生成任务，人工逐条校验可行性）。

  - PPO（仅终局奖励）Step 75/168/336 —— 稠密奖励消融。

## 4. 资源与算力

- 明确给出的：
  - **8 块 GPU，FSDP** 训练；rollout 由 **16 个 generator shard** 产生，每 shard 最多驱动 **32 台并发虚拟 iOS 设备**（合计约 512 条并发轨迹）。
  - 每步采 16 个任务 × G=8 = 128 条轨迹；回合上限 30 步；prompt 12288 token、每步生成 700 token；策略每批 2 次优化步、mini-batch 8 任务 1 epoch。
  - critic 用 LoRA（rank 32、α=64，排除视觉模块）+ 约 0.9M 参数的小 MLP（投影 128、隐层 512）。
  - 训练长度以**更新步数**表示：168 步 ≈ 1 epoch，336 步 ≈ 2 epoch。
- **未明确说明的**：GPU 具体型号与显存、单次训练墙钟时长、总 GPU·小时、判官（Gemini 调用）的 API 成本与吞吐、设备池规模的成本。这些对复现和成本评估很关键，论文没有交代。

## 5. 实验数量与充分性

- **规模**：3 个 benchmark × 约 8 类系统/checkpoint（SFT、terminal-only PPO×3、PPO×3、GiGPPO×3、4 个基线模型），主表约 30 余个数值；另有 3 组定位配置消融、1 组 GRPO 奖励设计对照、3 组定性 trace（图 2–4）。覆盖了“稠密 vs 稀疏奖励”“PPO vs GiGPPO”“分布内 vs 分布外”“小模型 vs 前沿模型”四条主线。
- **充分性**：
  - 优点：同时给出训练过程多个 checkpoint（可看收敛趋势），并有 terminal-only 的同预算对照，能支撑“稠密奖励加速收敛”的因果性主张；跨 iOS→Android 的零样本迁移是最有说服力的证据；trace 分析具体到错误恢复行为。
  - 不足：**未报告随机种子数与方差/置信区间**，iOSWorld 上 2.3%–9.8% 的差异（尤其 PPO Step 336 掉到 2.3%）很可能落在噪声内，却未被统计检验；训练任务集规模、任务类型分布、训练/评测重叠度未量化；定位消融只在 SFT 规划器上做，未验证 RL 规划器下的最优定位配置是否一致；缺少对判官本身可靠性的评估（judge 与人工判定的一致率、judge 偏差对策略的影响）。
- **公平性**：把前沿模型接入同一解耦架构与同一 prompt/截图输入，是较公平的比较方式；但 UI-TARS-72B 未在 iOSWorld 评测（表中 N/A），且其 AndroidWorld 成绩受益于 Android 专项训练，作者对此有说明。整体看比较是诚实的，作者也主动报告了 iOSWorld 上的失败模式。

## 6. 主要结论与发现

- 在线 RL 显著优于 SFT：UINavBench 16.7% → 32.4%（PPO Step 336）；AndroidWorld 4.7% → 32.8%（约 **7 倍**），证明学到的是可迁移策略而非 iOS 轨迹记忆。
- **真实 iOS 上追平前沿模型**：PPO Step 336 的 32.4% 与 Gemini-3.1-Pro 持平，多个 checkpoint 超过 Gemini-3.5-Flash（28.4%）与 Qwen3.8-27B（19.6%，参数量 3 倍以上），并远超 UI-TARS-72B（11.0%）。
- **稠密奖励带来收敛加速**：PPO Step 168（1 epoch）已匹配或超过 terminal-only PPO Step 336（2 epoch）；GiGPPO 在 UINavBench 上进一步把所需步数减半（Step 75≈PPO 168，Step 168≈PPO 336）。
- **GiGPPO 在分布内最有效**：在最接近训练环境的 UINavBench 上加速最明显，说明“视觉相似状态的回报”确实是有效价值信号；iOSWorld 上仅 GiGPPO Step 336 有明显提升（9.8% vs 4.5%）。
- **iOSWorld 仍是短板**：合成应用布局偏离训练分布、个性化与多 App 任务超出训练覆盖；后期 checkpoint 甚至出现“按名字找不到合成 App → 去 App Store 安装同名真实 App / 去 Safari 搜索”的副作用行为。
- **AndroidWorld 仍落后前沿模型**（32.8% vs 60.8%），作者归因于公开 Android UI 数据丰富、被前沿模型预训练覆盖，而公开 iOS 数据稀缺。

## 7. 优点

- **架构切分有清晰的功能论证**：把昂贵 RL 精确投在开放式规划上，把确定性定位留给 SFT，是性价比很高的工程-研究折中，并被定位消融间接支持。
- **奖励设计细致且有实证反例**：不是简单“加稠密奖励”，而是明确指出 γ=1 会导致刷步数式 reward hacking，并给出非对称折扣 + 负惩罚 + 稠密回报上界与终局奖励等量级配平的设计闭环；blocked complete、over

- complete、blocked complete 等边界情形都有明确数值定义；基础设施性失败被 mask，避免把环境噪声当成策略错误学进去。这套“奖励语义分类学”比多数 GUI RL 工作只给 0/1 终局奖励要成熟得多。
- **价值估计的工程细节扎实**：价值头接在动作首 token 之前的隐藏状态、邻居自身奖励绝不作为输入、critic 单独预热 15 步、critic 与策略学习率相差两个数量级——这些都是容易被忽略但直接决定 PPO 在长程稀疏任务上能否稳定的细节，论文给出了动机而不只是超参。
- **真实设备规模化基础设施是隐性贡献**：快照回滚把回合重置从“重建会话”降到约 10 秒，配合 512 条并发轨迹，才使“在真实 iOS 应用上做在线 RL”从不可行变为可行；这一点对工业界复现的价值可能高于算法本身。
- **诚实的负面结果**：附录主动报告 GRPO 全非负奖励下的刷步数式 reward hacking、iOSWorld 上“去 App Store 安装同名应用”的副作用行为、AndroidWorld 仍落后前沿模型近 30 个点，并给出归因，没有选择性汇报。

## 8. 局限与待澄清之处

- **判官即奖励，但判官本身未被评估**：整条奖励链路完全依赖 Gemini 系列模型，论文没有报告 judge 与人工判定的一致率、judge 的假阳/假阴率，也没有分析 judge 系统性偏差（如偏好“看起来有进展”的截图）会被策略如何利用。这是该方法最大的外部效度风险。
- **成本论证不完整**：论文以“前沿 VLM 单任务数美元”立论，但自身每步都要调用一次稠密判官、每回合再调一次终局判官，512 并发下的 API 吞吐与费用、以及相对纯 Gemini planner 的实际节省比例均未量化。若判官成本与直接调用前沿模型同量级，“降本”这一核心动机就缺乏支撑。
- **规划-定位解耦的错误归因问题**：定位器冻结且被假定 >90% 准确，规划器无法通过 RL 修正定位错误，只能学到“迁就定位器失败模式”的计划分布；论文未做“定位错误 vs 规划错误”的失败归因拆解，也未验证 RL 后规划器的最优定位配置是否与 SFT 时一致（消融只在 SFT 规划器上做）。
- **非对称折扣的有效视野偏短**：γ=0.5 意味着 5 步前的稠密奖励权重已降到 1/32，而回合上限 30 步；长程任务的中间信用分配实际上主要由不折扣的终局项承担，稠密通道更多在起“局部塑形”作用。论文未分析折扣因子敏感性（如 0.7/0.9）。
- **邻居机制的可扩展性存疑**：邻居来自同一任务的兄弟轨迹（G=8），任务多样性高时同任务可用邻居稀少；64-bit 感知哈希对动画、时间戳、滚动位置等动态 UI 元素敏感，可能把“视觉不同但语义相同”的状态判为远邻。论文未报告邻居距离分布与命中率。
- **统计严谨性不足**：无随机种子、方差、置信区间与显著性检验；iOSWorld 上 2.3% 这类数值不宜作为结论依据。训练任务集规模、任务类型分布、训练/评测重叠度均未量化。
- **模型规模单一**：只验证了 8B planner，没有 scaling 曲线，无法判断该方法在 3B/30B 上的收益是否同向。
- **评测与训练共用 VLM 判定范式**：benchmark 成功判定同样由 VLM 按清单核验，与训练判官同源，存在共同偏差放大的可能。

## 9. 启示与可复用点

- **“贵的 RL 只给开放式决策，确定性映射交给 SFT”** 是一个可迁移到其他具身/工具调用场景的分工原则。
- **非对称折扣 + 负奖励 + 两通道量级配平** 提供了一套可直接借用的稠密奖励设计模板，尤其适合“终局信号强、中间信号噪声大”的长程任务。
- **邻居条件价值估计（GiGPPO）** 把 GiGPO 的“完全相同状态”放宽为“感知哈希近邻 + 距离自校准可信度”，是对真实环境中状态几乎不重复这一事实的合理回应，思路可推广到任何难以精确重访状态的在线 RL 设定。
- **基础设施失败 mask** 应成为真实设备 RL 的标准实践，否则环境噪声会持续污染优势估计。

## 10. 总体评价

这是一篇工程含量很高、问题拆解清晰、且愿意报告负面结果的系统级工作。其最有说服力的证据是 iOS→Android 的零样本迁移（4.7%→32.8%）与真实 iOS 上追平 Gemini-3.1-Pro；最有价值的可复用贡献是奖励语义分类学、非对称折扣的价值函数形式与邻居条件 critic；最明显的短板是判官可靠性未评估、成本账未算清、统计检验缺失。作为“真实移动设备在线 RL”的早期规模化尝试，其方法论框架比具体数值更具参考意义；但若要作为可复现的实证结论，仍需补齐方差报告、判官一致性评估与成本核算。
