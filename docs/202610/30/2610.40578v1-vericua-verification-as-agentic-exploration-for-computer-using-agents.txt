Building and scaling computer-using agents (CUAs) across desktop, mobile, and web environments requires reliable task-completion verification for data curation, evaluation, and reinforcement learn-ing. Typical automated approaches prompt vision-language models (VLMs) to judge trajectories or generate programs to inspect application state. However, both rely on partial views of complex digital environments. VLM judges are restricted to supplied observations, while generated programs depend on accessible state. These views can omit decisive evidence or leave completion judgments unsupported. Tailoring separate verifiers to different platforms and access settings adds further engineering cost. We present VeriCUA, a platform-agnostic framework for verification through agentic exploration. It treats verification as dynamic evidence gathering and assessment within a shared procedure for online and offline settings across platforms and observation modalities. After inspecting the available context to construct a task rubric, the verifier selects GUI or code checks for unresolved requirements and combines their findings under explicit evidence rules. Experiments show improved agreement with reference labels over the compared baselines across these settings, with the largest offline gains on hard cases and stronger rejection of false completion claims online. Further analyses connect these gains to complementary evidence and test-time exploration. 

1. Introduction 

Vision-language models (VLMs) have enabled computer-using agents (CUAs) to navigate the digital world through software interfaces (Rawles et al., 2025; Xie et al., 2024; Zhou et al., 2024). Given a natural-language instruction, an agent observes the interface, plans, and acts, leaving a trajectory of thoughts, actions, and observations. Digital tasks span applications in which success can depend on visual presentation, application records, or changes to persisted files. A trajectory can appear successful even when edits remain unsaved or an operation fails without a visible warning. The agent may also report completion after fulfilling only part of the instruction. Accepting such a run as successful produces a false positive, making the distinction between attempted actions and their actual effects central to verification. Developing these agents therefore requires reliable judgments throughout evaluation, data curation (Sun et al., 2025), and reinforcement learning (Xue et al., 2026a), including applications for which no task-specific checker has been supplied. An execution can be verified online from the resulting machine state or offline from its retained trajectory. Evidence can come from rendered interfaces, structured observations, or artifacts such as files and database records. VLM judges assess trajectories from selected observations (Pan et al., 2024), while automatically generated checkers inspect application state through model-written programs (Xue et al., 2026b). A fixed set of frames may omit a decisive effect, and a generated query may target state that does not answer the verification question. Platform-native signals support more specialized judgments and validation (Chae et al., 2025; Sun et al., 2026b), but their availability varies with the application and access setting. Agentic approaches actively inspect trajectories or environments (Cui et al., 2026; Sanayei et al., 2026; Wan et al., 2026). A shared procedure must seek relevant evidence under these access constraints and ground its conclusions in the observations.

To address these evidence and access limitations, we present VeriCUA, a platform-agnostic framework that formulates CUA verification as agentic exploration (Figure 1). It provides a shared procedure for offline and online verification using the sources and inspection tools available in each setting. Verification begins after the executing agent’s attempt ends. The verifier first explores the available context to understand the app and its task artifacts, then uses these observations with the instruction to construct a rubric of fine-grained requirements. This context helps interpret task concepts and locate potential evidence, especially when the application is unfamiliar. The verifier chooses GUI or code tools to check the rubric’s requirements. Findings from these checks reveal what remains unresolved and guide further inspection of relevant frames, artifacts, or another available source. VeriCUA’s unified design separates the verification workflow from the interfaces through which evidence is obtained. Offline verification navigates retained screen frames and action logs, using structured observations such as accessibility trees when recorded. Online verification can inspect the accessible machine state left by the executing agent through GUI or code tools, including files, databases, and system services. These sources answer different questions about the requested outcome. An action log records an attempted edit, while a file read can show whether the edited content persisted. A report that the task is complete remains a claim to verify. The framework links findings to their supporting observations and records source properties such as frame timing or state persistence. Explicit evidence rules combine the findings into a task verdict while retaining which requirements are supported, refuted, or unresolved. We evaluate this shared procedure in offline and online scenarios on multiple platforms. VeriCUA achieves higher agreement with reference labels than the compared baselines in both settings. It also rejects more false completion claims than the VLM judge in the online study. The action-space study shows that adding code-based state reads enables more decisions without increasing false positives. At a matched number of verification passes, adding visual evidence improves agreement and decision coverage compared with repeating the same configuration.

2. Related Work 

Computer-Using Agents and Their Evaluation. Computer-using agents are evaluated on web, mobile, and desktop tasks (Rawles et al., 2025; Xie et al., 2024; Zhou et al., 2024), with dedicated environments covering scientific applications (Sun et al., 2026c). These benchmarks typically use task-specific programmatic evaluators to check the resulting application state. Human-labeled tra-jectory datasets provide reference judgments across applications (Sun et al., 2026a), while audits of benchmark evaluators identify errors in the checks used to produce reference labels (Xie et al., 2025). Benchmarks of environment-aware judges assess evidence acquisition and verification of states and execution processes (Shi et al., 2026). Completion judgments also support data curation and training beyond benchmark evaluation. Trajectory synthesis pipelines use verifier scores to select examples (Sun et al., 2025), and continual reinforcement learning relies on automated feedback during environment adaptation (Xue et al., 2026a). Rubric-based reward modeling further uses synthetic criteria derived from preferred and rejected responses (Liu et al., 2026). Safety-oriented evaluation additionally examines whether agent behavior satisfies workflow constraints (Sun et al., 2026b). The range of applications and evaluation criteria creates demand for verification that can locate relevant evidence through available interfaces, including tasks without a dedicated evaluator. 

Verifying Trajectories and Reward Models. VLM judges assess task completion from trajectory observations (Pan et al., 2024), while structured critics evaluate task requirements or intermediate milestones (Li et al., 2026). Task-adaptive rubrics can be generated from task descriptions to guide trajectory evaluation (Ding, 2026). Generated verifiers construct programs that inspect application state (Xue et al., 2026b). Reward benchmarks evaluate the reliability of trajectory judgments against reference labels across tasks and platforms (Lin et al., 2025; Sun et al., 2026a). Agent-based evaluators assess intermediate task requirements in code-generation workflows (Zhuge et al., 2025). Agentic approaches gather additional evidence by iteratively inspecting recorded trajectories (Wan et al., 2026) or interacting with the execution environment (Cui et al., 2026). Evidence-first verification separates investigation from validation, checking proposed claims against their state or trace sources before accepting rubric verdicts (Sanayei et al., 2026). These approaches motivate both seeking task-relevant evidence and assessing how it supports a judgment. VeriCUA builds its rubric after inspecting the available environment or recording, then selects GUI or code checks for unresolved requirements. Source-aware rules combine the resulting findings within a shared offline and online verification workflow.

3. Method 

3.1. Verification as Active Evidence Gathering 

Given an instruction 𝑔 , an executing agent produces a trajectory 𝜏 = [𝑜 0, 𝑎 0, . . . , 𝑜 𝑇 ] of observations and actions, together with any recorded reasoning, and leaves the environment in state 𝑠 𝑇 . VeriCUA begins after this attempt ends and assesses whether the execution fulfilled 𝑔 using the sources available to the verifier. Although task completion is binary, the verifier outputs 𝑦 ∈ { success , fail , abstain },allowing abstention when the gathered evidence is insufficient to support a decision. The available sources S = {𝑆 1, . . . , 𝑆 𝑚 } can include a retained trajectory, recorded accessibility trees ( a11ytrees ), a frozen machine snapshot, or accessible post-execution machine state. Offline verification uses retained observations, while online verification can inspect exposed machine state alongside any retained execution records. When a requirement concerns a change made during execution, an available pre-execution reference can also serve as a source. The shared workflow in Figure 1 begins with context inspection , which gathers information about the application and available observations into context 𝑐 . Rubric synthesis uses 𝑔 and 𝑐 to produce requirements 𝑅 that make the instruction checkable. During active exploration , the verifier selects checks for these requirements and uses their results to decide what to inspect next. Finally, rule-based arbitration combines the findings under the setting’s evidence rules and handles any unresolved requirements. 3.2. Environment-Aware Rubric Synthesis 

An instruction specifies the requested result but may leave its application-specific interpretation implicit. A request to save a note, for example, does not necessarily identify the application’s storage directory or explain which view reveals whether the note persisted. Generating requirements without this context can introduce assumptions about files or interface elements that the application does not expose. Before constructing the rubric, VeriCUA uses the available inspection tools to gather context 𝑐 . Online inspection can identify application packages, relevant directories, and exposed database schemas; offline inspection reviews the recorded steps, frames, and available structured observations. From the instruction 𝑔 and observed context 𝑐 , the verifier constructs a rubric 𝑅 = {( 𝑟 𝑖 , ℎ 𝑖 )} 𝑛 𝑖 =1, where each 𝑟 𝑖 is a checkable task requirement and ℎ𝑖 ∈ { hard , soft } indicates whether it is mandatory for success or an additional check. Requirements can concern a resulting state or a change relative to an available pre-execution reference. Each hard requirement must be justified by the outcomes requested in the instruction, while context supplies its application-specific meaning and helps locate evidence. 3.3. Adaptive Hybrid Action Space 

The action space connects the rubric to the sources that can answer its requirements. Figure 2 distinguishes three views of task state: • Trajectory. Retained frames, actions, and reasoning record what the executing agent observed and attempted. The verifier can search the action log, inspect selected frames, and read recorded 

a11ytrees when available. • Surface. The current machine interface can be inspected through a new screenshot or a UI hierarchy read. A recorded screenshot belongs to the historical trajectory; this view provides a fresh observation of the accessible machine. • Persisted State. Files, application databases, and stored settings can retain effects that the current interface does not show. Code tools can inspect them through file reads, database queries, or queries to exposed services. The harness records persistence for each read. Alongside stored artifacts, live machine access provides volatile observations such as current UI dumps and harness artifacts. GUI tools support visual inspection through frame selection, region enlargement, and optical char-acter recognition (OCR), while code tools query exposed machine state. The online verifier can also synthesize a checker : a sequence of permitted reads paired with a predicate that evaluates a requirement. The harness executes the reads; structured predicates use a restricted evaluator, while visual or semantic comparisons use a model judgment. A single online inspection action 𝛼 𝑘 can execute a checker comprising several reads and its predicate evaluation. The verifier chooses its next inspection from the findings already collected, focusing on requirements

The harness records the executed tool, arguments, and source metadata, including frame timing or the persistence of queried state. 3.4. Evidence Discipline 

VeriCUA links each finding to an executed read, then applies source constraints and corroboration rules before assigning requirement statuses. 

Grounded Findings. Each finding identifies a rubric requirement, states the support or refutation inferred from an observation, and cites the executed check that returned the observation. The harness rejects citations that match no executed call and attaches each valid citation’s observation and source attributes to the finding. Source attributes and corroborating probes then determine how each linked assessment contributes to a requirement’s status. 

Source-Aware Evidence. The attested /asserted source labels distinguish observations of task state from records of the executing agent’s intent or claims. A post-action frame, a file read, or a database query can provide attested evidence. The executing agent’s completion message and a pre-action frame showing an intended operation are asserted evidence for that operation’s outcome. Asserted evidence can direct further inspection but cannot alone mark a requirement met. Source attributes further constrain what an observation can support, including whether a recorded image precedes or follows the action whose effect is being checked. Online reads distinguish per-sistent artifacts from volatile interface state, which can answer different questions about the same requirement. For example, a screen displaying edited text can support its visible contents, while a file read can check whether that text was saved. A finding must address the task requirement, and its observation must satisfy the source conditions for the inference being made. 

Rule-Based Arbitration. The arbiter applies the setting’s confirmation and refutation rules to the stored findings E𝐿 , assigning each requirement a status of met, unmet, or unknown. A met status requires attested support, while unmet requires corroborating refutations from separate probes. Evidence that does not settle the requirement leaves it unknown. The task verdict is success when all hard requirements are met, and fail when any is unmet. If some remain unknown and none is unmet, the task is unresolved and follows the setting’s abstention or fallback policy. Aggregation is deterministic for fixed findings and rules; the stored records allow confirmation thresholds to be re-evaluated without repeating inspection actions. 

3.5. Online and Offline Instantiations 

Online and offline verification share the same workflow over the sources illustrated in Figure 2. Access conditions determine the available checks and the treatment of unresolved tasks. 

Online. Online machine access allows the verifier to combine GUI inspection with code-based checks of stored artifacts. Task-specific checkers can be reused across repeated executions of the same task with compatible application schemas. Persistent attested reads can confirm requirements, while volatile observations provide corroboration. The verifier abstains on unresolved tasks to avoid assigning training or filtering labels unsupported by the collected evidence.

Offline. VeriCUA audits fixed, time-stamped recordings through multiple paths, seeking support through forward inspection and refutations through backward inspection. A requirement is met when every completed path provides attested support. For tasks left unresolved, the reported configuration uses an initial judgment : a single-pass VLM assessment of the retained trajectory computed before exploration and withheld from the audit paths. This fallback supplies the final verdict while unresolved requirements remain unknown. Detailed setting rules and inspection budgets are given in Appendices A.1 and B.3. 

4. Experiments 

4.1. Experimental Setup Benchmarks. In online environments, we run AndroidWorld (Rawles et al., 2025) on an Android emulator, OSWorld (Xie et al., 2024) in a virtual machine, and ScienceBoard (Sun et al., 2026c) in its scientific desktop environment. Each episode is executed by the benchmark’s own agent scaffold, and the verifier probes the resulting machine state after the episode ends. For offline verification, we evaluate recorded WebArena trajectories from three executing agents (Zhou et al., 2024) and the human-labeled OSReward trajectories (Sun et al., 2026a), which span four platforms and several agents. 

Protocol. All verifiers and baselines run on gemini-3-flash-preview , and the backbone study re-runs them on gemini-3.1-pro-preview . In online environments, gold is each benchmark’s official evaluator and the executing agents also run on gemini-3-flash-preview . On WebArena we provide a11ytree variants of the input beyond the GUI, to the verifier and the judges alike. The remaining protocol details are provided in Appendix B. 

Baselines. We compare against a VLM judge, an automatically generated verifier, and two structured judges. Implementation details are provided in Appendix B.2. • VLM judge. A single-pass judge such as TRM (Sun et al., 2025), which assesses the supplied observations in one model call and returns a verdict or a score. • Auto-Generated Verifier (Xue et al., 2026b). A model-generated evaluator script per task, run once against the machine for a binary verdict. • CUAJudge (Xue et al., 2026a). A checklist judge that derives key points from the task and checks them against sampled frames in one call. • OS-Themis (Li et al., 2026). A milestone judge that checks ordered milestones and reviews them. The VLM judge runs in both settings, the auto-generated verifier only in online verification, and CUAJudge and OS-Themis only in offline verification. 

Metrics. We report agreement with gold, precision, recall, and F1 for the success class, and the false positive rate, with abstentions counted as fail. For verifiers that abstain we also report the decision rate and the accuracy on decided episodes. Verdict conventions are given in Appendix B.4.

5. Analysis 

5.1. GUI Versus Hybrid Action Space GUI Only versus Hybrid. On online AndroidWorld, adding code-based state checks to GUI inspection increases the decision rate and recall while leaving false positives unchanged (Figure 3). In the paired analysis, every additional correct decision from the code channel is supported by a file or application-store read. Access to stored state therefore resolves requirements that GUI observations leave unsettled. 

5.2. The Effect Of Observation Different Observations. On WebArena, adding a11ytrees to screenshots raises VeriCUA’s decision rate while leaving accuracy unchanged. Trees alone yield the highest decision rate and lowest cost, at lower accuracy. Table C.2 in Appendix C.2 reports the observation-input ablation. The comparison with baseline judges uses trajectories from three rollout agents. Their accuracy changes little between tree-only and combined inputs, and VeriCUA remains ahead under both settings (Figure 4b). Per-agent results are given in Table C.4. 

More Observations. We also vary the number of final frames given to the single-call OSReward judge (Figure 4a). Additional frames improve its accuracy on the hard subset, but the judge remains below VeriCUA. Accuracy on the full set changes only modestly. 

5.3. Test-Time Exploration Combining Passes. On the multi-pass AndroidWorld suite, three passes use the default configuration of code and structured-state checks. An additional pass enables visual inspection through screenshots and file-image reads, referred to as the vision fallback. All passes and the auto-generated baseline share one restored snapshot per episode. The combination rule retains a decided verdict and abstains when decided passes disagree. Combining the default passes gives modest gains over the strongest single pass. Adding the visual pass improves agreement and decision rate further, both reaching 87% (Figure 5a). 6. Conclusion 

We presented VeriCUA, a platform-agnostic framework for verifying computer-using agents through agentic exploration. The verifier inspects available context before constructing a task rubric, then selects GUI or code checks to gather evidence for unresolved requirements. Source-aware arbitration combines the findings within a shared workflow for offline recordings and online environments. Across the evaluated platforms, VeriCUA improves agreement with reference labels over the compared baselines, with fewer false positives online and the largest offline gains on hard trajectories. Analyses show that complementary evidence sources and verification passes improve decision coverage, while stronger backbones further improve accuracy. These results support agentic verification for CUA evaluation and motivate its use in data curation and reinforcement learning.

A.3. Evidence Aggregation 

On recorded trajectories, up to 𝐾 audit paths gather support through forward inspection and seek refutations through backward inspection. The default 𝐾 = 3 permits early stopping after two paths agree on every hard requirement. A requirement is met only through attested support from every completed path and unmet only with corroborating refutations from separate probes. If the evidence 

> 16 VeriCUA: Verification as Agentic Exploration for Computer-Using Agents

does not settle the task, the initial judgment supplies the fallback verdict without adding attested support to unknown requirements. In online environments, initial inspection maps the device’s packages, stores, and schemas before rubric synthesis. The observed context informs the rubric and subsequent checker construction; each requirement receives checkers on more than one surface where possible; predicates are evaluated by a restricted evaluator or, for semantic comparisons, by a judge call; a requirement is met by one persistent attested confirmation and unmet by two corroborating refutations (the unmet_min 

threshold, which trades decided episodes for precision when raised). An unresolved task produces an abstention, which binary evaluation counts as fail. Across passes, the combination rule takes the decided verdict and abstains when two decided verdicts disagree. 

A.4. Read-Only Enforcement 

On recordings the read-only property is structural, since every verb is a pure function of files on disk. On a machine the verbs come from a fixed allowlist, arguments that could smuggle shell control are rejected, and a digest of the plan’s persistent targets is compared before and after execution. 

A.5. Online Environment Adapters AndroidWorld. In online environments, VeriCUA runs against AndroidWorld on an Android emulator. The harness has root access over adb , so every store the benchmark’s own evaluator can read is readable by the verifier. Each episode is executed by the benchmark’s agent scaffold; when it ends, the harness saves the device state as a snapshot and verification runs against that snapshot, so any verification pass can be replayed on the identical end state. Before the episode starts, the harness records a pre-state anchor of the application storage, against which requirements about a change are compared. The agent’s submitted answer is extracted by the harness and exposed through the 

submitted_answer getter as the artifact under test. The emulator is a headless Pixel 6 image at API level 33 (Android 13) with root access over adb .Snapshots are taken through the emulator console once the official evaluator has run. 

OSWorld and ScienceBoard. OSWorld runs in a virtual machine and ScienceBoard in its own scientific desktop environment. Both are verified through the same allowlisted read-only getters over the machine, and ScienceBoard’s evaluator reads the state of the scientific applications inside the VM. Both use the virtual machine images that the benchmarks ship, without modification. 

A.6. Recorded Observation Processing 

A recorded trajectory enters as the agent’s actions and reasoning, its screen frames, and, when the platform recorded them, its a11ytrees . Frame semantics, whether frame 𝑖 captures the state before or after action 𝑖 , is declared per dataset and determines the post-effect and pre-action evidence types. B.2. Baseline Implementations Offline Verification. TRM scores the trajectory from 1 to 5 in a single call from the instruction, every thought and action, and the last three frames; CUAJudge checks up to six task-derived key points against the first and last of up to six frames in a single call; OS-Themis verifies up to four ordered milestones over up to eight frames and reviews them in a second call. The three offline judges run under one harness at temperature 0, with images downsampled to a long side of 1280 pixels, the first and last frames pinned, no self-consistency voting, and a parse failure mapped to fail. TRM thresholds its 1–5 score at 4 and is the only judge that sees the agent’s thoughts. CUAJudge collapses the original four-stage pipeline into one call, dropping the dedicated frame-selection and init-versus-final modules. OS-Themis collapses the multi-agent critic to two calls with the budget cut to four milestones and eight frames against the original six and twelve; Table C.6 shows that restoring the original budget changes little. 

Online Environments. The online VLM judge answers in one word from the instruction and the final screenshot and never abstains; the auto-generated verifier writes one evaluator script per task with full device access and runs it once. The auto-generated verifier receives the instruction with its concrete parameters, the same generic device context our synthesis receives, unrestricted host-side adb and Python, and the agent’s submitted answer on answer-scored tasks. It does not receive the trajectory, the results of context inspection, or the pre-state anchor, and it runs last on each end state.

Majority Voting. Majority voting combines the same three verifier draws by vote with abstentions folded to fail. 

B.3. Verifier Configuration Offline Verification. The default runs 𝐾 = 3 paths and stops after two when they agree on the status of every hard requirement, which happens on about two fifths of the trajectories. A path spends up to four tool calls gathering support and then at least four, or two per hard requirement, hunting refutations. Each call returns one observation, frames are downscaled to at most 1288 pixels on the long side, and only the last eight images stay in context. The rubric comes from three candidate decompositions consolidated in a fourth call. The sealed initial judgment reads the last five frames together with the thought and action log and is reused only as the fallback. 

Online Environments. Rubric synthesis draws two candidate rubrics at temperature 0.7 and consol-idates them in a third call at temperature 0; checker synthesis makes two parallel calls at temperature 0.7 and asks for two checkers per hard requirement on different surfaces where the state allows it; context inspection uses one call over at most three packages and six databases, followed by one schema probe; a semantic predicate costs one judge call at temperature 0 over at most three images. No call carries a token cap, and each has a 180-second timeout with up to six retries. 

B.4. Evaluation Metrics 

The binary evaluation treats success as the positive class. Abstentions are counted as fail for agreement, precision, recall, F1, and the false positive rate. For verifiers that abstain, we also report the decision rate and the accuracy on decided episodes.

E. Limitations and Broader Impacts 

VeriCUA trades cost for evidence. A verification pass issues tens of tool calls and model calls per trajectory, an order of magnitude more than a single-call judge, so it suits filtering and reward assignment better than interactive use. On recorded trajectories it abstains wherever the recording holds no evidence for a requirement. Those abstentions are a coverage limit, and online access lifts it only for environments that can be instrumented. A stochastic verifier also needs its draw-to-draw spread reported beside every comparison, as we do. Reliable trajectory verification lowers the cost of training computer-using agents and of auditing benchmark labels. The same machinery could be misused to certify agents that act on real systems, which is one reason VeriCUA never writes to the environment it verifies.

F.1. Recorded-Trajectory Verification 

You decompose a computer-use task into atomic, individually checkable requirements for a verifier. Output requirements about the FINAL END-STATE the task demands (what a programmatic checker inspecting files/documents/settings afterwards would verify), NOT about the method or the steps taken. Rules: - Each requirement is one concrete, verifiable condition. - Honor every quantifier/detail: "all"/"each" => ALL; exact names/values/paths => exact. Split compound asks into separate requirements. - Mark hard (must hold for success) or soft (minor/cosmetic). - Do NOT invent process requirements ("must have clicked X"); if the end-state is right, the route does not matter. Output ONLY: ```json {"requirements": [{"id": "r1", "description": "...", "hard": true}, ...]} ```

F.2. Online Verification 

You author verification requirements for tasks executed on an Android device. Given a task instruction, produce the END-STATE requirements a strict human examiner would check AFTER the task supposedly finished. Rules: - END-STATE only: describe what must be true of the device state, never the procedure ("brightness setting equals maximum", not "user opened settings"). - Atomic: one checkable fact per requirement. Split name vs content vs location. - Strict reading: if the instruction names a value, place, or format, it is required exactly; include implicit artifacts (a created note must exist AND contain the given text). - hard=true for requirements whose failure fails the task; hard=false for cosmetic/soft ones. - Only what the instruction implies: do NOT add adjacent settings, modes, or hygiene the instruction never mentions (no invented requirements). - COUNTS ARE EXACT: "take one video" means exactly one new video was created, not at least one; "log the reimbursable transactions" means exactly that set was added — nothing missing, nothing extra. When the instruction quantifies, produce a requirement for the exact count or exact set of NEW artifacts (relative to the episode start), not mere existence. - Do NOT bind platform-specific encodings or exact constants the instruction does not state: say "the minimum value the system allows", never "(0)". Resolving concrete encodings is the checkers' job, not yours. - Do NOT bind storage locations or app conventions the instruction does not name ("a photo was taken" requires a new image in SOME standard media location, not specifically DCIM). Location is a requirement only when the instruction states one. Output ONLY JSON: ```json {"requirements": [{"id": "r1", "description": "...", "hard": true}]} ```
