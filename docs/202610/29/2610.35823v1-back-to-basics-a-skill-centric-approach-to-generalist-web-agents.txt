Abstract
Browser agents do not just need more practice. They
need to practice the right things. We introduce MINIWEB,
a realistic miniature of the web comprising 65 intercon-
nected websites across 15 domains, where agents navigate,
search, and transact as people do. Its 369 human-annotated
tasks cover everyday workflows and label 37 reusable inter-
action primitives grouped into 7 skill families, allowing us
to diagnose which skills fail rather than only whether a task
succeeds. Benchmarking ten open-weight agents, we find
that drag & gesture is consistently the weakest family, with
no agent solving more than 24% of its instances. To address
this gap, we introduce MINIWEBGEN, a framework that
autonomously generates verified, skill-centric training data
from MINIWEB.
Fine-tuning Qwen3.5-4B on just 3.1K
verified trajectories improves single-primitive success by
24.9pp across 13 unseen websites, with gains across every
skill family. However, these trajectories teach short-horizon
interactions, which do not directly translate to full-task
success. We build on this result with MINIWEBAGENT,
which pairs the trained executor with a planner that decom-
poses full tasks into the skill-level steps it learned to per-
form. This approach improves task success by 19.4pp on un-
seen MINIWEB sites and transfers to external benchmarks,
with gains of 9.3pp on WebArena-Lite, 16.1pp on Online-
Mind2Web, and 20.0pp on WebVoyager, without training on
their trajectories. We provide a simple recipe for compact
browser agents: practice reusable skills directly, then com-
pose them to solve unfamiliar tasks.

2. Related Work
Web benchmarks and synthetic environments.
Web
benchmarks aim for realism, reproducibility, or cover-
age. MiniWoB and MiniWoB++ [17, 25] pioneered syn-
thetic environments for low-level web interaction, with
small self-contained pages that exercise individual widgets
such as sliders and drag targets. Self-hosted environments
such as WebShop [35], WebArena [39], WorkArena [7],
and MyPCBench [15] provide realistic locally hosted
websites, but are limited in term of coverage, while
Mind2Web [6] and live-web benchmarks [9, 13, 16, 34]
broaden coverage at the cost of task stability and repro-
ducibility. Environment-generation pipelines address this
by compiling real-site interaction structures into finite-state
machines [31], generating environments with verifiable
tasks [5, 38], or synthesizing versions of webpages [14].
Most of these benchmarks score whole tasks: step-level
metrics [6], progress rates [18], and key-node evalua-
tion [22]. They measure how far an agent gets but do not
attribute a failure to a specific skill. Concurrent with our
work, ComponentBench [11] evaluates agents on 97 canon-
ical UI components, including sliders and date pickers, us-
ing programmatically verified tasks across three React com-
ponent libraries. MINIWEB shares this focus on interac-
tion skills but embeds them in full multi-page websites with
persistent backend interactions.
It also composes prim-
itives into multi-step, cross-site tasks and provides skill-
segmented demonstrations with per-primitive verdicts.

Training data and skill composition for web agents.
Web agents are traditionally trained on end-to-end task tra-
jectories [12, 13, 24, 28, 32].
Recent work has scaled
these training corpora by converting tutorials into demon-
strations [21, 33], relabeling or reverse-synthesizing tasks
from exploration [19, 26], or collecting trajectories on
the live web [27].
These pipelines inherit the cover-
age of their sources, whereas MINIWEBGEN uses privi-
leged knowledge of each site to direct generation at pre-
defined primitives, including interactions that end-to-end
data rarely contains (dragging, searching, ...).
While
other work reuses skills at inference time as induced work-
flows [30] or distilled APIs [37], we instead train skills
into an executor’s weights through practice. To compose
them, MINIWEBAGENT adopts the established separation
of planning from execution found in planner–grounder de-
signs [10, 36], manager–worker frameworks [1, 2], and
plan-and-act agents [8, 23]. Our contribution is not this ar-
chitecture but the experience used to train the executor: we
examine whether targeted practice improves individual in-
teractions on unseen websites, and whether a planner can
compose those improvements into more successful multi-
step task execution.
3. Methodology
We want to study the primitive skills, or macros, of current
web agents. Given a task that requires a specific set of skills,
can an agent reliably perform each one? When the task
fails, can we identify which skill it struggled with? To an-
swer these questions, we need tasks whose component skills
are explicit and can be evaluated separately, which current
web-agent benchmarks do not provide [6, 9, 13–15, 35, 39]
(Tab. 1).
3.1. MINIWEB
We introduce MINIWEB, a collection of 65 synthetic web-
sites built around 37 interaction primitives. We build it from
the bottom up (Fig. 3): First the primitives, then supporting
websites, and finally tasks that chain them together.
Primitive selection and schema.
The set of primitives
a web agent needs is hard to enumerate from first princi-
ples, so we start from existing data. With Claude Opus 4.8,
we label 15.7K tasks from WebArena [39], WebShop [35],
WebVoyager [13], and Mind2Web [6] with the recurring
interaction patterns that each requires, reusing an existing
label whenever one fits. This first pass yields 139 candi-
date macros, which are dominated by searching, filtering,
and extracting information, and only 0.3% of their 52K la-
bels involve dragging and none drawing, uploading a file,
or editing a spreadsheet cell. In group brainstorming ses-
sions, we merge near-duplicate and site-specific candidates,
add the interactions the source benchmarks miss, and sep-
arate reasoning from the physical interaction. The result
is an initial set of 46 primitives, which we refine after an-
notation. Each is a site-agnostic interaction with a single
purpose that may take several browser actions, such as fil-
tering items with a slider or editing a spreadsheet cell. We

Website construction.
We select 65 websites across 15
representative domains to cover a broad range of interac-
tion primitives and cross-site workflows.
Half of these
domains are absent from WebArena [39], Mind2Web [6],
WebVoyager [13], and WebShop [35]. We then have anno-
tators specify each site’s supported primitives, features, and
connections to other sites. These links form an information
flow graph, which allow for realistic cross-site features such
as payment confirmations or cross-site sharing. For realistic
content, 21 sites are seeded from public datasets1, which we
join through a synthetic layer of users and accounts. The re-
maining 44 sites use deterministic synthetic data, for about
4M records in total. More details can be seen in Fig. 2.
A coding agent2 implements each site’s frontend and back-
end from its specification, and all the authors and annotators
review every site and fix it until it supports its primitives.

The entire process took roughly a month with 6 annotators
working 8 hours a week. The backends log every request
in a session and write all changes to a per-session overlay,
so verifiers can inspect what an agent did, and many agents
can run in parallel from the same initial state.
Task annotation and verification.
An episode is a tra-
jectory τ = (o0, a1, o1, . . . , aT , oT ) of observations and
browser actions, during which the backend records a request
log L(τ). A task T = (g, ⟨m1, . . . , mk⟩) pairs an instruc-
tion g with a chain of primitives. Annotators compose tasks
from supported primitives, specify their dependencies, and
write realistic instructions. They then perform each task
while our tool records browser interactions and server re-
quests, marking the span [bj, ej] of each mj to produce a
skill-segmented demonstration τ ⋆. Six annotators produced
369 tasks over three months, including 43 cross-site tasks.
At the end, the first author manually reviewed every task
together with its verifier and demonstration, correcting or
removing those with errors. As a final refinement of the
primitive set, we drop the 9 hyper-specific primitives that
annotators used fewer than three times. The remaining 37
primitives in 7 families form the final set M.
We use two graders. Parameterized verifiers [38] check
observable interactions against the backend request log,
while a VLM judge [34] evaluates semantic and reason-
ing outcomes using the primitive’s rubric, request log, and
screenshots. A task succeeds only if every required primi-
tive j ∈R passes,

Grader validity.
We validate both graders on 183 human
demonstrations that remain valid on the current sites and
pass the task verifier.
For each, we construct two neg-
atives: one truncated before the final required primitive
and one empty episode. Across these 549 cases, the de-
terministic verifiers achieve 98.9% accuracy and the judge
98.2%. On 3,689 episodes from the ten untrained agents,
the two graders agree on 93.1% of task outcomes (Cohen’s
κ = 0.85). A human audit of 120 agent episodes, stratified
by the graders’ verdicts and weighted back to all episodes,
finds the judge right on 92.2% of task outcomes (κ = 0.84)
and the verifiers on 88.9% (κ = 0.77), close to the agree-
ment between two human labelers (κ = 0.86). Supp. E
details the validation protocol, the recordings we leave out,
the grader disagreements of each agent, and the audit.

4. Experiments and Analyses
We use MINIWEB to ask four questions. Which skills do
current web agents lack (Sec. 4.1)? Does practicing skills
in isolation improve them, and the tasks that chain them
(Sec. 4.2)? Does an agent that composes trained skills trans-
fer to websites and benchmarks it never saw (Sec. 4.3)? And
does our skill-centric data transfer better than a task-centric
corpus of the same size (Sec. 4.4)?
Setup.
We profile ten open-weight agents (Tab. 2): four
general models in the browser-use harness [20] and six web
or computer-use agents in their native agent loops [4, 5, 12,
24, 29]. For training experiments, we use Qwen3.5-4B and
compare an untrained single agent, a single agent trained
on all MINIWEBGEN trajectories, an untrained planner-
executor, and MINIWEBAGENT, which pairs the planner
with the trained executor (Tab. 3). To isolate the effect of
training data, we also train the same executor on a size-
matched set of task-centric trajectories collected on our
training sites with InSTA’s pipeline [27].
Training uses only the 52 MINIWEB training sites. We
evaluate on 62 human-authored tasks and 103 generated
single-primitive tasks from 13 held-out sites, as well as
WebArena-Lite, WebVoyager, and Online-Mind2Web. For
the live benchmarks, we exclude tasks that are impossible
or blocked by our network; full evaluation details, action
budgets, repeated-run protocol, and statistical tests appear
in Supp. J and Supp. H. We report our key findings below:
4.1. Drag & gesture is the weakest family in all web
agent models.
As shown in Tab. 2, drag & gesture is the weakest skill
family for every untrained agent. Web and computer-use
agents perform worse on drag than general models (9.0%
vs. 18.0% on average), despite performing better on typ-
ing, suggesting that end-to-end web training underrepre-
sents rarer interactions such as dragging. Although drag is
our smallest family, the gap is large: pooled across agents,
drag reaches only 12.4% success, compared with 38.0% for
the next-weakest family, out-of-page I/O.
The failures are also highly localized. In 72% of failed
drag instances, the agent reaches the correct slider or can-
vas but fails during the gesture or immediately afterward
(Fig. 5). Dragging is typically planned open-loop from a
single screenshot, while the resulting value only becomes
visible after release, so small spatial errors can directly pro-

the untrained single agent (33.3% vs. 14.5%) (Fig. 6, right).
4.4. At matched size, our skill data matches or beats
task-centric data.
Does the gain come from skill-specific practice, or sim-
ply from training on more web trajectories? To test this,
we reimplemented InSTA’s trajectory collection pipeline on
MINIWEB [27] to collect a size-matched corpus of task-
centric trajectories of MINIWEB, which, like our skill data,
Qwen3.5-4B writes. We then train the same executor on
such corpus.
The task-centric executor does not signifi-
cantly improve over the untrained planner on any of the
four benchmarks, while our skill-trained executor does on
all four (Tab. 3). Head to head, our executor is ahead ev-
erywhere, and the gap is significant on Online-Mind2Web
(+10.7 points, p < 0.001) and held-out MINIWEB (+10.2,
p = 0.027; Holm p = 0.081). At this size, skill-centric data
is at least as useful as task-centric data, and it is the one that
reliably adds to planning.
5. Conclusion
In this paper, we introduce MINIWEB, a synthetic bench-
mark centered on 37 interaction primitives across 65 lo-
cally hosted websites, providing per-primitive evaluation
and skill-segmented data generation for web agents.
Its
skill profiles show that drag & gesture is the weakest skill
family of every agent we tested. Using this infrastructure,
MINIWEBGEN expands limited seed demonstrations into
3.1K verified trajectories for targeted skill practice. Fine-
tuning a compact base model on them improves the ex-
ecution of single primitives, but on its own it does not
raise success on multi-step tasks and lowers it on exter-
nal benchmarks, because the model learns single primitives
from single-primitive episodes, not how to chain them: it
stops after one primitive, and removing that stop alone does
not help. MINIWEBAGENT separates task planning from
practiced skill execution; without training on any target-
benchmark trajectories, it improves over the base model
on the held-out sites, WebArena-Lite, WebVoyager, and
Online-Mind2Web, and its trained executor adds to what
planning alone achieves, most on the held-out sites and
Online-Mind2Web. Our findings suggest that targeted skill
practice on synthetic websites, combined with an explicit
separation of planning and execution, helps compact open-
weight agents on websites they were not trained on.
6. Limitations & Future Works
We acknowledge several limitations in our study.
First,
MINIWEB contains fewer human-authored tasks than
Mind2Web [6] and WebArena [39]. Although our anno-
tation interface (Supp. D) streamlines task creation and tra-
jectory recording, devising diverse tasks still requires sub-
stantial effort and creativity.
MINIWEBGEN alleviates
training-data scarcity but does not replace broader human-
authored evaluation. Second, although parameterized ver-
ifiers reduce grading costs, running closed-source frontier
agents remains expensive. We therefore leave these agents
unevaluated, reflecting both resource constraints and our fo-
cus on small open-weight models. Third, we do not fully
resolve the drag & gesture deficiencies identified by our
benchmark. Our focus is on showing that improvements
across skill families, when composed, can improve task per-
formance on unseen websites, rather than achieving mastery
of any individual skill. We leave specialized methods for
mastering drag & gesture interactions to future work. Fi-
nally, this study does not include scaling experiments due to
compute and evaluation costs. Future work should investi-

gate how skill-centric training performs with larger datasets,
greater website diversity, and larger models.

A. Mining candidate macros from web-agent benchmarks
This section expands the first step of Sec. 3.1: it defines a macro (Supp. A.1), describes how candidate macros were mined
from the tasks of four web-agent benchmarks (Supp. A.2), reports what the mining found (Supp. A.3), and explains how the
candidates became the 37 primitives (Supp. A.4).
A.1. What is a macro?
We define a macro as the smallest unit of web interaction that carries a distinct, recurring intent. A macro occupies an
intermediate level of granularity between an atomic action (click, keystroke, or scroll) and a task, a high-level
natural-language goal that may require extended planning to fulfil. A macro is short-horizon: it realizes a single coherent
intent through a short, contiguous chain of atomic actions and requires no further decomposition into sub-goals. Crucially,
macros are written site-agnostically.
Structurally, each macro is a pair of a verb and a modifier, combined in snake_case as verb_modifier. The verb
denotes the primary goal of the interaction (e.g., navigate, search, extract, submit) and is drawn from a closed,
human-curated vocabulary V; the modifier specifies how the target of that goal is defined or structured (e.g., by_semantic,
from_free_text, by_attribute) and is drawn from a closed vocabulary M. A macro is therefore an element of a
curated subset of V × M.
Definition 1 (Macro). Let A denote the space of atomic web actions, and let a task be a sequence over A that fulfils a natural-
language goal on some website. A macro m = (v, µ), with v ∈V and µ ∈M, is a site-agnostic unit of web interaction
satisfying:
1. Single intent. m expresses exactly one intent;
2. Verifiable terminal state. Executing m reaches a single terminal state whose success is checkable by a single evaluator; and
3. Atomic minimality. Decomposing m yields only atomic actions in A—that is, m cannot be split into a chain of smaller
macros.
These conditions induce a strict granularity hierarchy, atomic action ≺macro ≺task: a task decomposes into a chain of
one or more macros, whereas a macro decomposes into a chain of atomic actions but admits no intermediate decomposition
into smaller macros.
A.2. Macro bank creation
We construct the macro bank through a combination of LLM-driven induction and human supervision. The procedure first
elicits a prior over the macro space by mining the tasks of four existing web-agent benchmarks (WebArena, WebVoyager,
Mind2Web, and WebShop), and then extends this seed bank to the domains of MINIWEB. The induction is orchestrated by
prompting Claude Opus 4.8 to operate over a relational store with four tables: a verb bank V, a modifier bank M, a macro
bank, and the pooled task set. The process proceeds in three stages.
First pass: reference-bank construction.
We pool the tasks from all four datasets into a single corpus and process them
iteratively. For each task, the agent reasons about the sub-goals required to accomplish it and proposes the macros, and where
necessary the constituent verbs and modifiers, needed to express those sub-goals. When an existing entry in V or M suffices,
the agent reuses it; otherwise it proposes a new verb or modifier and marks it as proposed. Throughout, the agent consults
the current state of the bank before each addition to avoid introducing redundant entries.
Deduplication.
Because the first pass admits proposed verbs and modifiers greedily, the resulting vocabularies contain
near-duplicates. The agent therefore reviews V and M and flags candidate duplications, which are then adjudicated by a
human annotator who either merges each entry into an existing verb or modifier or keeps it as distinct. This step yields the
curated vocabularies that fix the macro bank.
Second pass: task–macro assignment.
The macro assignments produced during the first pass are confounded by the order
in which tasks were processed, since the bank was still growing as tasks were seen. To remove this dependence, we discard
the first-pass assignments, fix the curated bank from the deduplication step, and prompt the agent to reassign macros to every
task from scratch, disregarding the prior assignments. Fixing the reference bank ensures that each task is labeled against the
same macro vocabulary, independent of its position in the corpus.

This procedure yields a seeded macro bank grounded in existing benchmarks. We then assign the seeded macros to each
website domain of MINIWEB and brainstorm additional macros, again with LLM assistance under human review, to cover
intents that the four source datasets do not exercise.

A.4. From candidates to primitives
The candidates describe what existing tasks ask for at the granularity of their instructions, so many differ only in the value
they target. In group brainstorming sessions we merged candidates that perform the same interaction on different values
(e.g., the 27 select candidates, such as select_by_color and select_by_size, are choices from a set of options),
removed site-specific ones, and separated reasoning from the physical interaction: the extract, compute, compare, and
verify candidates correspond to the reasoning operations of Supp. B, which are attached to the interaction they follow. We
then added interactions the benchmarks rarely or never exercise, such as dragging a slider, drawing a signature, uploading a
file, and editing a spreadsheet cell. This gave the initial set of 46 primitives in 7 skill families (Sec. 3.1). After annotation,
we kept the 37 primitives that annotators used at least 3 times (Supp. B).
Mapping the candidates to the final primitives.
To measure how often the benchmarks need each final primitive, we map
each of the 136 candidates to the final primitive that performs its interaction, or to none. Gemini 3.6 Flash proposes each
mapping from the candidate’s name, its number of labels, and three example tasks from the benchmarks that use it most, and
one of the authors checks every candidate. The author keeps 131 of the 136 mappings (96.3%, κ = 0.96; 99.7% of the labels).
The 5 changes cover 176 labels: posts and replies move from the free-text primitives to create_by_form, comparisons
of on-page values from compare_by_form to report_information, and a search form to sort_by_form. No
candidate maps to none. The price filter is the only candidate in the drag & gesture family, so dragging accounts for 0.3%
of the mined labels (at most 2.1%, in Mind2Web), against 7.6% of the primitive instances in MINIWEBGEN’s training
episodes. Tab. 1 (top) shows which primitives each dataset exercises. How evenly it exercises them is the effective number of
primitives, the exponential of the entropy of the primitive shares, which equals the number of primitives in use when all are
used equally. Excluding the reasoning primitive, which every information task ends with, the benchmarks’ labels spread over
3.4 (WebShop) to 9.6 (WebArena) of the 36 primitives and MINIWEBGEN’s trajectories over 32.8; on the 25 primitives that
some benchmark uses, they still spread over 23.1.

a base primitive, the physical interaction (e.g.,

macros in our code and in the induction pipeline of Supp. A.

C. Websites
MINIWEB has 65 websites in 15 domains, served offline by one local server. They share one fictional world (a city, Lakeport,
WA, and a company, Meridian Systems, recur across sites), so one task can move between sites. Six hubs carry the effects of

passwords. Twenty-one sites are seeded from public datasets; the other 44 hold synthetic data generated with fixed seeds.
Thirteen sites are held out: no training data comes from them, and they are used only for evaluation (Sec. 4).

D. Annotation interface
Six annotators wrote and recorded the 369 tasks in a web tool served next to the sites (Fig. 8). Its dashboard orders the work
in three steps: review each site and report bugs, annotate tasks, and build their verifiers. It also shows the current coverage of
every primitive, least covered first.
Annotating a task (Fig. 9).
The tool samples one to three sites and a set of primitives to cover, weighted toward primitives
with few tasks. The annotator first explores the sites freely, then designs the task as a graph in the editor below the browser:
one node per primitive instance with its subtask and reasoning operation, and edges for the order and data flow between
instances. Every primitive of a multi-primitive task must be connected. The annotator then writes the instruction in their own
words, sets the starting login and two-factor state, and records the task in the embedded browser. After recording, they mark
each instance’s span on the action timeline and enter the expected answer. Optional LLM helpers draft a task, rephrase an
instruction, or infer a primitive chain from it; their output is only a suggestion. Annotators can also propose a new primitive,
which is added to the registry for later review.
Building the verifier (Fig. 10).
For each primitive instance the verifier builder shows the gold HTTP requests from the
recording and a check scaffold: request gates, actions, visited pages, and an answer matcher. The annotator pins the values
the instruction dictates, marks the remaining checks as advisory, and tests the verifier in a sandbox: it must pass the gold
recording and should reject two negative controls, an empty trajectory and an answer given without any action.
Reviewing tasks.
The macro browser (Fig. 8b) steps through every recorded span of one primitive across all tasks. Review-
ers used it to make tags consistent across annotators. A task review page compares each task with its state before correction;
a reviewer marks it verified or stale, asks for a re-recording, or deletes it.
E. Grader validation
Every task is graded twice: by its parameterized verifiers, which check the backend request log, and by the VLM judge
(Gemini 3.5 Flash), which reads each primitive’s rubric, the request log, and the screenshots (Sec. 3.1; the judge’s prompt is
in Supp. K). We check both against human demonstrations and measure how often they agree on agent episodes.
Valid demonstrations.
A human recording can stand in for a correct episode only if it is current and complete. Of the
369 recordings, we leave out the 67 tagged as stale, which predate a change to their site, data, or task, and the 119 that the
task’s current verifier rejects, such as early recordings whose recorder missed the graded form submission or recordings made
before the task was edited. The remaining 183 recordings pass the verifier by construction.
Positives and negatives.
From each valid recording we build three cases: the recording with the annotator’s answer (should
pass); a near miss, the same recording cut just before its last required primitive instance and without an answer (should fail);
and an empty episode with no actions and no answer (should fail). Over these 549 cases, the verifiers are 98.9% accurate and
the judge 98.2%. The verifiers pass every positive and the judge 97.8% of them; both reject every empty episode, and each

Human audit of agent episodes.
The checks above use human recordings, which also supply the judge’s reference. To
test both graders on agent behavior, we sample 120 of the 3,759 episodes that the ten agents produced on an earlier version
of the task set (376 tasks, before the final review below), stratified by the two graders’ verdicts and oversampling their
disagreements, and a labeler passes or fails each primitive from the screenshots, the action log and the request log, without

Human demonstrations.
Annotators record tasks in an embedded browser (Supp. D). A script injected into every site
page records each action with its target element and parameters, every HTTP request the action triggers with its response,
and an observation after each change, while the server logs every request independently. Spans of primitive instances are
later marked on this action timeline.
MINIWEBGEN executor.
The executor writes a Python script against three objects, dom, act, and expect (prompt in
Supp. K). Only act changes the page, and each of its calls is recorded together with the screenshot taken just before it.
The restrictions are enforced by the sandbox rather than by the prompt. A static check rejects imports, private and dunder
attribute access, while loops, class definitions, and every direct browser or JavaScript call (e.g., evaluate, goto, fill).
The script runs with a minimal set of builtins. act refuses hidden, off-screen, occluded, or stale targets and any target not
returned by dom; keys are allow-listed, and besides the task’s start page the script can open only the pages its step names, by
typing the address as a recorded action. Click points are jittered inside the target, and drags follow a path with intermediate
waypoints. Privileged DOM access thus helps the executor find targets, but every recorded step is an action on what the
screenshot shows.
Agents.
Every arm we train or evaluate runs in the same browser-use harness, on MINIWEB, WebArena-Lite, WebVoyager,
and Online-Mind2Web alike. The state message holds the screenshot and the indexed interactive elements; the model outputs
a short memory and one action (flash mode; browser-use’s own planning, judge, and message compaction are off). The task
is given as “You are interacting with a web application at {start_url}. Your task: {task}”. We add three actions: drag and
draw for gestures, on the 0–1000 coordinate scale that Qwen3.5 grounds in natively, and macro_done, which ends one
step of a task. We remove the actions that bypass the page or need the open web: web search, LLM page extraction, in-page
text and selector search, JavaScript evaluation, file-system access, saving as PDF, and direct file upload (files are chosen in
the site’s file explorer). Generated trajectories are replayed in this harness to produce training rows, so each row has exactly
the observation and action format the agent sees at test time. The budget is 40 site actions on MINIWEB and WebArena-Lite
and 100 on the live web. In MINIWEBAGENT, the planner only looks, scrolls, delegates, and answers; each delegation runs
the executor for at most 15 actions in the same browser.

H. Live-web evaluation sets
We report WebVoyager and Online-Mind2Web on normalized subsets of 536 and 280 tasks that leave out tasks no agent can
complete from our network, and outdated tasks. Both subsets are fixed once and used for every configuration of Sec. 4. Every
removal depends on the website or on the task text, never on whether a configuration solved the task.
WebVoyager (643 →536 tasks).
Three steps, in this order:
• Impossible tasks (−48, 595 left). We start from the 595-task set that Fara-7B and MolmoWeb evaluate on [4, 12], which
drops 48 tasks they treat as impossible.
• A site that blocks our network (−43, 552 left). Cambridge Dictionary answers our browser with a Cloudflare check on
nearly every visit. In two full-set runs, of the family-specialist agent of Supp. G and of an earlier version of it, 93% of its
86 episodes end with a final answer that reports the check, against at most 2.4% on any of the other 14 sites.
• Outdated text (−16, 536 left). Fara’s task file refreshes the wording of 16 tasks that we ran with the original 2023–24 text.
We found them by comparing the task texts, not by looking at results.
As the official instructions require for time-sensitive tasks, we move the explicit 2023 and 2024 dates of 64 Booking and
Google Flights tasks forward by three years (e.g., December 2023 becomes December 2026), keeping the month, day, and
length of stay; dates without a year are left as written. Judging follows the official evaluation script: its prompts, the last 15
screenshots, and a failure when there is no answer, with GPT-4o in place of the retired gpt-4-vision-preview.
Online-Mind2Web (300 →280 tasks).
No impossible-task list is published for this benchmark, so we remove only web-
sites that gate our network. A site is set aside when at least half of its episodes, pooled over the same two full-set runs at 100
steps, end with a final answer that reports a network gate: Cloudflare, a CAPTCHA, access denied, press-and-hold, or human
verification. A CAPTCHA at a login or sign-up step does not count, since a task may not need the account, and only whole
sites are removed, never single episodes. Nine sites with 20 tasks meet the rule (Tab. 12). On the sites we keep, 5 of the 560
episodes report a gate, all on one site (apartments.com, 5 of 16). Judging uses WebJudge with o4-mini [34].
Browser and pacing.
Every configuration uses the same Chromium browser at 1280×800. On the live web it presents
itself as desktop Chrome and does not expose the automation flag; we never solve CAPTCHAs or otherwise get past a bot
check. On Online-Mind2Web, at most one episode runs on a site at a time, and two minutes pass between the end of one
episode on a site and the start of the next, because bot checks rose with the number of requests from one address. Location
defaults are kept.
Effect of the normalization.
The family-specialist agent of Supp. G, the one configuration we also ran on the full sets,
reaches 60.3% on all 643 WebVoyager tasks and 69.2% on the 536 (the judge accepts 17 of the 107 removed tasks), and
25.7% on all 300 Online-Mind2Web tasks and 26.1% on the 280. Our live-web numbers are therefore not comparable with
numbers reported on the full sets.

J.3. Why practice alone does not raise task success
Trained on episodes of one or two primitives, the single agent ends whole tasks early: its median episode shrinks from 18 to
9 steps on the held-out tasks, from 40 to 8 on WebArena-Lite, from 80 to 9 on WebVoyager, and from 100 to 14 on Online-
Mind2Web, while the untrained agent reaches its action budget in 56% of WebArena-Lite episodes. The trained agent’s
WebVoyager run used a 40-action budget instead of 100; 17% of its episodes reached it, so its WebVoyager number may be
slightly low, but its median episode (9 steps) is far below either budget.
J.4. Stop-early control
Trained on the same steps without each episode’s final done step, the single agent no longer stops early: its median episode
runs the whole 40-action budget on the held-out tasks and on WebArena-Lite, which it reaches in 96% of episodes on both.
Its task success does not rise: 34.4% on the held-out tasks against 39.2% with the done steps (p = 0.42) and 22.5% on
WebArena-Lite against 20.3% (p = 0.44), far below MINIWEBAGENT (58.1% and 36.4%; p < 10−3 for both). Removing
the early stop alone does not chain primitives into tasks. Without trained done steps it answers worse: on the 21 held-out
tasks that end in an answer it passes 23.8% against 34.9% with them. On the 41 tasks that need no answer, which the missing
steps cannot cost it, it passes 39.8% against 41.5% (p = 0.91) and 61.0% for MINIWEBAGENT (p = 0.007).
J.5. WebArena-Lite by site
Two training sites reuse WebArena’s Reddit and GitLab data (Tab. 8). Tab. 16 splits WebArena-Lite by site. Without the
Reddit and GitLab tasks, MINIWEBAGENT still gains 8.9 points over the untrained single agent (p = 0.001) and 4.8 over
the untrained planner (p = 0.10). Over the single agent the largest gain is on Reddit; over the untrained planner, the trained
executor gains most on GitLab and loses on Reddit.
J.6. Model calls
Planner turns do not count toward the site-action budget, so MINIWEBAGENT makes more model calls than the single agent
(Tab. 17). Its planner reaches its turn cap (25 on MINIWEB and WebArena-Lite, 60 on the live web) in 18%, 40%, 22%, and
30% of the episodes on the four benchmarks.
J.7. Robustness of the skill profiles
Counting only the primitive instances whose earlier primitives in the task all passed, so that a family is not penalized for
failures upstream of it, drag & gesture remains the weakest family for each of the ten agents. Averaged over the agents,
success by chain length stays within 3.8 points of the independent-primitive prediction pn at every length (Fig. 6, left). Among
the six agents with their own loops, five have a drag action in their released action spaces (Fara1.5-4B: left_click_drag;
MolmoWeb: drag_and_drop; UI-TARS-1.5-7B: drag; OpenCUA-7B: dragTo) and still pass at most 17% of drag
instances; Fara-7B’s has none, so its 0% is by construction. Graded by the task verifiers instead of the judge, drag & gesture
is the weakest family of every one of the ten agents; pooled over the agents, the verifiers pass 11.2% of drag instances against
34.8% for the next-weakest family.

J.8. Training and data details
The drag & gesture training data.
Of the drag & gesture trajectories in the training set, 100 draw signatures, 23 reposition
items, and 28 pan a map, all with real drags; 73 of the 74 slider trajectories set the value by clicking on the track, which the
sliders accept, and the playback and ranking trajectories use clicks.
Training details.
The executor is a rank-64 LoRA (α = 128, dropout 0.05) on the language model’s attention and MLP
projections, trained for one epoch on the 27,646 steps of D (3,128 plain trajectories, 857 two-trajectory chains, and 629
trajectories with an injected and corrected mistake), at learning rate 10−4 with a cosine schedule and a batch of 8 steps. The
task-centric executor uses the same recipe on 27,644 steps from 3,795 trajectories, collected on the 52 training sites with our
reimplementation of InSTA’s pipeline [27]. Gemini 3.5 Flash proposed 140 goal-level tasks per site from its home page; the
untrained Qwen3.5-4B attempted each in our harness, writing every step’s memory and action; Gemini 3.5 Flash judged each
episode from its screenshots, actions, the server’s request log and its data changes. In our skill data, the actions come from
MINIWEBGEN’s verified executions and Qwen3.5-4B writes each step’s memory when they are replayed, so both sets carry
the same model’s text. The judge accepted 4,308 of the 7,267 episodes, and trajectories were drawn from those round-robin
over the sites up to the step budget. On the 310 human tasks of the training sites, run by the same agent, this judge agrees
with the task verifiers on 87.1% of episodes, with 77.5% precision and 92.2% recall; our generated trajectories instead pass
a backend check by construction.
MINIWEBGEN yield.
Over the generation runs that produced the training pool, 6,384 candidate tasks were proposed,
5,432 passed a dry run on the site’s state, 4,467 were worded into instructions, and 4,011 were executed with the backend
showing the intended change, in 5,785 attempts (3,653 first-attempt successes). After removing near-duplicates and capping
trajectories per site, 3,428 were kept; 3,128 of them form the training pool (the rest were retired in review or did not replay in
the agent harness). Failed attempts were mostly a scripted action the page did not accept, such as a hidden, covered or stale
element (903), and a failed scripted check on the page (528); the backend check rejected 185.
Held-out sites.
The 13 held-out sites were fixed once, before any trajectory was generated. Three of the 62 held-out tasks
also use a training site (email, team chat, or the code editor) for a cross-site step.

K.1. Macro induction
The orchestrator prompt of the macro mining pipeline (Supp. A), given to Claude Opus 4.8. It runs the first pass, the
deduplication with a human annotator, and the second, order-free pass over the tasks of WebArena, Mind2Web, WebShop,
35


and WebVoyager.
Master Directive: Automated Macro Extraction Pipeline
System Context:
You are an autonomous orchestrator managing a multi-stage data extraction
pipeline. You are connected to a local SQLite database (macros.db). The schema is
pre-defined with strict relational constraints: the verbs and modifiers registries
only accept status IN ('seed', 'established', 'proposed').
Goal: Read the task datasets (WebArena, Mind2Web, WebShop, WebVoyager), extract a
unified macro action space without letting processing order bias the result,
execute database updates directly, facilitate a human-in-the-loop deduplication
phase, and finally plot an order-free discovery curve.
Two invariants that govern the whole pipeline (do not violate):
1. Independence during proposal. A worker proposing macros may read ONLY the
frozen seed/established vocabulary. It must NEVER read another worker's
proposed entries. All proposals from all workers and datasets meet for the
first time in Phase 2.
2. Order-freeness of all reported numbers. No coverage claim or curve may depend
on the order in which tasks or datasets were processed. Anything
order-sensitive is averaged over many random orderings.
Execution Strategy:
Split this workload and delegate to sub-agents or separate context sessions as
needed. Do not process all tasks in a single continuous loop. Track your state and
process in batches. Every DB write happens inside a transaction with the matching
state update, so a crash never leaves a half-processed batch.
Execute the following phases sequentially.
------------------------------------------------------------
Phase 0: Read and Understand
Read and understand the following, by priority:
- docs/macros_def.md
(authoritative). This is the frozen, reviewed definition;
the whole pipeline inherits its axis decision (intent, not mechanics), its
closed verb set, and its closed modifier vocabulary.
- docs/MiniWeb_brainstorm.pdf (loosely, for project intent only; the macro
definition in macros_def.md overrides anything here).
Confirm that macros.db is seeded BEFORE Phase 1: the seed verbs and modifiers must
come from the taxonomy backbone and blind brainstorm in macros_def.md, so the
vocabulary's origin is NOT any dataset. Do not start Phase 1 against an empty
registry.
------------------------------------------------------------
Phase 1: The Proposer (Independent Task Analysis and Extraction)
Delegate to one or more workers, in batches (e.g., 20 tasks per batch). Track which
task IDs are processed.
Objective: Iterate through unprocessed tasks in webarena_tasks, mind2web_tasks,
webshop_tasks, and webvoyager_tasks, and emit, per task, the macros involved --
proposing new vocabulary only when the frozen vocab genuinely cannot express the
intent.
Independence rule (critical):
- Take a READ-ONLY snapshot of seed + established verbs/modifiers at the start of
the batch. Match against THIS snapshot only.
- Workers must NOT query or reuse each other's proposed entries. Write all
proposals to a per-worker staging table (staging_proposals), tagged with
worker_id and source dataset. Nothing proposed is visible to any other worker.
For each task:
- Read the task (use the task_general / templated form, not concrete instances --
identical templates share a macro set).
- Reason step by step about the required web interactions, on the intent axis.
Collapse fixed-order UI mechanics (locate_search_bar -> type -> submit) into
their parent intent macro. Do not emit mechanics as macros (see macros_def.md,
"What is NOT a macro").
- Matching logic:
* If a required macro maps semantically to a seed/established
(verb, modifier) tuple in the snapshot, USE those IDs.
* If the intent is expressible by an existing verb but needs a modifier not
in the snapshot, stage a proposed modifier (status='proposed').
* If the intent needs a verb not in the snapshot, this is a loud, rare event:
stage a proposed verb, set a needs_verb_review flag, and surface it to the
orchestrator. Verb proposals are human-gated in Phase 2 and should be the
36


exception -- the verb set is meant to saturate small. A flood of verb
proposals means the seed was too thin (see Phase 1.5).
- Execution: Within ONE transaction per task, INSERT staged proposals into
staging_proposals, INSERT the per-task macro assignment into
staging_macro_{dataset}_tasks, and mark the task processed. Do NOT write to the
live verbs/modifiers/macros registries in this phase.
Continue batching until all tasks are processed.
Phase 1.5: Seed-adequacy gate
Before merging, count accepted-shaped proposals. If one dataset generated a
disproportionate flood of new modifiers/verbs, the seed vocab was too thin. Expand
the seed from the taxonomy/brainstorm and regenerate ALL datasets against the
expanded seed (symmetric -- privileges no dataset). Only proceed to Phase 2 once
proposal volume is sane.
------------------------------------------------------------
Phase 2: Deduplicator (Provenance-Blind, Human-in-the-Loop Merge)
Act as an interactive terminal assistant for this phase. Do not automate the final
decisions. This is the ONLY place proposals from different workers/datasets meet.
Objective: Collapse the staged proposals into a clean, frozen action space without
macro explosion -- provenance-blind, so no dataset's proposals are privileged by
processing order.
- Pool and strip provenance: Load ALL staging_proposals from ALL workers and
datasets into one set. Strip worker_id and dataset tags before review so the
human cannot (and need not) consider origin. Overlap/origin is never an input
to the merge.
- Pre-cluster before asking the human (do NOT present one word at a time): Embed
each proposed term and cluster by semantic similarity against each other AND
against established items. Present the human with groups, not isolated words --
e.g., "6 proposals resemble search: [list]. Suggest: merge all into search /
split into N / keep K as new."
- Interaction loop (per cluster):
* Print the cluster, your semantic analysis, and a suggested action.
* Prompt: (M)erge all into [suggestion], (S)plit (specify groups),
(A)ccept listed as new, or (D)rop?
* Pause and wait for human terminal input.
* needs_verb_review clusters are always shown explicitly and never
auto-suggested as merges.
- Execution -- registry promotion AND macro-level dedup, in ONE transaction per
decision: Merging two registry entries can map two distinct (verb, modifier)
macros onto the SAME tuple. This is a macro-level dedup, NOT a simple ID swap.
For each merge, in a single transaction:
1. Repoint references: UPDATE staging_macro_* (and macros) rows from the
dropped ID to the kept ID.
2. Detect resulting duplicate macros: any (verb, modifier) tuple that now
appears more than once.
3. Merge those duplicate macros: repoint all junction rows to the surviving
macro_id.
4. Only now DELETE the orphaned registry entry. Verify no FK/uniqueness
violation before COMMIT; ROLLBACK on conflict and re-present to the human.
* (A): UPDATE status proposed -> established.
* (D): drop the proposal and its staged assignments.
- Output: a fully established registry and a finalized macro table. Snapshot this
as an immutable artifact (frozen_vocab.json) -- Phase 3 reads the snapshot,
never the live DB.
------------------------------------------------------------
Phase 3: The Auditor (Symmetric Relabeling and Coverage Audit)
Delegate to a pool of analytical workers capable of parallel execution.
Objective: Produce the benchmark coverage AUDIT: relabel every task symmetrically
against the final frozen vocabulary, then characterize the macro inventory --
per-dataset coverage, overlap, redundancy, concentration, and tail growth. This
phase DESCRIBES the inventory; it does not test a hypothesis. Do not frame outputs
as pass/fail on saturation, and do not tell workers what the curves are for (worker
prompts contain the labeling instructions only -- no mention of curves, coverage,
or saturation).
- Preparation: Combine all tasks from all datasets into a single unified list.
- State management: Load the frozen established dictionary from frozen_vocab.json
as an immutable in-memory snapshot passed to every worker. Workers do not read
the live DB (no Phase-2 edit can race a Phase-3 read).
- Symmetric relabeling (this is the point of the phase): Phase-1 assignments were
made against per-worker snapshots that predate the merge; they are NOT
37


comparable across datasets. Remove them. Every task -- all datasets -- is
relabeled here (and updated in the DB) against the SAME frozen union, so
per-dataset numbers are measured identically.
* For each task, the worker assigns the macro sequence using ONLY the frozen
dictionary. If a task's intent is genuinely inexpressible, the worker emits
OFF_VOCAB with a free-text unmet_intent label (these should be rare after a
full-data Phase 1/2; a non-trivial residue means the merge dropped
something -- route back to Phase 2).
* Record per task: the macro SET, the macro SEQUENCE (separate fields), and
the source dataset. Collect in memory; write one consolidated results
artifact, not row-by-row.

Macro judge: rubric principles (data/macros.yaml)
rubric_principles:
scope: 'Judge ONE macro instance: its subtask, the task instruction, and the reference (gold) evidence for
that instance.'
evidence_order:
- server requests the site received (method, URL, body, status) -- the authoritative record of state changes
- the page the agent saw after acting (URL, visible text/state)
- the agent's own messages -- never decisive; a claimed success with no matching request or page state is a
fail, and a claimed failure does not undo a success the requests or pages show
outcome_over_path: A different route (menu vs search vs direct link, another control, another order) passes
when it reaches the same end state as the reference -- unless the instruction itself names the route or
control ("from the sharing options", "using the date filter"); then that route must be used.
targets_must_match: Values that identify WHAT was acted on (item/record ID, recipient, amount, date, option,
destination) must match the reference or the instruction. Incidental values (timestamps, generated IDs,
formatting, free-text wording the instruction does not dictate) may differ.
final_state: When the agent changed the same thing several times, judge the LAST state. This is about what
the agent changed (saved values, toggles, reactions); opening a page, dialog or menu is done once it was
opened, and navigating away afterwards does not undo it.
no_collateral: Unrequested destructive side effects fail the instance -- deleting, cancelling or overwriting
items the instruction did not ask for, even when the requested item was also handled.
server_over_screenshot: 'An accepted server response that confirms the state (e.g. a like request answered
"liked") outranks a screenshot; screenshots are taken at step time and can lag the page. Use screenshots
where the requests are silent or ambiguous.'
complete: Every element the subtask names must be done; partial completion fails.
accepted: 'A request counts only if the site accepted it: 2xx, or a 3xx redirect after a form submit.
4xx/5xx or a re-rendered form with an error does not count.'
reference_gaps: If the reference lacks evidence for something (recorder gap), judge that part from the
instruction instead.
