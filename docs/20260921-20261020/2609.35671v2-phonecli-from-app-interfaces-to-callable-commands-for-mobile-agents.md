## 摘要
移动 GUI 智能体通过感知—动作循环运行：每一步截取设备屏幕、调用视觉—语言模型（VLM）并发出动作。这种方式速度慢、成本高且脆弱，但其大部分工作其实是导航——而日常导航是静态的、有序的并且被无休止地重复。我们提出 PhoneCLI，它将应用的 GUI 导航编译为可调用命令，无需任何应用内部 API、运行时插桩或模型训练。离线阶段，PhoneCLI 从外部探索目标应用，并将其屏幕、交互元素和导航边提炼为带有语义标注的地图；每个屏幕生成一个确定性命令：一条到达该屏幕的重放序列。在线阶段，智能体选择一条命令，在执行前进行验证，然后以亚秒级时间确定性地执行，且 VLM 成本为零；开放式交互以及编译路径的每次失败都会回退到内嵌的 VLM 解释器，即纯 VLM 智能体，因此编译只会有益。在 AndroidLab 上，PhoneCLI 提高了任务成功率，同时减少了步骤数和 token 消耗，并且可迁移到 AndroidWorld 官方的 M3A 智能体，带来一致的效率提升。PhoneCLI 编译的是应用的导航而非单次运行，因此它能服务于新任务，而不仅是重复任务。

## Abstract
Mobile GUI agents operate through a perception--action loop: at each step they screenshot the device, invoke a vision--language model (VLM), and emit an action. It is slow, costly, and brittle, yet most of what it does is navigation---and everyday navigation is static, ordered, and endlessly repeated. We present PhoneCLI, which compiles an app's GUI navigation into callable commands, without any app-internal API, runtime instrumentation, or model training. Offline, PhoneCLI explores a target app from the outside and distills its screens, interactive elements, and navigation edges into a semantically annotated map; each screen yields one deterministic command: a replay sequence that reaches it. Online, the agent selects a command, verifies it before execution, and then executes it deterministically in sub-second time at zero VLM cost; open-ended interaction and every failure of the compiled path fall back to the embedded VLM interpreter, exactly the pure VLM agent, so compilation can only help. On AndroidLab, PhoneCLI improves the task success rate while reducing steps and token consumption, and it transfers to AndroidWorld's official M3A agent with consistent efficiency gains. What PhoneCLI compiles is the app's navigation rather than one run, so it serves new tasks, not only repeated ones.

# PhoneCLI 论文结构化总结

## 1. 核心问题与整体含义

- **背景痛点**：移动 GUI 智能体普遍采用“截图 → 调用 VLM → 输出动作”的感知—动作循环，每步耗时数秒、每步一次 API 调用，且易产生坐标幻觉与导航失败。
- **关键观察**：智能体的大量工作其实是**导航**，而日常 App 导航是静态、有序、高度重复的；导航骨架的变化远慢于内容变化。
- **三重挑战**：
  - **封闭性**：移动 App 是黑盒，不提供客户端可编程接口，无法像桌面那样使用 CLI/API/代码执行。
  - **重复性**：用户行为高度模式化，路径可离线枚举。
  - **泛化性**：训练路线需为每个新 App 采集数据或重训，面对百万级 App 不可行。
- **现有路线不足**：PreAct 在线编译“智能体做过的事”（仅复用同一任务）；UI-KOBE 运行时按 UI 图导航（智能体仍在环）；轨迹挖掘把路径作为文本提示回灌（复用仍需感知成本）。
- **核心命题**：把 App 的 GUI 导航**离线编译为可调用命令**，在线确定性重放；即“PreAct 编译智能体做过什么，PhoneCLI 编译 App 本身是什么”。

## 2. 方法论

### 2.1 核心思想
- **设计原则**：“把静态的构建一次，把非静态的即时处理”。
- **类比**：混合模式执行——高频代码 AOT 编译，其余按需解释；对应“编译（compilation）”与“解释（interpretation）”分工。
- **三阶段架构**：
  1. **离线编译**：外部探索 App，构建语义地图与命令目录。
  2. **在线调用**：路由选择命令 → 验证 → 确定性重放。
  3. **运行时解释**：VLM 兜底处理开放式交互与所有编译路径失败。

### 2.2 形式化定义
- App 地图：`G = (S, E, λ, M)`
  - `S`：发现的屏幕集合；`E`：交互元素（含归一化坐标）；`λ: E ⇀ S × Alias*`：元素到目标屏幕及别名的偏函数；`M`：每屏一条命令。
  - 命令 `c = [a₁, …, a_k]`：从干净启动到达目标屏的确定性动作序列。
- 命令目录 `C`：仅含稳定标识符、自然语言描述与目标，**不含坐标与动作步骤**，使路由在符号层而非计划层运作。
- 路由函数 `r(T, C) → (d, id, ans)`，四种决策：
  - `OP`：命令单独完成任务，重放后做可回答性检查；
  - `MACRO_VLM`：宏完成导航后移交 VLM；
  - `NEED_VLM`：无匹配命令，VLM 从当前状态探索；
  - `FINISH`：无需设备交互直接作答。

### 2.3 离线编译（Stage 1）
- **结构化探索**：从干净启动态 BFS 遍历，读取 UI 层级、记录交互元素、逐个激活并观察目标屏；可滚动页面探索多页；受深度与屏幕预算约束。
- **屏幕去重**：在语义标注前基于原始元素计算签名，避免共享底部导航栏导致不同 Tab 被合并。
- **语义富集**：LLM 将元素分类为 `STABLE`/`DYNAMIC`，赋予语义类型（button/input/label 等）与别名；为每屏生成自然语言描述。
- **编译为命令**：每屏一条命令，典型形式为 `force_stop → launch → tap/swipe（固定坐标 + 步间等待）`；可执行而非建议性，无模型在环；App 变更后可重建。

### 2.4 在线调用（Stage 2）
- **Phase I 选择**：任务 + 紧凑命令目录交给轻量 LLM；目录以前缀树压缩（共享路径合并、缩进展开），仅含元素路径、语义标签、稳定操作 ID，不含坐标与动作，防止路由“发明”设备级动作。
- **Phase II 验证**：执行前判断命令目标屏的自然语言描述是否与任务语义一致；不一致则拒绝并回退 VLM，避免“看似合理但错误”的重放浪费恢复轮次。
- **确定性重放**：模型决定“做什么”，程序保留“怎么做”；无感知、无模型调用、无法幻觉坐标，亚秒级完成。
- **完成方式**：
  - `OP` 路径：落地后做**可回答性检查**（与 Phase II 的“目的地是否匹配”性质不同），可答则直接返回；不可答则降级为 `MACRO_VLM`。
  - 移交时注入**着陆提示（landing hint）**：目标屏描述 + 交互元素列表 + 明确说明“仅完成导航、交互仍待执行”，实现暖启动。
- **落地检查**：重放后匹配当前 UI 层级与记录屏幕；若明显不相关则重启至干净态再交 VLM，确保不静默误导。
- **算法 1 流程**：构建目录 → 路由 → 按 `d` 分支 → 解析命令 → 验证（失败则 `INTERPRET`）→ 重启并重放 → 落地检查（失败则重启 + `INTERPRET`）→ `OP` 可答则返回，否则注入提示进入 `INTERPRET`。

### 2.5 运行时解释（Stage 3）
- **记忆机制**：每轮 VLM 响应附 `STATE_ASSESSMENT` 字段，历史评估按时间序注入下一轮提示，形成显式记忆。
- **恢复机制**：检测无进展行为（重复滚动/等待）并注入针对性提示（如尝试搜索入口、关闭广告浮层）；执行错误记录并在下一轮带纠正提示重现。
- **优雅降级**：编译路径不可用时统一运行纯 VLM 智能体；落地检查失败则从重启后的干净态开始。Stage 3 是设计上的协程而非最后手段，保证成功率不低于 VLM-only 基线。

## 6. 主要结论与发现

- **成功率提升且随主干变弱而增大**：Qwen3.7-Plus +12.3 分（50.7% → 63.0%），GLM-4.6V +3.2 分（41.3% → 44.5%），Kimi-K3 +0.8 分（68.8% → 69.6%）。
