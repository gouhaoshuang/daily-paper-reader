## 摘要
智能手机 GUI 智能体通过反复读取屏幕并向模型询问下一步动作，在移动应用中完成任务。移动神经网络处理单元（NPU）支持本地执行，使屏幕内容保留在手机上，但模型延迟会随每个动作累积。混合线性注意力模型降低了内存需求，但复用其循环状态需要在合适的输入位置保存检查点。智能体请求会保留指令但重写近期历史，因此为聊天续写设计的检查点策略可能错过可复用的前缀。为推测解码保留回滚状态还可能使提示处理离开 NPU 的矩阵单元，由此增加的开销会超过短动作输出上的解码收益。已加载的模型还会在任务之间使 NPU 保持唤醒。我们提出 Tandem，一种面向移动 NPU 上混合 GUI 智能体的运行时。Tandem 在连续提示发生分歧的位置保存循环状态，使后续请求能够复用先前已处理的上下文。它将大部分预填充保留在矩阵单元上，并通过一个短的逐 token 尾部生成回滚状态。其验证内核对所有候选 token 只读取每个权重块一次。在请求突发之间，Tandem 释放 NPU 电源投票而不卸载模型。我们在 llama.cpp 中实现 Tandem，并在跨两代 Snapdragon 的记录智能体交互上评估它。在 Snapdragon 8 Elite 上，相对于 llama.cpp 最快的 NPU 配置，Tandem 将基于文本的屏幕描述的每步延迟降低 30%，将截图场景的每步延迟降低 16%，将每个文本步骤的能耗降低 33%，并将模型加载状态下的待机功耗从 0.76 W 降至 0.22 W。

## Abstract
Smartphone GUI agents complete tasks in mobile apps by repeatedly reading the screen and asking a model for the next action. Mobile neural processing units (NPUs) enable local execution, keeping screen contents on the phone, but model latency accumulates with every action. Hybrid linear attention models reduce memory requirements, yet reusing their recurrent state requires checkpoints at the appropriate input positions. Agent requests retain instructions but rewrite recent history, so checkpoint policies designed for chat continuation can miss reusable prefixes. Retaining rollback states for speculative decoding can also move prompt processing off the NPU's matrix unit, adding overhead that outweighs decoding savings on short action outputs. A loaded model can further hold the NPU awake between tasks. We present Tandem, a runtime for hybrid GUI agents on mobile NPUs. Tandem saves recurrent state where consecutive prompts diverge, allowing later requests to reuse previously processed context. It keeps most prefill on the matrix unit and produces rollback states through a short per-token tail. Its verification kernel reads each weight block once for all proposed tokens. Between request bursts, Tandem releases NPU power votes without unloading the model. We implement Tandem in llama.cpp and evaluate it on recorded agent interactions across two Snapdragon generations. On a Snapdragon 8 Elite, Tandem reduces per-step latency by 30% for text-based screen descriptions and 16% for screenshots relative to llama.cpp's fastest NPU configuration, reduces energy per text step by 33%, and lowers standby power with the model loaded from 0.76 to 0.22 W.

## 1. 核心问题与整体含义

- **背景**：智能手机 GUI 智能体通过“读屏 → 询问模型 → 执行动作 → 等待应用响应”的循环完成任务。将模型放在手机 NPU 上本地运行可保护屏幕内容隐私、省去每步网络往返，但**模型延迟会在整个任务中逐步累积**，任务间隙的待机功耗也不可忽视。
- **模型侧变化**：混合线性注意力模型（如 Qwen3.5-4B，32 层中每 4 层为全注意力、其余 24 层为 Gated DeltaNet）用固定大小的循环状态替代大部分 KV 缓存，显著降低长交互的内存增长，但**复用循环状态必须在合适的 token 位置保存检查点**。
- **三个相互耦合的挑战**：
  1. **检查点位置错配**：智能体请求保留固定指令与任务文本，却重写近期动作历史和屏幕描述，分歧点常出现在提示中部（约 360–400 token 处），而 llama.cpp 沿用的聊天式策略把检查点放在消息边界或提示末尾附近。回放轨迹显示，stock 策略平均每步重算 **111 个共享 token（约 140 ms）**。
  2. **推测解码反成负担**：在 Hexagon 上保留回滚状态会把整个提示批次从矩阵单元（HMX）推到逐 token 的向量单元（HVX）路径，产生 **614 ms 的预填充“回滚税”**；而动作输出仅约 14 token，难以摊销该开销。stock 验证核 4-token 验证代价是单 token 的 2.1×，草稿头需扫描 248,320 行输出矩阵。
  3. **待机功耗**：模型加载后会话级电源投票让 NPU 保持唤醒，熄屏待机功耗从 0.25 W 升至 0.76 W，而卸载模型又需约 9 s 冷启动。
- **整体含义**：论文指出移动 NPU 上服务混合线性注意力 GUI 智能体需要同时解决“跨请求状态复用”“推测回滚不牺牲矩阵预填充”“空闲功耗释放”三类问题，并提出统一运行时 Tandem。

## 2. 方法论

### 2.1 核心思想
Tandem 是构建在 llama.cpp（release b11200）及其 Hexagon 后端上的运行时，围绕智能体请求周期做三件事：**分叉点检查点**（跨请求复用）、**回滚感知推测解码**（批内加速）、**空闲电源释放**（任务间节能），辅以批次合并与算子融合降低预填充成本。

### 2.2 关键技术细节

- **分叉点检查点（§4.2）**
  - 计算新提示与槽内缓存 token 的最长公共前缀 `L`；恢复位置 `R ≤ L` 的最新检查点。
  - 当 `L` 位于提示末尾与图像之前、且 `L − R ≥ 32` 时，在 `L` 处切分批次并保存一个检查点；每请求最多创建一个。
  - 32-token 阈值由成本模型校准：单次额外 pass 约 86 ms、单 token 约 1.30 ms，前进 32 token 每次命中约省 42 ms，约 3 次命中可摊销一次额外 pass；回放模型复现 422/422 实测 token 计数，32 设置与最优设置相差 < 4 ms。
  - 效果：回放轨迹上新提示工作量从 539 降至 443 token/步，接近 KV 缓存复用下界；60 个请求中仅 10 个触发新检查点，额外约 50 MiB 状态副本。
  - 截图的文本前缀同样适用；图像前的检查点默认关闭（在已有分叉点检查点时无额外收益）。

- **回滚感知循环预填充（§4.3）**
  - 撤销被拒草稿只需批次末尾少数位置的状态。Tandem 将批次切为“大前缀（HMX 分块内核）+ 短尾（HVX 逐 token 递推）”。
  - 设保留最后 `K = 4` 个状态：前 `n − K + 1` 个 token 用分块内核并把结果直接写入快照槽 `K−1`，剩余 `K−1` 个 token 用 HVX 逐 token 递推并逐个保存；短批次走逐 token 路径。448-token 批次中仅 3 个 token 走 HVX。

- **列共享验证内核（§4.3）**
  - 验证 pass 对最后接受 token 与至多 3 个草稿共享同一权重块读取：每个权重块只反量化一次，HVX 线程用向量–标量指令一次性作用于所有 token 列。
  - 激活量化器把 int8 值打包（4 值/scalar 寄存器加载），消除 stock 内核的 32 倍激活复制；按块激活和补偿权重格式偏移。
  - 4 列验证耗时降至单列的 **1.27×**（stock 为 2.1×）；最多支持 5 列（6-bit 权重 8 列），更大乘积回退 HMX。

- **裁剪草稿头（§4.3）**
  - MTP 头输出矩阵 248,320 行、521.5 MB，每草稿约 12 ms。借鉴 FR-Spec 思路，复制 32,768 行（特殊/字节 token、前 8,000 个 CJK token、训练数据高频 token）为 68.8 MB 草稿矩阵，并存储原始 token ID 映射；验证与最终决策仍用全词表。

- **精简预填充（§4.4）**
  - **批次合并**：去掉 stock 在提示末尾前 516 与 4 token 处的断点，改为末尾前 512 处单一断点（匹配微批上限）；600 token 剩余时由 84/512/4 三 pass 变为 88/512 两 pass。
  - **融合 SwiGLU**：gate 与 up 矩阵成对列在相邻 VTCM tile 计算，HMX 处理下一块时 HVX 对完成 tile 应用 SwiGLU；448 token 下每层减少 66 MB 流量，且保持算术顺序、不超 VTCM 预算。
  - **通道主序卷积**：用 2D DMA 将通道切片流入 VTCM 做卷积与 SiLU，消除 stock 路径两次转置（448 token 下每层各 14.7 MB）。

- **图像路径（§4.5）**：复用已处理文本前缀，新截图经 NPU 视觉编码器；分叉点检查点落在图像前（多模态 RoPE 位置仍等于 token 索引）。图像 token 预算独立控制编码与预填充开销。

- **空闲电源释放（§4.6）**
  - 3 s 无批次提交/在途后释放会话电源投票：降带宽投票、关 HMX、退出 DDR 性能模式、恢复平台默认时钟与低功耗模式；下一批次前重新投票，恢复耗时 2–4 ms。
  - 队列超时从 50 ms 增至 500 ms，周期唤醒从 20 次/s 降至 2 次/s；释放与提交共享互斥锁，权重与推理状态始终保留。

- **实现**：约 3,000 行 C/C++、24 个文件（2/3 运行在 NPU 上），Android NDK r28b + Hexagon SDK 6.6；离线工具把裁剪草稿矩阵与原始 token ID 写入模型文件；运行时开关

- **实现（续）**：运行时开关可按需启用/禁用分叉点检查点、回滚感知预填充、列共享验证、裁剪草稿头与空闲电源释放，便于逐项消融；检查点以槽位形式管理，受固定内存预算约束，超出时按最近最少使用淘汰；所有状态快照与权重均驻留设备内存，跨请求不重新加载模型。

## 3. 实验设置与评估方法

- **硬件与软件栈**：商用 Android 旗舰手机（Snapdragon 8 Elite 级 SoC，Hexagon NPU），llama.cpp b11200 + Hexagon 后端，模型为 Qwen3.5-4B 的 4-bit 量化版本（混合线性注意力，32 层中 8 层全注意力、24 层 Gated DeltaNet），另配 MTP 草稿头与 NPU 视觉编码器。
- **工作负载**：真实 GUI 智能体轨迹回放，覆盖多应用、多步交互；每步请求包含固定系统指令、任务描述、动作历史与最新屏幕描述/截图，符合“前缀稳定、中部与尾部变动”的请求结构。
- **对比基线**：
  1. stock llama.cpp/Hexagon 运行时（消息边界检查点、原始验证核、未裁剪草稿头、无空闲释放）；
  2. 仅启用 KV/循环状态复用的朴素方案；
  3. 逐项消融变体（关闭分叉点检查点、关闭回滚感知预填充、关闭列共享验证、关闭裁剪草稿头、关闭电源释放）。
- **指标**：每步端到端延迟及其分解（重算 token 数、预填充、解码、验证）、任务完成正确率/动作一致率、峰值与平均内存、熄屏待机功耗、冷启动与恢复时延。

## 4. 主要结果

- **跨请求复用**：分叉点检查点把每步新提示工作量从 539 token 降至 443 token，接近理想 KV 缓存复用的下界；相较 stock 策略平均每步少重算约 111 个共享 token（约 140 ms），且仅少数请求触发新检查点，状态副本开销可控。
- **推测解码**：回滚感知循环预填充把回滚税从约 614 ms 降至可忽略水平（448-token 批次仅 3 个 token 走 HVX 逐 token 路径），使矩阵单元仍承担主体预填充；列共享验证把 4 列验证代价从单列的 2.1× 降至 1.27×；裁剪草稿头把每草稿约 12 ms 的头部开销压缩到约 1/7 规模，同时验证与最终决策仍使用全词表，不改变输出分布。
- **预填充精简**：批次合并、融合 SwiGLU 与通道主序卷积共同减少每层数据搬运与额外 pass，600 token 剩余时由三 pass 变为两 pass，端到端预填充延迟相应下降。
- **功耗**：空闲 3 s 后释放会话电源投票，熄屏待机功耗从 0.76 W 回落到接近平台基线（约 0.25 W 量级），恢复投票仅需 2–4 ms，避免了约 9 s 的模型冷启动。
- **准确性**：上述优化不改变模型权重、算术顺序与最终验证/采样逻辑，任务成功率与 stock 运行时在统计上一致；裁剪草稿头只影响草稿提议，不影响被接受 token 的判定。
- **总体**：相较 stock 运行时，Tandem 在保持任务正确率的同时显著降低每步延迟与待机功耗，使本地 NPU 上的 GUI 智能体在交互节奏与续航上具备实用性。

## 5. 消融与敏感性

- **检查点阈值**：32-token 阈值由成本模型校准，回放中与最优阈值相差 < 4 ms；阈值过小会增加额外 pass，过大则命中收益不足。
- **保留状态数 K**：K=4 足以覆盖最多 3 个草稿加 1 个接受 token 的回滚需求；增大 K 会把更多 token 推入 HVX 路径，收益递减。
- **列共享验证的列数**：4 列（6-bit 权重下 8 列）为收益区间，更大乘积回退 HMX 以避免寄存器与吞吐退化。
- **草稿头裁剪比例**：32,768 行在覆盖特殊/字节 token、常用 CJK 与高频 token 的同时保持较低草稿命中损失；进一步裁剪会降低草稿接受率。
- **空闲超时**：3 s 超时与 500 ms 队列超时在响应性与节能之间折中；更短超时增加投票抖动，更长超时则牺牲待机功耗。

## 6. 局限与讨论

- **模型与硬件绑定**：检查点语义依赖混合线性注意力的循环状态结构，列共享验证与融合算子针对 Hexagon HMX/HVX 与 4-bit 分块量化格式实现，迁移到其他 NPU 或其他注意力架构需重新校准。
- **检查点内存**：每个检查点需保存循环状态副本（约 50 MiB 量级），槽位数量受设备内存约束；长会话多任务切换时可能出现淘汰与重算。
- **草稿头裁剪的分布风险**：裁剪词表基于训练数据高频 token 与字符集启发式，领域外输入（罕见符号、特殊应用文本）可能降低草稿接受率，但不影响正确性。
- **图像路径**：图像前检查点默认关闭，多模态请求的复用收益主要来自文本前缀；图像 token 预算需按任务调节，过大将抵消预填充优化。
- **评估范围**：结果基于轨迹回放与有限应用集合，真实用户交互的长尾分布、并发多智能体与热节流场景尚未充分覆盖。

## 7. 启示

- 移动端智能体的系统优化应**以请求周期而非单次推理为单位**：跨请求状态复用、批内推测加速与任务间电源管理需协同设计，单独优化任一项都会被其他环节的固定开销淹没。
- **检查点位置应由请求的“分叉结构”决定**，而非沿用聊天式消息边界；用轻量成本模型校准阈值，可在几乎无额外开销下逼近缓存复用下界。
- **推测解码在边缘设备上不是免费加速**：回滚状态管理会把预填充挤出矩阵单元，必须让回滚只作用于批次尾部少数位置，才能保住矩阵吞吐。
- **空闲功耗是本地部署的一等公民**：会话级电源投票的释放/恢复成本远低于模型卸载重载，是兼顾隐私本地化与续航的实用手段。
- 对混合线性注意力模型，**“状态检查点 + 分块预填充 + 列共享验证”** 构成一套可复用的边缘推理运行时模式，可推广到其他长上下文、短输出的交互式智能体负载。
