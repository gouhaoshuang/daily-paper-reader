# Nexus: An Execution Fabric for AI Agents Across Cloud, Edge, and Devices 

Nexilume Research 

September 2026 

Abstract 

Language-model agents are evolving into long-running services that interact with models, tools, computers, mobile devices, and distributed environments. Existing agent frameworks simplify reasoning and tool invocation. However, cloud-centric designs face three limitations: centralized execution increases failure impact, scaling pressure, and compute cost; extending agents across computers, mobile devices, and edge environments requires a unified execution abstraction with permission control; and long-running executions require consistent lifecycle management across failures, recovery, results, usage, and settlement. We present Nexus, a cloud–edge platform for deploying and operating agent services. To reduce dependence on centralized serving, Nexus extends agent execution to distributed edge infrastructure through an OpenWrt-based runtime, where edge nodes register their available service and computation capabilities and remain accessible through a unified invocation interface. To support heterogeneous environments, Nexus separates agent reasoning from environment-specific execution and uses run-scoped delegation to bind Computer, Mobile, and other resource operations to explicitly authorized subjects, devices, and capabilities. To manage long-running executions, Nexus represents each invocation as a persistent task and jointly tracks its execution state, intermediate events, outputs, failures, recovery state, resource usage, and charging records across cloud and edge components. We evaluate Nexus using controlled workloads, device interactions, and model-driven workflows. For a 16-MiB, 32-round hashing task arriving once per second with a two-second deadline, both capacity experiments pass all batches at a tested Cloud CPU ceiling of 0.25 vCPU with additional edge execution, compared with 2 vCPU for Cloud execution. Ten five-action Computer–Android workflows produce the expected artifacts, and all six live-revocation cases block the subsequent write while retaining an already-authorized read. Under worker loss, operation journaling reduces duplicate appends from six per task to zero, with 0.933 s mean normal-path overhead. Across 24 pairs using the same model and device backend, Nexus completes 24 tasks and Dify completes 22; among the 22 jointly successful pairs, Nexus’s observed completion time is lower by a median 3.88 s. Dapr provides lower successful-call latency in a separate service workload, while Nexus completes under a smaller tested incremental-runtime memory ceiling, 16 MiB versus 64 MiB. The results show how data locality, operation-scoped authority, and persistent result identity support Agent services across cloud and edge resources, with workload-dependent resource and execution costs. a

# 1 Introduction 

Language-model agents combine reasoning with tool use and external state, supporting applications in software development, information retrieval, and interactive task execution [1–3]. Deploying these agents as reusable services requires coordinating not only model inference but also the distributed resources on which their actions depend. For example, a reporting agent may process files on a workstation, consult a hosted model to generate a report, and submit it through a mobile application on the caller’s device. Although these steps serve a single request, they span different execution hosts, user-owned environments, and service interfaces. Reliable service execution therefore requires making these resources accessible, restricting agent actions to authorized environments and operations, and preserving the association between each request, its actions, and their outcomes across interruptions. Existing work provides complementary abstractions for constructing and operating agents. ReAct and Toolformer connect language models to external actions [1, 2], while AutoGen and Dify support agent interaction and workflow orchestration [3, 4]. For distributed execution, Ray schedules tasks and actors across cluster nodes, and Dapr provides service discovery, invocation, and access control [5, 6]. For interaction with external resources, the Model Context Protocol (MCP) standardizes tool and resource interfaces, with the host coordinating connections, permissions, and user consent [7]. For execution continuity, LangGraph persists workflow state and completed node outputs, allowing interrupted workflows to resume without rerunning successfully recorded work [8]. Together, these approaches provide foundations for distributed serving, controlled tool invocation, and workflow recovery. However, as shown in Figure 1, extending these abstractions to independently managed edge resources requires additional coordination across network access, environment actions, and execution lifecycles. Service discovery identifies an endpoint, but making an edge-hosted agent callable across network address translation (NAT) and public IPv6 also requires suitable reachability mechanisms and endpoint deployment support. Hosting all execution in the cloud simplifies some of these requirements but retains dependence on centrally provisioned capacity and shared failure domains. Likewise, permission to invoke a tool service does not by itself specify which caller-owned computer or mobile device should perform an action, or whether that action remains authorized when dispatched. Workflow persistence addresses another boundary: it preserves recorded progress, but does not make a completion record atomic with an external file write or device action. A failure between the action and its recorded completion can therefore leave retry safety unresolved, even when the workflow state is recoverable. The remaining problem is to maintain the association among an agent’s service endpoint, its

authorized environment actions, and their execution outcomes throughout invocation, recovery, result delivery, and accounting, without requiring all computation to share a hosting environment. Our key observation is that distributed execution need not fragment service access, resource authority, or invocation continuity . First, calling a cloud model or agent does not require subsequent computation to remain in the cloud: edge-hosted capabilities can be exposed through the same service interface, allowing distributed resources to supplement centralized serving. Second, the host running an agent’s reasoning loop need not determine which environments it can access: resource selection and permissions can instead be associated with the caller’s invocation, allowing the same agent to operate in different authorized environments. Third, the lifetime of an invocation need not coincide with that of a particular process or connection: its identity and recorded progress can persist across execution attempts, retaining the association among completed work, outputs, usage, and charges. These separations suggest that agent execution can extend to distributed resources while service access, authorization, and lifecycle state remain jointly managed. Realizing this opportunity requires addressing three challenges. First, distributed serving must make edge-hosted agents uniformly addressable and invocable despite differences in capabilities, connectivity, and resource limits. Agents may reside behind network address translation (NAT) or be accessible through public IPv6. Bridging these network conditions must preserve a common service interface without requiring centralized execution or replicating a complete cloud service stack at every endpoint. Second, agents must be able to perform actions in caller-selected environments without conflating connectivity with authority. Executing commands, accessing files, navigating browsers, and operating mobile applications involve different action semantics and execution contexts. The system must dispatch each action to the intended environment, return results or observations to the agent, and enforce resource bindings and permissions throughout the interaction rather than treating an established connection as unrestricted access. Third, agent lifecycle management must preserve continuity between an invocation and the actions performed on its behalf across interaction, interruption, recovery, and completion. An action may take effect before a failure prevents its completion from being recorded, making replay potentially duplicative and abandonment potentially wasteful. Persistent task state alone is therefore insufficient: the system must distinguish recorded completion from uncertain effects, determine when actions can be safely retried, and keep recovered progress, outputs, usage, and charges associated with the originating invocation. We present Nexus, a cloud–edge platform that combines agent routing, authorized environment interaction, and persistent lifecycle management. To make distributed agents accessible across network boundaries, we design an agent-routing protocol implemented natively on the OpenWrt router operating system. The protocol maps agent identities and advertised capabilities—the operations they provide—to reachable endpoints through inter-router route exchange and registrations that expire unless renewed. It supports outbound relay connections for agents behind NAT and direct access over public IPv6; where address provisioning and network ingress permit, each published agent can be bound to a dedicated public IPv6 address. Shared registration and routing on OpenWrt, together with cloud service management, allow endpoints to execute agent operations without replicating the complete service stack. To enable agents to act in heterogeneous environments, a shared software development kit (SDK) exposes caller-selected computers, browsers, workspaces, and mobile devices through action interfaces. Environment-specific adapters dispatch commands, file operations, browser interactions, and mobile actions to the selected environment and return results or observations to the agent, allowing its reasoning loop to operate independently of the device performing the action. Invocation-scoped delegation binds actions to the caller, selected resources, and permitted operations; binding validation and permission checks govern dispatch, with live revalidation on supported execution paths. To manage the agent service lifecycle, the cloud layer connects publication and invocation with persistent execution state, user interaction, recovery, output retention, and settlement. Each invocation establishes a run—a persistent execution context that associates execution attempts, reported progress, outputs, and usage with the originating request. For actions registered through the SDK’s recovery interface, stable operation identifiers link recorded outcomes to that run. Recovery reuses recorded results instead of repeating completed actions and suspends unsafe automatic replay when external effects remain uncertain. Cooperating resources that enforce duplicate suppression can additionally use these identifiers to recognize retries without repeating previously applied effects. Outputs and usage reports remain associated with the original invocation, while pricing terms captured at invocation and cost reports checked against configured limits govern settlement. The SDK exposes environment actions and lifecycle operations alongside model and file interfaces, reducing the deployment-specific control and recovery logic required in task handlers. We evaluate how these mechanisms affect serving capacity, environment actions, and execution continuity (Section 5). # 2 Related Work 

2.1 Agent reasoning, tools, and communication 

Research on language-model agents studies how models select actions and use the resulting observations. ReAct alternates reasoning with external actions so that observations can inform subsequent decisions [1]. Toolformer learns which tools to call, when to call them, and how to incorporate their outputs [2]. Wang et al. organize agent designs around role specification, memory, planning, and action [9]. At the application level, AutoGen supports programmable conversations among agents, AgentScope provides reusable components for tool use and agent interaction, and Dify supports visual workflow construction and model and tool integration [3, 4, 10]. These approaches support the decision-making and application logic that Nexus deploys and connects to distributed execution resources. Communication protocols make independently implemented components interoperate. The Model Context Protocol (MCP) connects a host application to servers exposing tools and contextual resources through clients that manage individual connections. The host coordinates permissions and user consent [7]. The Agent2Agent (A2A) protocol standardizes communication between agents, including descriptions of available capabilities,

task-status updates, result exchange, and authentication requirements [11]. These protocols therefore provide more than message formats. Nexus complements them by mapping supported protocol operations to registered agent services and coordinating their network routes, caller-selected execution environments, and invocation records. Here, an invocation denotes one admitted request to an agent service, which may produce multiple actions and execution attempts. 

2.2 Distributed execution and edge service routing 

Distributed runtimes separate application logic from the machines executing it. Ray provides remote tasks, which execute functions, and actors, which retain state across method calls [5]. Ray Serve builds on this runtime to distribute requests among service replicas—multiple running instances of a deployment—and adjust their number with demand [12]. Service-based routing similarly separates a service identity from a fixed host address: requests identify the desired service, and the network directs them to an available instance at the edge [13]. Dapr provides service discovery and invocation through a sidecar, a helper process associated with an application that handles communication on its behalf [6]. Istio manages a service mesh, a communication layer that applies routing, security, and monitoring policies across services; Envoy provides a proxy that forwards and controls service traffic [14, 15]. At the model-access layer, Portkey Gateway routes inference requests among model providers and supports retries and response caching [16]. These systems address related but distinct routing targets: distributed computations, application services, and model requests. Nexus focuses on making agents hosted on independently managed edge resources callable through a common interface. Its OpenWrt-based routing protocol maps agent identities and capabilities—the operations an agent provides—to eligible execution endpoints. Registrations expire unless renewed, while route exchange maintains information about remote services. Relay paths support endpoints behind network address translation (NAT), which translates private network addresses and can restrict incoming connections; direct paths support publicly reachable Internet Protocol version 6 (IPv6) endpoints. The distinction is the coordination of agent-specific service access with device authorization and invocation continuity, rather than assuming that service discovery or distributed execution is itself new. 

2.3 Environment interaction and authorization 

Agent actions must be mapped to concrete execution environments. AgentScope, for example, supports tool interaction and sandboxed execution, in which operations run in an isolated environment [10]. Isolation and resource authorization address different questions: the former limits an operation’s effects within an execution environment, while the latter determines which environment and operations a caller may use. Nexus connects agent actions to caller-selected computers, browsers, workspaces, and mobile devices, and returns their results or observations to the reasoning process. This design follows established access-control principles. Zero-trust architecture requires access decisions to depend on the requesting identity and target resource rather than network location alone [17]. Transport Layer Security (TLS) 1.3 protects communication against eavesdropping and tampering and supports peer authentication [18]. OAuth grants limited resource access through tokens. Its resource-indicator extension identifies the servers for which a token is intended, enabling access to be restricted to those recipients [19]. Such channel and credential protections must be combined with application-level rules specifying which device an agent may operate and which actions it may perform. Nexus applies these principles through invocation-scoped delegation: permissions are associated with a particular caller, selected resources, and admitted agent request. Environment-specific adapters preserve operation semantics, while binding checks and live permission revalidation constrain action dispatch on supported paths. 

2.4 Persistent execution and agent service lifecycles 

Agent runtimes also manage resources and execution progress. AIOS provides shared services for scheduling agent requests, managing context and memory, and controlling resource access through a software development kit (SDK) [20]. LangGraph supports checkpoints, which save workflow state for later resumption, and retains outputs from completed workflow steps so that those steps need not be repeated after an interruption [8]. Dapr Workflow reconstructs execution from recorded history and reuses completed task results. Its activity functions, which perform external work, can execute more than once; the documentation therefore recommends idempotent activities, for which repeating a request does not change the intended outcome [21]. These mechanisms motivate a distinction between recovering recorded progress and determining whether an external action can safely be repeated. # 3 System Overview 

Nexus connects distributed agent services and caller-selected execution environments through a shared invocation lifecycle. Figure 2 shows its four components. The OpenWrt routing layer makes edge-hosted agents discoverable and reachable; environment adapters execute authorized device actions and return results or observations; a shared software development kit (SDK) exposes these facilities to agent code; and the cloud layer manages service publication, invocation state, output retention, and accounting. The SDK runs within the agent process, which may be hosted in a cloud container or deployed on an edge endpoint. This organization separates where an agent executes from how its service is accessed, its actions are authorized, and its lifecycle is managed. An owner first deploys an agent handler and declares its capabilities, the operations that the service accepts. Edge-hosted agents register these capabilities with OpenWrt using leases, which are time-limited registrations that must be renewed. Route exchange makes registered services known to other participating routers, while cloud publication makes them available to authorized callers. The routing layer maps agent requests to eligible endpoints through local, relayed, or direct IPv6 paths. Relay access supports endpoints behind network address translation (NAT); public IPv6 access supports direct entry points, including dedicated per-agent addresses where network provisioning permits. Model access is configured separately, so invoking a hosted model does not require the agent handler to execute in the cloud. When invoking a published agent, the caller selects the required execution environments and grants permitted operations. Admission checks access and establishes a run—a persistent execution context associating the request with its caller, agent deployment, selected resources, and applicable pricing terms. The platform invokes the handler through the selected service path and supplies this context. Through the SDK, the agent can issue computer commands, access workspace files, navigate a browser, or operate a mobile application. Environment-specific adapters dispatch actions to the selected resources and return results or observations for subsequent reasoning. Resource-binding and permission checks constrain dispatch, with live revalidation on supported paths. A reachable device is therefore not automatically an authorized execution environment.

# 4 System Design 

4.1 OpenWrt-native agent routing 

The OpenWrt component implements the routing layer in Section 3. An agent exposes named operations, called capabilities , through an endpoint , the network entry point receiving requests. The routing layer selects an eligible endpoint and delivers an invocation , a request to execute an operation, to its handler , the code implementing it. OpenWrt is a Linux-based router operating system: ordinary Internet Protocol (IP) forwarding reaches a network address, whereas agent routing selects which service may perform the requested work. The routing service, agentd , maintains service records and policies; the invocation gateway, agent-gw , checks requests and forwards them using these decisions (Figure 3). Handlers may run on the router or nearby servers without hosting model inference there. Cloud manages publication and persistent invocation records, while environment adapters separately authorize the handlers’ device actions. 

4.1.1 Registering and sharing agent services 

A registration specifies an operation name and interface version, origin, endpoint, access restrictions, and a 

lease , the period for which the registration remains valid without renewal. The software development kit (SDK) renews registrations, re-registers missing records, and withdraws them when a managed server stops. Expiry immediately removes eligibility; health checks separately exclude temporarily unhealthy endpoints. Registration therefore establishes a candidate route, not guaranteed availability or permission for every request. Discovery identifies candidate routers; approval makes them peers permitted to exchange routes. 4.1.2 Selecting and reaching an agent 

Protocol adapters translate supported external calls into a common request containing the operation and routing context. The Model Context Protocol (MCP) exposes tools and resources; Agent2Agent (A2A) supports communication between agents. Their supported entry points are mapped by protocol, addressed service, and configured operation, not inferred from prompts. Native and translated requests then share the same eligibility checks. Selection separates permission from preference. In authenticated configurations, the gateway verifies the requesting agent and its tenant , the administrative group governing access and resource limits. Rules match tenant, source agent, and operation; highest priority wins, with rule identifiers breaking ties. A selected deny rule rejects the request rather than falling through to a weaker allow rule. Allowed requests filter candidates by capability, liveness, and constraints on region, latency, cost, load, trust, and permitted paths. Lookup by route identifier or operation name reduces search work without bypassing checks. Limits on request rates and simultaneous execution additionally bound request admission.

> 4.1.3 Recovering connections and routing state

Connection recovery should contact an existing task rather than start a new execution. For asynchronous calls, which acknowledge acceptance before completion, the destination returns a task identifier and access token. Later queries and control requests retain that identity and the original routing constraints, allowing a surviving execution process with retained state to be contacted without resubmitting the work. A lost acceptance reply remains ambiguous, and process termination or record expiry can remove control state. The evaluated capacity-limited implementation preserves unexpired records during lookups and rejects new tasks when full (Sections D.6 and D.7). Streaming delivers events before execution completes. A caller resumes reading with the same task identity, original route, unchanged request content, and an event cursor , the identifier of its last complete event. The retained history supplies later events without restarting the handler. Unavailable routes, changed content, expired history, or exhausted capacity cause explicit failure. Task controls and stream history have bounded, process-local retention; they do not provide general restart recovery. Retained-cursor replay uses the explicit Nexus stream interface, not standard MCP resumption (Sections D.14 and D.15). Trying another candidate route is separate from stream resumption. This applies only to synchronous requests, which wait for a response, with caller retry permission, a nonempty key identifying the logical request, and an explicitly idempotent operation, whose repetition produces no additional intended effect. Retry uses one ordered snapshot of eligible routes and a shared time budget. This does not authorize replay of arbitrary device actions or relocation of a partially delivered stream. Router restart reconstructs service availability rather than agent progress. OpenWrt restarts routing processes; local services re-register and peers exchange fresh snapshots instead of restoring expired leases. Configuration changes are validated before replacing active tables: invalid updates retain the last valid state, while invalid startup tables remain empty and invalid policy denies requests until repaired (Section A.11). The routing layer thus restores paths to eligible services or retained tasks; persistent action outcomes, outputs, usage, and settlement remain lifecycle responsibilities (Table 2).

4.2 Delegated agent interaction with execution environments 

An execution environment is the device-side context where an agent’s action, such as a file read or application interaction, takes effect. Following Section 3, Nexus separates this environment from the reasoning host through 

delegation , permission to act on the caller’s behalf during an invocation, and adapters that translate requests into device-specific operations. Each action is bound to an authorized environment, executed there, and followed by a result or observation returned to the agent. 

4.2.1 Binding actions to authorized environments 

A run is the persistent context of an admitted agent invocation. Its environment context identifies the selected resources, permitted operations, and access credentials. Pairing establishes device identity; delegation authorizes specified operations for a run. A paired computer may therefore permit an agent to read, but not write, its 

workspace , the directory configured for file access. Workspace grants are restricted to agent-declared capabilities and associated with the caller and project; Mobile retains its own device-binding and grant records. Device identity, permission, and readiness are checked separately. As shown in Figure 4, the agent uses the shared software development kit (SDK) to send an action and run-scoped credential to Cloud. Cloud checks the applicable resource binding and permissions, delivers the command to the selected device, and returns its result, observation, or error. This path controls device actions rather than service routing: a Computer connection need not traverse the OpenWrt agent gateway in Section 4.1. Production connections use protected web requests (HTTPS) or a protected, persistent two-way channel (secure WebSocket, WSS). Cloud nevertheless receives delegated commands and results; these connections do not conceal that data from Cloud. 

4.2.2 Executing actions through device-specific adapters 

The adapters share an action-and-result interface without making device operations interchangeable. The 

Computer Runtime , a device-side execution program, opens an outbound command channel; Browser reuses it, while Android periodically requests queued commands (Table 3). 

Computer. The Runtime runs under a local operating-system account. It signs a Cloud-issued challenge with its private key; Cloud checks the signature using the public key registered during pairing, verifying device identity. Cloud then issues a single-use ticket for the outbound channel and assigns a connection version to distinguish it from replaced connections. This supports devices without public addresses or incoming remote-login connections. Commands carry identifiers, required permissions, inputs, and deadlines. The Runtime checks the operation–permission mapping before dispatch; connection versions and message sequence numbers reject stale or repeated messages. Receipt acknowledgment remains separate from an execution result. Workspace file operations resolve paths within the configured directory, but shell commands retain the local account’s privileges: a workspace is not a security boundary for arbitrary command execution. 

Browser. The adapter executes browser actions on the caller-selected Computer, checking the active run, device binding, unexpired credential, and saved browser-control grant. It returns page descriptions and screenshot references as observations. Each stored observation has a revision number; an action supplying an expected revision older than the current one is rejected. This prevents acting on a superseded observation, but does not detect page changes that occur without a new observation being stored (Section C.14). A missing browser, offline Computer, or lost browser session—the retained browser-control context—produces an error rather than execution on a substitute device. 

Mobile. The Android client uses a paired device credential to request commands and report results over HTTPS. It executes supported actions through Android Accessibility, the operating-system facility for observing and interacting with applications under user-granted permissions. 4.2.3 Command-result retention and recovery 

A restored connection does not establish that an earlier action completed. Cloud may redeliver an unexpired Computer command, so the Runtime combines duplicate requests for the same still-running command rather than starting separate executions. Completed results are retained in a bounded encrypted local journal , a stored record indexed by command identifier. A repeated command with a retained result returns that result without re-executing the action (Section C.13).

Unlike the baseline Android client, the evaluated candidate retains one completed result in an encrypted, pairing-scoped outbox , storage for a result awaiting Cloud acknowledgment. It retries that report before requesting another command and removes the stored result after acknowledgment. This repeats result delivery rather than device execution, provided Cloud treats repeated reports as the same completion. The environment layer therefore preserves available command outcomes and leaves uncertain effects unresolved; the lifecycle component in Section 4.4 uses the run to associate action records, recovery decisions, outputs, usage, and settlement.

The software development kit (SDK) provides the application-facing interface for the routing, environment access, and invocation lifecycle described in Section 3. The developer implements a handler , the function performing an agent operation, while the SDK manages registration, request transport, resource access, interaction, and reporting. The handler retains responsibility for reasoning and action selection. Cloud, router connections, model credentials, environment grants, and pricing remain operator-configured rather than being created by the SDK.

> 4.3.3 Outputs, usage, and settlement reporting

Private Display is the caller-authorized page showing a run’s messages, progress, observations, and outputs. SDK helpers publish events and protected file references rather than modifying the page directly. Their role is reporting: a shell log does not execute a command, a browser frame reports an existing observation, and a readiness notification does not create or verify an output. Run-file uploads and writes to a selected output workspace use different interfaces and require their corresponding permissions. The runtime’s credential for writing events is separate from the caller’s permission to read them. Caller-visible events remain within the authorized run rather than being published to the Internet. Usage and service-cost reporting are also separate. After an actual model call, usage.report records its model and measured token counts; missing usage remains incomplete rather than being replaced with zero. Each logical model request has a stable report identifier so retries can be associated with the same request. Under reported pricing, the handler aggregates the applicable service cost and submits one final report per turn using a stable billing key, the identifier retained across report retries. The charge follows the configured pricing terms and authorized limit, not necessarily the model provider’s cost. File transfer, event reporting, handler completion, and settlement have separate outcomes. Some reporting failures allow execution to continue; an optional bounded outbox , storage for pending events, supports report retries but cannot recreate interrupted computation or undo device actions. Usage and cost reports are separate requests, so partial success must retain which report was accepted. An accepted cost report is likewise not proof of completed settlement. These distinctions preserve the SDK’s role as a shared interface while leaving persistent action recovery and final accounting to the lifecycle mechanisms in Section 4.4. 

4.4 Persistent agent service lifecycle and bounded accounting 

An agent service may continue after its caller disconnects, wait for user input, or require another execution attempt after a worker failure. Its lifecycle therefore cannot be represented by a single network connection. The platform must preserve which work was authorized, which action outcomes have been recorded, and which pricing terms govern the resulting charge. The Cloud component addresses this requirement through persistent execution records that connect publication, invocation, interaction, recovery, output delivery, and accounting. Following Section 3, OpenWrt determines how requests reach agents, environment adapters control device

Publication exposes an agent’s callable operations and selected deployment , the configured server running its handler , the code implementing an operation. Cloud combines the declared input requirements and interaction behavior with access policy, allowing the same service to support Web and programmatic callers without an agent-specific Web interface. 5.6 Mechanism Ablation and Sensitivity 

We examine three sources of overhead: finding a service endpoint, executing the request bridge, and redelivering output after a disconnection. Each experiment varies the relevant mechanism or execution configuration while preserving the requested operation and expected result. 

Faster route lookup without changing the decision. A route index should reduce the work needed to find an eligible endpoint while preserving which endpoint is selected. We compare indexed lookup with a full scan of all routes, using identical route entries, eligibility rules, ranking scores, and query order. For each query, we check that both implementations either return no route or select the same route with the same score. These checks run outside the timing intervals. Eleven workload settings on each of two platforms use ten paired trials of 4,000 queries per setting, with no observed selection mismatch. For each paired trial, speedup is the full-scan mean lookup time divided by the indexed mean lookup time. At 10,000 routes on OpenWrt, the median speedup is 158.4 ×, with a 95% interval of [117.9, 187.0], using 262,144 additional bytes (256 KiB) of index storage. The median trial-level 95th-percentile latencies are 0.942 𝜇 s for indexed lookup and 133.618 𝜇 s for scanning. The index saves time by avoiding unrelated routes, but matching candidates still require eligibility checks and scoring. Its advantage therefore decreases as more routes match the same requested capability. Queries with no eligible route retain the same no-result behavior, including missing and expired-route cases. The experiment identifies a storage-for-search-time tradeoff: the index accelerates the existing decision rather than replacing it with a different policy (Section A.9).

5.7 Workload Dependence and Deployment Conditions 

The experiments use controlled workloads on one host with virtualized OpenWrt, an Android emulator, and fresh model requests. Balanced order reduces temporal drift, while host activity and upstream waiting contribute variation. Task families and resource grids retain separate estimates and the outcome populations defined in Section 5.1. Shared components are fixed within each pair; intentional configuration changes, software revisions, and process-accounting changes distinguish experiment groups. These configurations are evaluated separately, without an end-to-end experiment combining all mechanisms in one runtime release. Topology determines how the results transfer to other deployments. Logical peers share a physical failure domain, and the IPv6/Relay experiment adds a laboratory bridge only to Relay while both paths traverse Cloud (Sections A.16, A.17, and A.18). The capacity grid fixes arrival rate and deadline while adding edge resources. It measures central execution relief, with admission, authorization, result delivery, and settlement still using Cloud. Independent-node scaling, whole-platform resource use, and complete Cloud loss require measurements in those deployment conditions.

# 6 Discussion and Conclusion 

6.1 Locality, Authority, and Recovery as Deployment Choices 

The results connect three deployment choices. First, a common invocation interface allows computation to move toward its input while retaining the same business operation. For the large-input hashing workload, the tested Cloud CPU ceiling meeting the fixed deadline changes from 2 to 0.25 vCPU when additional edge resources execute the computation. Small inputs already meet that deadline at 0.25 vCPU. Complete Agent workflows add model waiting and different local coordination costs, so their faster placement varies by workload. The useful choice is therefore where to perform each operation given its data, computation, and service dependencies. Second, a shared environment abstraction separates the reasoning host from the device and authority used for an action. The resource experiments preserve output and operation identities through both SDK and explicit HTTP adapters, while the SDK reduces application-side protocol code. Live revocation prevents a subsequent write without retracting an already-authorized read. The additional admission, delegation, and result handling have measurable time costs; their purpose is to preserve the requested service and access semantics across execution locations. Third, the state available after interruption determines how an invocation can continue. A committed journal result can be reused after worker loss. An external effect lacking a completion record instead calls for resource-supported reconciliation or a caller decision about retrying. A durably recorded device receipt can be retransmitted under the original command identity, with acknowledgment waiting delaying subsequent work. These experiments relate each recovery mechanism to the state it preserves and the execution decision it enables. 

6.2 Implications for Agent Service Design 

The external comparisons place these choices in concrete service settings. Over the same model and device tools, Nexus’s observed completion time is lower by a median 3.88 s among the 22 jointly successful Dify pairs, with independently realized model trajectories included in each duration. For byte-echo invocation, Dapr provides lower successful-call latency. In the separate constrained-memory experiment, Nexus operates under a smaller tested incremental-runtime ceiling. Selecting between such configurations requires both the required service behavior and the resource constraints under which it will run. More generally, execution location, action authority, and recovery state can vary independently while referring to the same logical invocation. This separation permits device-specific actions and edge-hosted computation to participate in a persistent service. It also leaves explicit dependencies: Cloud admission and settlement remain centrally managed, and external-effect uniqueness requires support at the resource that performs the effect. Larger physical deployments will need to account for these dependencies alongside node capacity, network conditions, and device behavior. 

6.3 Conclusion 

This work reveals a gap between task completion and reliable agent operation: correct final outputs can coexist with repeated external effects. Extending agents beyond the cloud therefore requires more than relocating computation; it requires preserving the relationship between authorization, execution, recovery, and settlement. Nexus addresses this problem through OpenWrt-native routing, invocation-scoped delegation, and persistent lifecycle management. Experiments demonstrate lower Cloud capacity requirements for a data-intensive workload, live enforcement of device permissions, and reuse of committed work after worker loss. The recovery results further distinguish result persistence from duplicate-effect suppression, which requires cooperating resources in the evaluated design. These findings support a broader design principle: agent execution may span heterogeneous environments, but its actions, outcomes, and charges must remain associated with the same authorized invocation. Reliable agent infrastructure must preserve this continuity, not merely deliver a successful final response.
