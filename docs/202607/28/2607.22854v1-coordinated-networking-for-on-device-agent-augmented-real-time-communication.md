## 摘要
AI智能体正在催生一种新的智能体增强实时通信（RTC）范式，其中人类专注于高层协作，而智能体自主检索、分析和实时生成信息以支持其交互。这些应用在多个领域带来了新体验：例如，当企业员工共同起草法律文件时，他们的智能体可以代表他们进行讨论和起草，免去了手动审阅彼此工作的负担。由于现有的基于云的智能体存在隐私风险和服务器成本无法扩展的问题，设备端智能体增强实时通信提供了一种有前景的替代方案。然而，这种设备端范式引入了一个新的网络挑战：由人类（用于实时视频流）和智能体（用于发送上下文文件以供分析）生成的并发流量流之间的竞争。我们设计了HFS，一个旨在确保智能体增强实时通信应用中高实时视频质量和低智能体响应时延的框架。我们通过一种应用引导的多流传输方法来实现这一目标，其中统一的应用层编排器根据实时视频流和智能体上下文流的不同应用需求共同控制其发送速率。我们在WebRTC和llama.cpp之上构建的原型表明，HAFS优于基线，实现了1.5倍的视频质量提升，同时将智能体响应时间减少了31%。

## Abstract
AI agents are enabling a new paradigm of agent-augmented real-time communication (RTC), where humans focus on high-level collaboration, while agents autonomously retrieve, analyze, and generate information in real time to support their interactions. These apps enable new experiences across various domains: for example, when corporate employees co-author a legal document, their agents can discuss and draft on their behalf, sparing them the burden of manually reviewing each other's work. As existing cloud-based agents suffer from privacy risks and unscalable server costs, on-device agent-augmented RTC offers a promising alternative. However, this on-device paradigm introduces a new networking challenge: contention between concurrent traffic flows generated by humans (for live video streaming) and agents (for sending context files for analysis). We design HFS, a framework to ensure both high live video quality and low agent response latency in agent-augmented RTC apps. We achieve the goal through an app-guided multi-flow transport approach, where a unified app-layer orchestrator jointly controls the sending rates of live video and agent context flows based on their heterogeneous app requirements. Our prototype built atop WebRTC and llama.cpp demonstrates that HAFS outperforms baselines, achieving 1.5x higher video quality while reducing agent response time by 31%.

## 1. 论文的核心问题与整体含义

- **研究背景**：AI智能体（Agent）驱动的实时通信（RTC）正在兴起，人类与智能体协同工作：人类关注高层协作，智能体自动检索、分析、生成信息。例如，企业员工远程合著法律文档时，智能体可代理部分起草与审核任务。
- **问题与动机**：
  - 现有基于云的智能体方案存在**隐私风险**（用户需上传敏感数据）和**服务器成本不可扩展**（GPU 推理成本随用户数线性增长）。
  - 设备端（On-Device）智能体是一种有前景的替代方案，但引入了**新的网络挑战**：并发流量流（人类实时视频流 + 智能体上下文文件流（如 KV Cache））竞争共享带宽，导致：
    - 人类-智能体流竞争：视频质量严重下降（VMAF 降低 53%），且恢复缓慢（>30 秒）。
    - 多智能体流竞争：多个 KV Cache 并发传输时，智能体响应时间增加 56%。
- **整体目标**：设计一个框架，同时保证高实时视频质量（高码率、低帧延迟）和低智能体响应延迟。

## 2. 论文提出的方法论

### 核心思想：应用引导的多流传输 (App-Guided Multi-Flow Transport)
- 在**应用层**设置统一编排器（Orchestrator），全局感知所有视频流和智能体上下文流，联合控制发送速率。
- 利用现代 RTC 架构中**SFU（Selective Forwarding Unit）** 将端到端路径拆分为发送端-SFU 和 SFU-接收端两段，RTT 短（p95 < 50ms），使得应用层也能实现近似网络内（in-network）的精确速率控制。

### 关键技术细节

#### (1) 人类-智能体流协调器 (Human-Agent Flow Coordinator)
- **目标**：最大化智能体流吞吐量且不干扰视频流。
- **帧级排队估计器**：结合 RTP 反馈（测量视频帧的一路延迟）和 SCTP ACK（测量帧间隔内排队延迟），得到组合帧级排队 `Q_f`。
- **多流速率控制机制 (MI/AI-MD)**：
  - **MI (Multiplicative Increase)**：当排队延迟低于帧间隔 L 时，总速率指数增长。
  - **AI (Additive Increase)**：当排队延迟在 `[L, α·Ddl)` 之间时，速率线性增加（类似 TCP 的 AI 步进）。
  - **MD (Multiplicative Decrease)**：当排队延迟接近截止时间 `α·Ddl` 时，将总速率锚定于接收端测得的 SCTP 吞吐量 `r_f`，快速排空队列。
- **视频速率控制**：基于代理流探测到的接收端吞吐量 `r_f` 估计可用带宽，优先保证视频所需码率 `b_req`，剩余容量分配给智能体流。解决了传统延迟敏感 CCA 的误判和恢复慢问题。

#### (2) 多智能体流协调器 (Multi-Agent Flow Coordinator)
- **目标**：在智能体流分配的总速率预算内，调度传输顺序以最小化智能体响应时间。
- **问题建模**：建模为两机器流水线问题（发送网络传输 + 接收 GPU 解码），采用 **Johnson 规则** 求出最优顺序：
  - 将流分为两组：网络时间 ≤ 计算时间的流（按网络时间升序）、网络时间 > 计算时间的流（按计算时间降序）。
  - 先调度第一组，再调度第二组。
- **计算时间预测**：通过单步 LLM 解码预测输出长度（输出 token 数），再结合离线预简的文件化推理解码时间函数。虽然预测有误差（MAE ~18%-36%），但调度只依赖相对顺序，对误差鲁棒。
- **鲁棒性增强**：
  - 动态更新优先级：当网络带宽变化 >20% 时，基于剩余字节重算。
  - 重叠预填充（Overlapped Prefill）：当 KV Cache 传输慢于本地预填充时，提前发送原始上下文文本，并对 KV Cache 从最后一个 token 反向流式传输，避免依赖冲突。

1. **性能提升**：

## 7. 优点

- **实用性**：仅需应用层修改，无需改动底层传输协议或网络设备，可直接部署于 WebRTC 兼容平台。
- **新颖性**：首次系统性分析并解决设备端智能体 RTC 中的多流网络竞争问题，提出帧级排队引导的速率控制。
- **跨学科整合**：将调度理论（Johnson 规则）、LLM 推理特性（预填充/解码延迟差异、KV Cache 压缩）与网络传输协调结合。
- **鲁棒设计**：对网络波动和预测误差都有应对机制（动态优先级更新、重叠预填充）。
- **低资源需求**：支持消费级 GPU（Jetson、M3 Pro）和移动设备（S25），且能利用 NPU 加速。

## 8. 不足与局限

- **扩展性未验证**：多用户 SFU 环境下，大量 SCTP 连接的内存压力可能导致吞吐量下降，论文仅作为未来工作提及。
- **跨流公平性**：HAFS 面对 Cubic 等队列构建 CCA 时会主动退让以保护视频延迟，不与外界流竞争公平份额。这种“利他”行为可能在有多个 HAFS 用户时需网络层协调（如 L4S）。
- **KV Cache 粒度依赖**：假设固定粒度（512 或 1k tokens）预填充，粗粒度浪费带宽，细粒度丢失跨块注意力，需要动态优化。
- **计算预测开销**：单步解码预测增加额外推理延迟，虽小但未被明确量化。
- **实验范围**：仅测试了 3 个 LLM 和 2 个数据集，更多模型和任务（如代码生成）有待验证。
- **未考虑 Non-Real-Time 流**：论文假设所有智能体流均为高优先级，但实际可能有后台同步等低优先级流量，HAFS 当前未区分。
