## 摘要
无服务器计算是边缘-云连续体的一种有吸引力的模型，但其无状态假设在函数需要持久数据时被打破：从远程云存储获取状态会消除在边缘运行的延迟优势。将数据保持在附近意味着复制它，而复制强制要求一个与函数执行位置以及每个应用程序所需一致性相耦合的放置决策。我们研究了在两种一致性模型（强一致性和最终复制）下函数调度和数据放置的联合问题。首先，我们将其表述为一个二元线性规划，该规划为给定的系统快照提供最优放置，并将其作为参考点。由于求解器无法扩展到超过几百个节点，我们添加了两种信息逐渐减少的启发式方法：一种基于相同完整快照的全局视图贪心方法，以及一种每个节点仅根据本地观察到的需求做出决策的聚合视图启发式方法。在一系列系统规模中，全局视图启发式方法的性能保持在最优值的百分之几以内，同时扩展到超过10^4个节点。聚合视图启发式方法牺牲了一些解的质量，但能持续适应每次调用。在客户端移动性下，集中式策略会遭受过时的快照和反复出现的延迟峰值，而聚合视图方法则保持低且稳定的客户端观察延迟。在所有实验中，数据放置对结果的影响比函数调度更大。

## Abstract
Serverless computing is an appealing model for the edge-cloud continuum, but its stateless assumption breaks down once functions need persistent data: fetching state from a distant cloud store erases the latency benefit of running at the edge. Keeping data close means replicating it, and replication forces a placement decision that is coupled with where functions execute and with the consistency each application demands. We study this joint problem of function scheduling and data placement under two consistency models, strong and eventual replication. We first formulate it as a Binary Linear Program that yields the optimal placement for a given system snapshot, and use it as a reference point. Because the solver does not scale past a few hundred nodes, we add two heuristics with progressively less information: a Global-View greedy method that works from the same complete snapshot, and an Aggregated-View heuristic in which each node decides from locally observed demand alone. Across a range of system sizes the Global-View heuristic stays within a few percent of the optimum while scaling to over $10^4$ nodes. The Aggregated-View heuristic sacrifices some solution quality, but adapts continuously to each invocation. Under client mobility, centralized policies suffer from stale snapshots and recurring latency spikes, while the Aggregated-View maintains low and stable client-observed latency. Across all experiments, data placement proves more influential than function scheduling in determining the outcome.

## 1. 论文的核心问题与整体含义（研究动机和背景）

无服务器计算（FaaS）在边缘-云连续体中极具吸引力，但其“无状态”假设在处理持久数据时失效：函数需从远端云存储获取状态，这会抵消边缘部署的低延迟优势。将数据保持在靠近执行节点处就需要复制数据，而复制决策与函数调度位置以及每个应用所需的一致性模型紧密耦合。

现有工作或只关注函数调度而忽略数据依赖，或把数据放置与一致性混为一谈，缺乏对异构一致性模型（强复制SR与最终复制ER）下联合优化的形式化建模，也缺乏从集中式到分布式信息范围逐步缩小的启发式方法的系统对比。本文旨在填补这一空白。

## 2. 论文提出的方法论：核心思想、关键技术细节

### 2.1 问题建模
- **系统模型**：将基础设施建模为层次树（云端、雾层、边缘层），节点有计算速度、存储容量；节点间有网络延迟和带宽。
- **应用模型**：函数（FaaS）有注册类和调用实例；数据以“集合”（collection）为单位，每个集合有大小和一致性策略（SR或ER）。函数可访问多个集合，但访问SR集合时一个函数最多访问一个SR集合，且写函数必须与SR领导者同节点，读函数可与任何副本同节点。ER集合可自由访问，允许远程获取。
- **联合放置问题**：同时决策（1）数据放置：每个集合的副本放在哪些节点；（2）函数调度：每个函数调用从哪个源节点路由到哪个执行节点。目标是最小化速率加权总延迟（包括执行延迟和数据获取延迟）与存储成本的加权和，参数α控制延迟-存储权衡。

### 2.2 二元线性规划（BLP）
- 形式化为二进制线性规划，变量包括：放置变量 \(x_{c,j}\)、调度变量 \(w_{f,i,j}\)、领导者选举变量 \(l_{c,j}\)、路由变量 \(r_{f,i,c,j,a}\)（ER集合远程获取），以及辅助miss指示变量 \(z_{f,i,c,j}\)。
- 约束包括：每个调用调度到唯一节点、每个集合至少一个副本、SR集合唯一领导者、读写约束、ER获取路径约束、节点存储容量约束。
- 目标函数：最小化 \((T/T_{\max} + \alpha \cdot S/S_{\max})\)，其中T为速率加权总延迟（执行+获取），S为总存储占用。

### 2.3 全局视图贪心启发式（GV）
- 假设拥有系统全局快照，分两阶段：
  1. **最小可行基线**：为每个集合放置一个副本（写密集型SR集合放在写压力最大节点，其余放云端），选举领导者，基于LCA（最近公共祖先）调度函数，基于最近副本路由远程获取。
  2. **贪心扩展**：迭代评估每个候选副本放置（c, j），计算其带来延迟节省 \(\Delta L_{c,j}\) 与存储成本 \(\alpha \cdot size_c\) 的净收益，选择正收益最大的候选并提交，更新调度和路由，直到无正收益候选。

### 2.4 聚合视图启发式（AV）
- 每个节点仅基于本地维护的状态决策：
  - **本地状态**：可达性表（\(\rho_j(c)\) 记录已知副本方向：本地、上行、子节点）、副本存储（含最后访问时间戳和领导者标志）、流量统计（指数衰减计数器）。
  - **数据放置**：
    - SR集合：周期性协议（测量-聚合-决策），基于弹性力模型：领导者受写拉力、读拉力与存储浮力平衡，通过递归评估子节点是否满足领导者下移条件；追随者复制条件类似但无兄弟项。
    - ER集合：被动复制，每次缺失时从最近副本拉取，并在本地异步创建副本（逐跳靠近消费者）。
    - 分层逐出：节点空间不足时，按最大 \(size_c \cdot (t - t_{last})\) 逐出副本，向上级节点移动。
  - **函数调度**：SR路线严格匹配领导者或副本方向；ER路线优先选择持有最多所需集合的子节点，否则向上转发。

## 3. 实验设计

### 3.1 实验设置
- **场景生成**：
  - 三层拓扑（云端、雾层、边缘层），默认分支因子10，共111节点（1云端+10雾层+100边缘层）。
  - 网络参数基于Belcastro et al.的每层范围取几何均值：边缘≈90 Mbps/3.2 ms，雾≈1 Gbps/14.1 ms，边缘-雾延迟17.3 ms，雾-云延迟34.1 ms。
  - 存储容量：云端无限，雾层可放50%总集合大小，边缘层30%。
  - 函数参考执行时间指数分布均值279 ms（基于EdgeFaaSBench实测并乘以硬件校正因子）。
  - 集合大小指数分布均值1 MB。
  - 函数访问模式：每个函数访问1-2个ER集合（或1个SR集合），80%读函数，20%写函数。
  - 客户端：100虚拟客户端，函数选择Zipf分布（偏斜1.2），源节点70%边缘/30%雾层，调用率指数分布均值0.1 req/s。
- **对比方法**：
  - BLP（最优基准，CPLEX求解，超时600秒，内存上限50GB）
  - GV（全局视图贪心）
  - AV（聚合视图分散式）
  - CO（Cloud-only：所有数据放云端，所有函数在云端执行）
  - CD（Cloud-data：数据放云端，但仅ER函数可在边缘执行并需远程获取数据）
- **评估指标**：
  - RQ1（可扩展性）：求解时间、最大驻留内存（RSS），变量规模（节点数|N|、函数数|F|、集合数|C|）。
  - RQ2（解质量）：相对于BLP的延迟差（T diff）和存储差（S diff），考察不同α（1,0.1,0.01）和一致性混合（纯ER、纯SR、50/50混合）。
  - RQ3（静态工作负载下的客户端感知延迟）：模拟240秒，比较AV、GV、BLP（0.2s、0.5s每迭代超时）的时变延迟中位数。
  - RQ4（移动客户端适应能力）：循环移动模式（每30秒迁移一次），比较相同延迟指标。

### 3.2 基准与充分性
- 实验覆盖了三种一致性混合、三种α、从10到10101节点的规模、函数和集合从10到10000的规模，每组10个随机种子，报告中位数和IQR。
- 静态和移动场景各3种一致性混合，每个240秒仿真，12秒分箱统计中位数延迟。
- 对比方法包括最优（BLP）、集中式启发式（GV）、分散式启发式（AV）以及两个朴素基线（CO、CD），较为全面。

## 6. 论文的主要结论与发现
1. **可扩展性**：BLP最多处理~1000节点（SR）或~100节点（ER/MIX），之后超时或超内存；GV可扩展到>10^4节点，在ER下仅0.16秒，MIX下160秒；AV无全局计算开销。
2. **解质量**：
   - 在α=1时，GV在ER下与CO等价（因存储成本高，不额外复制），在SR下略优于BLP（约5%更低延迟），在MIX下接近最优（中位数0%差）。
   - 随着α减小（存储成本降低），所有方法复制更激进，GV和AV延迟差距缩小至几个百分点，但存储开销显著增加（ER可达+303%）。
   - 朴素基线CO和CD表现差，CD的ER下延迟差高达+95%，证明数据远离计算点有害。
3. **静态工作负载**：AV在ER和MIX下延迟低于所有集中式方法（因主动复制将数据推向边缘），SR下所有方法接近。集中式方法有冷启动过程。
4. **移动客户端**：BLP和GV出现周期性延迟尖峰（因快照过时），AV始终保持低且稳定的延迟，证明基于调用的反应式策略能更好适应动态需求。在SR下GV表现反而差（因领导者固定无法适应写者移动）。

## 7. 优点
- **问题形式化完整**：首次在BLP中联合优化函数调度、数据放置与异构一致性（SR/ER），并考虑存储成本，可作为理论基准。
- **启发式设计有层次**：从全局到局部逐步降低信息依赖，结构清晰，GV与AV设计分别利用不同优化模式（贪心扩展 vs. 力平衡+被动复制）。
- **实验全面**：涵盖可扩展性、解质量、静态和动态工作负载，对比了多种基线和不同α/一致性搭配，结论可靠。
- **关键洞察**：发现数据放置比函数调度影响更大，分散式方法在动态环境下优于集中式方法，为边缘FaaS系统设计提供实用指导。

## 8. 不足与局限
- **实验覆盖有限**：拓扑形状固定为三层平衡树，未考虑多级雾或树非平衡情况；工作负载假设静态访问模式已知，未考虑未知或动态模式。
- **移动模式单一**：仅测试了周期性循环移动，未评估随机移动或突发移动模型。
- **存储成本参数α选择**：仅测试了三个值（1,0.1,0.01），未进行更细粒度的敏感性分析。
- **无实际部署验证**：所有评估基于仿真，未在真实边缘-云平台（如Kubernetes+分布式KVStore）上实现AV协议。
- **未考虑故障和一致性协议开销**：模型假设可靠网络和完美故障处理（云端始终保留备份），但实际中领导者切换、网络分区等未建模。
- **内存模型简化**：忽略函数冷启动和内存竞争，仅假设数据访问延迟占主导地位。
