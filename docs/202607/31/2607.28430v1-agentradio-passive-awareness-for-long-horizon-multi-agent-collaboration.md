## 摘要
理解大型代码库对于大型语言模型（LLM）智能体而言是一项长时程任务：回答单个问题可能需要构建并运行软件、跨文件追踪执行过程，并在数十分钟内综合证据。在 SWE-Atlas QnA（一个针对生产仓库长时程问题的基准测试）上，单个 Claude Code 智能体（Opus 4.6）仅解决了 32.3% 的任务。在上下文干净的智能体之间划分工作可缓解这一局限。然而，代码理解的子任务相互依存。一个智能体的发现可能改写另一个智能体的任务，因此智能体必须在执行期间进行协调，而不仅仅是在阶段边界处。现有多智能体系统仅通过分阶段交接或同步轮次支持阶段之间的此类交换。通信与工作仍然相互排斥。执行过程中产生的发现直到下一个边界才能共享。我们提出 AgentRadio，一个异步消息传递层，为编码智能体框架提供三个原语：线程、消息和等待提及。最后一个原语作为后台任务运行，在不中断前台工作的情况下呈现队友消息，从而使每个智能体保持对同伴的被动感知，并将新发现融入其正在进行的任务中。在分工与协商的五阶段协议下，由 AgentRadio 组织的四个智能体解决了 62.1% 的任务，比单个智能体高 29.8 个百分点，也高于使用更新 Opus 4.8 的 Claude Code（57.2%）。基于量规的分析显示，增益随任务难度增加而增长，这与中途修正作为潜在机制相一致。我们的代码可在 https://github.com/Coral-Protocol/AgentRadio 获取。

## Abstract
Understanding large codebases is a long-horizon task for Large Language Model (LLM) agents: answering a single question can require building and running the software, tracing execution across files, and synthesizing evidence over tens of minutes. On SWE-Atlas QnA, a benchmark of long-horizon questions over production repositories, a single Claude Code agent (Opus 4.6) resolves only 32.3% of tasks. Dividing the work among agents with clean contexts mitigates this limitation. However, the subtasks of code comprehension are interdependent. One agent's findings can rewrite another's task, so agents must coordinate during execution, not only at phase boundaries. Existing multi-agent systems support such exchange only between phases, through staged handoffs or synchronized rounds. Communication and work remain mutually exclusive. A discovery made mid-execution cannot be shared until the next boundary. We present AgentRadio, an asynchronous message-passing layer that equips coding-agent harnesses with three primitives: threads, messages, and waiting for mentions. The last runs as a background task, surfacing teammates' messages without interrupting foreground work, so each agent remains passively aware of its peers and folds new findings into its ongoing task. Under a five-phase protocol of division of labor and negotiation, four agents organized by AgentRadio resolve 62.1% of tasks, 29.8 points above a single agent and above Claude Code with the newer Opus 4.8 (57.2%). Rubric-level analysis shows the gain growing with task difficulty, consistent with mid-course correction as the underlying mechanism. Our code is available at https://github.com/Coral-Protocol/AgentRadio.

### 1. 核心问题与整体含义（研究动机与背景）

- **背景**：LLM 智能体面临的任务正在变得越来越长。从单步问答发展到操作实时网站、完整的计算机环境、解决真实 GitHub issue，乃至复制整篇研究论文。代码库理解是其中一个极端场景：回答一个关于生产系统行为的问题，需要构建并运行软件、跨文件追踪执行、在数十分钟内综合证据。
- **核心问题**：单个智能体的有效注意力会随上下文增长而退化（Lost in the Middle、长上下文性能下降、多轮对话迷失等）。在 SWE-Atlas QnA 基准上，单个 Claude Code 智能体（Opus 4.6）仅解决 32.3% 的任务。
- **现有方案的局限**：将工作分给多个上下文干净的智能体是自然对策，但代码理解的子任务高度相互依赖——一个智能体的发现可能改写另一个智能体的任务方向。这意味着协调必须发生在**执行过程中**，而非仅在阶段边界。
- **文献空白**：一项对 1400+ 篇 LLM 多智能体论文的调查发现，异步性"典型缺失"，仅 22 篇涉及。现有系统要么是"并行但隔离"（如 Anthropic 的研究系统批处理等待），要么是"并行但轮次同步"（如辩论系统仅在轮间交换），要么是"相邻形式的异步"（如共享记忆需主动读取、队列仅从规划器到工作器等）。**没有一个系统能让正在工作的智能体被动地听到同伴的消息**。
- **核心主张**："通信与工作相互排斥"这一假设是性能瓶颈的来源；AgentRadio 通过后台消息监听打破这一互斥，实现**被动感知（Passive Awareness）**，使中期发现可以实时共享并纠正执行方向。

### 2. 方法论：核心思想、关键技术细节与算法流程

#### 核心思想
- 将"通信"与"工作"解耦。智能体在正常工作的同时，后台进程会持续监听队友的 @提及消息，在下个工作步骤的边界处呈现，不打断正在执行的命令（类比：收音机不干扰司机双手握方向盘）。
- 关键洞察：`wait_for_mention` 作为**后台任务**运行，而非前台阻塞。这一"单比特差异"就是隔离的干预变量。

#### 三个通信原语
1. **create_thread(name, participants)**：在消息服务器上创建命名会话线程。
2. **send_message(thread, content, mentions)**：向线程追加消息并立即返回（非阻塞），可 @提及特定智能体。
3. **wait_for_mention(timeout)**：阻塞直到收到提及该智能体的消息，返回消息及所有线程的完整快照。**运行位置是该层的唯一自由度**——前台运行为阻塞接收，后台运行为被动感知。

#### 形式化区分
- 将智能体的运行写为步骤序列 s₁, s₂, ...（每步一次工具调用），M(t) 为第 t 步可见的队友消息集合。
- **阻塞接收**：消息仅在专用于 `wait_for_mention` 的步骤中增长，每次听到消息都消耗一个工作步骤。
- **被动感知**：M(t) 包含第 t 步之前发出的所有消息，且**没有任何步骤被用于监听**。

#### 五阶段协议（Algorithm 1）
- 共 4 个智能体，其中 agent-1 兼任**组装者（assembler）**，控制所有阶段转换（需收集每个智能体的明确批准）。
- **P1 探索**：每智能体启动后台监视器，独立探索仓库，草拟子问题。不发送任何消息。
- **P2 分工**：组装者打开规划线程。智能体汇聚 P1 发现、协商子问题划分，反复修订直至全体批准。触发消息的事件：提出/修改划分、发现与队友提议冲突、投出批准票。
- **P3 执行**：各智能体独立攻克自己的子问题。被动感知下，发现触发协作日志（worklog）即时发帖：涉及队友子问题的发现、与已同意计划的矛盾、障碍、已放弃的死胡同。
- **P4 审查**：每智能体在自己的结果线程中广播有证据的发现。触发审查消息的事件：与审阅者自己证据的事实冲突、证据过于单薄、审阅者在自身工作中看到但发现中未提及的现象。可将子问题退回 P3。
- **P5 提交**：组装者综合已批准结果起草最终答案，广播最后一轮批准，然后提交。

#### 实现
- 消息服务器是独立进程，实现三个原语；智能体通过三个薄壳脚本访问。
- 框架端只需"可以后台运行 shell 命令"这一能力（主流编码框架均已具备），**框架本身无需修改**。
- 关键优势：阻塞→被动切换**不增加 LLM 调用次数**，因为监听器是操作系统进程而非智能体步骤；唯一新增的 token 是浮现出来的消息内容。

### 3. 实验设计

#### 基准与数据
- **SWE-Atlas QnA**：124 道专家编写的问题，覆盖 11 个生产代码库、4 种语言（44 个架构与系统设计、37 个根因分析、28 个代码上手、11 个安全、4 个 API 与库集成）。
- 代码库来自 SWE-Bench Pro，通过 Copyleft 许可和提交固定的 Docker 镜像抵抗训练数据污染。
- 问题刻意使用非限定自然语言，静态探索不够，必须构建、运行、跟踪执行才能回答。
- 评分严格：共 1,306 条量规（平均每任务 12.3 条），每条是原子化事实陈述，经三轮专家多数投票+两轮人工审查；所有量规通过才算任务解决；修改源文件自动判失败。
- 评判者：基准自带的 LLM 评判器（Claude Opus 4.5），所有配置固定。

#### 方法阶梯（5 种配置）
- **B0**：单个 Claude Code 智能体。
- **B1**：6 次独立的单智能体运行，取最好结果（计算匹配基线）。
- **L1**：4 智能体 + 分工（一个探索后划分，独立解决，无审查合并）。
- **L2**：L1 + 协商（独立探索发表发现→提议划分→全员批准→交叉审查；即阻塞接收下的完整五阶段协议）。
- **L3**：同一协议 + 被动感知（完整 AgentRadio）。

#### 模型
- 两种模型完整重复整个阶梯：Claude Opus 4.6 和 DeepSeek V4 Pro，同一框架、同一设置（高思考强度、温度 0）。
- 额外对比：单智能体 Opus 4.8（公开榜单最强单智能体条目，57.2%）。

#### 统计方法
- 所有比较均为配对设计：L2→L3 仅改变通信模式，使用精确 McNemar 检验。

### 6. 主要结论与发现

- **主结果**：L3（AgentRadio 全栈）在 Opus 4.6 上达到 62.1% 任务准确率，比单智能体提升 29.8 个百分点（相对 +92%），超过单智能体 Opus 4.8（57.2%）；在 DeepSeek V4 Pro 上从 29.0% 提升至 50.8%。
- **每一步都有效**：分工 +7.2（Opus）、+2.4（DeepSeek）；协商 +12.1、+8.1；被动感知 +10.5、+11.3。
- **被动感知层的统计显著性**：L3 vs L2 精确 McNemar 检验 p=0.0023（Opus）/p=0.0026（DeepSeek），仅 2 和 3 个任务回退。
- **结构优于计算**：全栈（$19.45/任务）显著优于计算匹配的最佳 6 次采样（$17.76/任务），62.1% vs 37.9%（Opus）；50.8% vs 31.4%（DeepSeek）。
- **收益随难度增长**：被动感知在 L2 缺失 1-3 条量规的组中每任务增加 0.3-0.5 条量规，缺失 4 条时 +1.2，缺失 5 条时 +2.0。中期修正机制得到一致性支持。
- **类别异质性**：架构类别是最大赢家（Opus 上 +15 任务），因为这类问题最容易跨越划分边界；根因分析受益于朴素分工（探索性假设可独立进行）。
- **案例研究机制**：MinIO 案例演示了阻塞下发现"两次发生两次消失"→被动感知下同一发现变为全队证据并翻转 5 条量规；Grafana 案例表明被动感知只能放大已有发现，无法创造无人形成的概念，界定了方法的边界。

### 7. 优点

- **问题选择精准**：针对真实存在且已量化的瓶颈（通信与工作互斥），新颖度明确。
- **最小干预设计**：不设计新框架、新模型或新工作流，只增加一个背景监听原语，隔离度极高。论文精确量化"何时听到消息"这一单比特差异。
- **成本透明的对照实验**：B1 设计优雅地排除了"预算假说"，且被动感知层仅增加约 1/4 成本就换来 10.5/11.3 点增益。
- **分析纵深**：量规级归因（毛增/毛减的瀑布图）、难度分层（支持机制解释）、双模型验证、配对统计检验——远超出典型的"表格+结论"标准。
- **案例研究精选**：正向案例展示机制如何运作，反向边界案例如实展示其局限，增加了可信度。
- **诚实且可复现**：开源代码、固定评判者、配对比较。

### 8. 不足与局限

- **领域覆盖窄**：仅在代码库理解（SWE-Atlas QnA）上验证，领域特征可能与"被动感知是否有用"高度相关。在更序列化的任务（如 Minecraft 规划）或多智能体增益为负的区域（单智能体 >45% 准确率时）可能失效。
- **配置固定**：五阶段协议是人工设计的、固定的。未探索更自由的自适应协作策略，也未探索不同智能体数量（仅 4 个）的影响。
- **成本上升**：完整栈成本约为单智能体的 6 倍，即使控制了预算假说，"成本-收益"在实际工程中的可接受性仍存疑。
- **潜在干扰效应**：瀑布图表明被动感知层损失 23 条量规（推测消息可能将智能体从本应通过的证据线上拉走），论文承认但未彻底解析该机制。
- **未讨论失败模式的深层原因**：哪类消息是误导性的？是否与消息内容、时机或发送者置信度相关？没有细粒度分类。
- **模型有限、版本可能过时**：两个模型（一个闭源、一个开源）均来自 2026 年中期；Opus 4.8 也只做了单智能体对照，未测试其在多智能体配置下的表现。未进行评判者消融。
- **单次运行现实**：主结果每次配置仅运行一次，尽管配对设计减轻了差异噪声，但绝对数值仍受采样波动影响（表 3 中 B0 三次运行的 SD 达 5.1 个百分点）。
